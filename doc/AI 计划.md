# AI 计划

2026-11-04 定的方向，四条都排进来了，**第一批只交付两条**（理由在「顺序」那一节）。
这份文档定的是形状、成本、隐私口径与验收，不是提示词手册。

决定过的三件事，写在最前面：

1. **端**：先 BYOK（沿用翻译那一族：OpenAI 兼容端点 + 读者自己的密钥，本地 0600），
   服务端代理作为第二档（接已有的 CloudBase，与 `folio-redeem` 同一套部署与密钥习惯）。
2. **第一批**：选区问 AI + `.txt` 切章规则草案。
3. **不做**：模型自动改配置、自动写批注、把整本书上云建索引、OCR、看图说话。

## 一、端：一层 provider，两档实现

今天已有的地基：`folio-core/src/net/translate`（三只引擎：Google / OpenAI 兼容 / DeepL）、
设置里那一屏、密钥落 `config.json`（unix 下 0600）、Android 的 `INTERNET` 权限。
**AI 不再新长一条网络路径**：把「一个 chat/completions 形态的端点 + 密钥 + 模型名 +
超时 + 错误分类 + 用量」收成一层，翻译与 AI 共用它。

```
folio_core::net::ai
  Provider   ← 端点、模型、密钥、是否走代理
  ask(prompt, context, opts) -> Answer        // 一次性问答，流式先不做
  Usage { prompt_tokens, completion_tokens }  // 每次回一句，好记账与好说话
```

三档错误必须分开，别的都是细节：**没配好端点**（界面不该出现这一格，判据与真发请求
同一份）、**网络/端点错**（说清是哪一步）、**模型答得不像话**（截断、空答、拒答）。翻译那一族已经把
「静默把一次点击变成点了没反应」当成最坏的事（`links.rs` 里那句注释讲的就是同一个原则），
AI 照同一条办。

**代理那一档（第二批再动）**：一个云函数收请求、按设备与会员天数计量、转发到服务端密钥。
它买到的是「读者不必自己搞 key」，付出的是「**读者的书本文经过你的服务器**」——
这是隐私口径上的一个台阶，不是工程难度：

| | BYOK | 服务端代理 |
|---|---|---|
| 正文离开谁的设备 | 只到读者自己填的端点 | 到 CloudBase，再到模型 |
| 谁付钱 | 读者 | 你（要配额与防刷） |
| 已有地基 | 翻译那条的形状 | `folio-redeem` 的验单 + `folio_redemptions` 台账 + 设备号 |
| 界面上要说清 | 「送到 <host>」 | 「经 folio 的服务，按会员天数计次」 |

两档并存时**默认 BYOK**，代理只在读者主动选「用 folio 的额度」时走。

## 二、四刀，按可交付的顺序

### ① 选区问 AI（第一批）

**用户故事**：读到一段引典故、一句外语、一段绕的地方，选中它，问一句「这段说什么」，
在原地读到答案，不用离开这本书、不用复制粘贴去外部 App。

**形状**：划词卡片（`components/selection.rs` 的 `selection_menu`）加一格，图标 +
两三字标签（与「复制 / 划线 / 笔记 / 翻译 / 分享」同一排，别插书名）。
浮层复用翻译那一族已有的那张卡，**不另起第二套浮层**。问法先给三档预设，不做自由输入框：

- 「解释这段」—— 默认档；
- 「这段里的名词」—— 人名、地名、典故、术语；
- 「这段的原文说的是什么」—— 给古文、方言、翻译腔用。

**上下文**：只送选中的那段 + 前后各一截（约 300 字）+ 书名 + 章节名。**不送整章** ——
选区平均一次 150 字，加上下文约 700 字（≈1000 token 输入），一本书读下来问十次，
量级是每次几厘到一分（按端点现价，别在代码里写死单价）。

**落库**：不落。答案是一次性的；要留，读者选中答案 → 「加笔记」（今天那条笔记链路已经够）。
这条决定省下的是「AI 写的东西混进读者的批注里」那一整类麻烦。

**验收**：没配端点时这一格**不出现**（与听书那条 `speech_entry_visible` 同一判据家族）；
离线点它要当场说一句；错误不静默。CI 里钉得住的是「卡片动作的数量与顺序」与
「provider 层的请求体形状」（mock 端点），钉不住的是答案质量 —— 答案质量**不进门**，
只进人工看。

**2026-11-05 落地时补的两条**：

- 「没配端点」有**四种**，判据只写在 `net::ai::configured` 一处（界面那格与真发请求
  读同一份）：没开、地址空、两处模型都空、**只有出厂那份地址且 key 没填**。最后一种
  不是抬杠：`config::OpenAi` 的 `Default` 把官方地址与模型现成填好了（翻译那一档为了
  读者只贴 key 就能用），所以「拨开开关就能问」看着成立，按下那一格却会把正文发去
  一个读者从没配过的服务、只换一个 401。本地 Ollama / LM Studio 那条路照旧通 ——
  地址是读者自己填的，空 key 也问得出（这一层不猜「这个服务要不要 key」）。
- 载荷是**五项**：书名、章名、选中那段、前 300 字、后 300 字（`CONTEXT_BUDGET` 一份
  一侧，不是两侧合算）。章名走 `hit_place_at`，定版式那本书没有章表，直接取章名会递
  一个空串。这五项就是「会离开这台设备的字」的清单，**加一格等于改隐私口径**。

**代价**：`net/ai` 一层 + 卡片一格 + 一张浮层 ≈ +250～350 行，含测试。

### ② `.txt` 切章规则草案（第一批）

**用户故事**：读者手上那本 `.txt` 整本是一整篇（写法不在出厂表里），今天他得自己想一条
正则；现在他说「帮我看看这本书该怎么切」。

**形状**：设置第 13 格「TXT 分章规则」里那颗「加一条」旁边多一颗「按这本书建议」。
输入是**已经量好的东西**，不是整本书：头部 60 行 + 引擎现扫出来的候选标记行 30 条
（`novel::detect` 扫 hits 那一趟本来就有这些行，不必再切一遍）。
输出是一个草案：`{name, kind, pattern, numbering}` + 一句给人看的理由。

**硬约束，这条决定整刀的形**：

1. 草案**不自动生效**。它落成界面上的一行「建议：按 `^\s*Chapter\s+([0-9]+)` 切，
   会切成 214 章」，读者按「用上」才进 `Edits.extra`。
   理由不是不信任模型，是仓库里已经写死的规矩：**不变量不进数据**，
   而「一条规则吃掉正文」的后果今天已经量过（红楼那本被「编号」那族吃掉一整本，
   修法就是收紧那条模式的尾巴）。模型只是**多了一个会写坏规则的读者**，
   而它没有眼睛。
2. 草案要先过**本地那道自检**（`compile()` 的逐条降级 + 正反例），再给预览：
   按它切会得到多少章、正文中位数多少字。这两件事都不依赖模型，是引擎已经会做的。
3. 只给建议，不改**已有**条目；不删出厂规则；不碰阈值那一组。

**成本（2026-11-05 在八本真书上量的）**：载荷不是「约 1500 字」—— 样本 = 头部 60 行 +
候选 30 条，每行收在「出厂那格 `title_max_chars` + 20」，实测
**2142–2934 字**（上限 5400，`rulinwaishi` 2934 / `nahan` 2142）。预览是**整本重扫一遍**：
debug 构建下 73 ms（《老残游记》13 万字）到 **900 ms**（《红楼梦》92 万字），
release 按既有经验再快几倍 —— 那一格与网络往返同住一个后台作业，界面在等的那张卡上。
一本书一次，不做缓存也不心疼。
**验收**：mock 端点钉「草案解不开/自检不过/预览 0 章」三种坏结果都**拒在界面上**，
不进配置；模型答非所问（返回不是 JSON）退回「这次没帮上」而不是瞎填。
**代价**：≈ +180～260 行（含预览：预览复用 `split_with`，不用新写切章器）。

**2026-11-05 落地时改的一处形状**：入口**不在设置那一屏**，在读书这一侧 —— 目录右上角
「⋯」里多一件「建议切章」，只在「这一本是 `.txt`」且「端点填全了」两条都成立时出现。
理由写在 `model/rules_draft.rs` 模块头，一句话版是：**草案的输入与预览都是一本书的事，
而设置那一屏手里没有书**。摆在那儿要么猜哪本（猜错就是一条全局生效的错规则），要么新加
一册「当前开着的书」的全局状态。想给**没开着**的那本要规则，仍然走设置那一屏自己写一条。
卡片上「用上」按 `Preview::is_usable` 出现：切出 1 章、或中位字数不到 `min_median_chapter_chars`
那条门，就没有那颗按钮（聊斋那本按「第X回」切正好是这一档的反例：预览 1 章）。

### ③ 章末 / 卷末小结（第二批）

**用户故事**：读完一章，底栏或卡片上多一格「这一章说了什么」。

这一刀贵在三件事，全部有解，但要写清：

- **调用量**：一本 300 章的书 = 300 次，每次输入按一章正文（中文一章 2000–5000 字
  ≈ 3000–7500 token）→ 整本一次跑完是 **1～2M token 输入**。所以必须**按需生成**：
  读者翻到那一章的末屏才要，绝不批量预跑。
- **落库与失效**：小结要存（否则每帧重问）。新表 `ai_summaries(book_id, chapter,
  content_hash, model, text, created_at)`，键里必须带**那一章正文的内容哈希**与
  **模型名** —— 换了模型不重生成旧章是可接受的，但换了正文还不重生成就是假账。
  库不需要兼容（重导入就行）。
- **UI 落点**：它要占阅读页的一格，而那一屏今天已经排得满（顶栏返回/书签/目录，
  底栏 目录→放大→夜间→设置）。建议落「目录面板新增一栏」而不是正文里，
  先别动正文布局。

**验收**：无网络时读已缓存的小结要能成；生成中不挡翻页；失败只在那一格说话。
**代价**：≈ +400～500 行（含表与迁移一档）。

### 第④刀 书内问答（RAG，第三批，先不做）

**用户故事**：「这个人后来怎么样了」——对着一本书提问，答案带「在第几章」。

地基有一半是现成的：`search` 那套**现读现扫**（不建索引、零成本、已经能定位到命中偏移）、
`Locator{chapter, offset}` + `anchor::relocate` 能把答案**指回原文那一处**。
缺的是切块与召回打分，以及「多段上下文 → 一次归纳 → 逐段引用」。

**为什么它排在最后**：它的成本结构与①②不同 —— 问答要送 3–6 段（≈6000 token 输入）
且读者会连问；它的质量最差也最难验收（答得不像话时，界面上没有任何东西能自证）；
而它最容易被误做成「把整本书上云建向量索引」，那是隐私上的一个大台阶，
不该顺手替读者决定。**这一刀开工前要先回答三个问题**：
本地检索够不够（大概率对小说够，人物关系类问题不够）、要不要 embedding（要就得选
「云端 embedding」=正文外流）、以及答案要不要标「AI 生成，可能错」。

## 三、几件全局的规矩，四条刀都要守

1. **界面上永远说得出「这次请求去了哪儿」**：设置那一屏写明端点 host；代理档写明
   经 folio 服务。不写「AI 会保护你的隐私」这种话。
2. **日志不落正文**：只落模型名、token 数、耗时、错误类别。这是仓库既有日志纪律的延伸
   （书库/容器/排版那几段才是要出声的地方），正文与答案都不是诊断信息。
3. **AI 写不进读者的痕迹**：批注、书签、笔记三张表**不接受**任何 AI 写入。
   要留，必须由读者从答案里选中再按一次「加笔记」。
4. **默认关**：新端点填好也不自动出现入口，读者在设置里勾「允许 AI」才算开。
   这一条买的是「升级后没人莫名其妙发出请求」。
5. **不写死单价、不写死模型名**：价与模型都住在配置里，代码只认「端点 + 模型 + 上限」。

## 四、顺序与为什么第一批只有两条

| 刀 | 批次 | 一次成本量级 | 代码量 | 能自动验的程度 |
|---|---|---|---|---|
| ① 选区问 AI | **第一批** | ≈1k 输入 / 300 输出 | +250～350 | provider 层与卡片形状可钉，答案质量只能人看 |
| ② 规则草案 | **第一批** | ≈2.5k 输入 / 60 输出 | +180～260 | 高：坏草案能被本地自检当场拒掉 |
| ③ 章末小结 | 第二批 | 3–7k 输入 / 一章 | +400～500 | 中：要新表与失效键 |
| ④ 书内问答 | 第三批（待三个问题有答案） | 6k 输入 / 次 | 未估 | 低：最难验收，且隐私口径要先定 |

四条都排进来了，但第一批只交①②两条，理由不是排期话术：**①②共用同一层 provider，
而这两刀的验收都能在没有眼睛的环境里做**（②的草案由本地自检与预览把关，①只验形状与降级）。
③④各自要新地基（一张表、一套召回），把它们挤进第一批等于同时开三个未知数。

第一批开工前还有两件小事要办：`net/translate` 那一族要先**下沉**成共用的一层
（现在它是翻译专用，AI 直接复用会牵进翻译的语义），以及设置里那一格「允许 AI」的形状
（与「翻译」那一组同屏还是各自一组 —— 建议同组，因为共用端点与密钥）。
