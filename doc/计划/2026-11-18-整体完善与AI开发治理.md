**1. 项目方向应保持稳定，把下一阶段投入转向可靠性与可验证开发。**

Folio 的主线是 Rust + GPUI 原生阅读器，自研排版，支持可重排与定版式两类文档。14 个 workspace crate 已将格式、排版、字体、存储、网络、搜索等机制拆开；folio-core 负责入口映射与编排，folio-app 是唯一直接依赖 GPUI 的应用 crate。此次通过 `cargo metadata --no-deps --offline --locked --format-version 1` 核对了 workspace 清单与直接依赖。

静态统计为 426 个 Rust 文件、243,812 个物理行，包含注释、空行、测试和 examples，不代表纯生产代码量；检索到约 2,700 个测试属性，不代表本轮测试通过数。folio-app 约 10.95 万行，folio-format 约 5.51 万行，两者是主要复杂度集中区。按统一物理行统计，114 个 Rust 文件超过 700 行、73 个超过 900 行、53 个超过 1,200 行；这是规模信号，不能直接据此判定职责混乱。

值得保留的设计：Document/Content 两族统一入口；章内字符偏移与文本指纹锚点；排版、分页与绘制分开；缓存失效键集中构造；导入内容寻址；SQLite 锁纪律与迁移；协议依赖 Transport，便于离线测试；UI 按 reader/shelf/notes/settings 等能力纵切。

当前阶段不建议继续以增加格式、平台入口或新的 AI Runtime 为主要目标。先让已有阅读、数据、同步、备份和发布能力形成可证明的完整链路。

**2. Tide 对 AI 开发的限制，由五层机制共同完成。**

| 层次 | Tide 的实现 | 对 Folio 的价值 |
| --- | --- | --- |
| 指令入口 | 根 AGENTS.md 路由到工程标准、领域文档和 change gate | 缩短默认上下文，避免每个 Agent 自己选择规则 |
| 规则注册 | 稳定 Rule ID，记录 owner、scope、enforcement | 每条禁令有负责的代码与验收方式 |
| 自动检查 | 检查版本事实、文档分类、隐藏指令入口、skills、依赖与文件基线 | 阻断看起来合理但越界的新增实现 |
| 检查器测试 | 故意构造越界、遗漏、路径穿越、基线膨胀等负例 | 防止检查脚本空转或被顺手放宽 |
| CI 与审阅 | 本地和 CI 共用入口，基线比较历史版本，跨平台分别留证据 | 结果能复查，不能只凭 Agent 声称完成 |

依据为 Tide 的 `AGENTS.md`、`docs/tide-engineering-standard.md`、`config/tide-governance.json`、`scripts/check-project-governance.mjs`、`scripts/project-agent-instructions.mjs`、`scripts/check-project-governance.test.mjs` 和 `.github/workflows/quality-gates.yml`。

Tide 当前注册了 58 条规则、98 份文档、11 条开发 skills。此次实际执行 `node scripts/check-project-governance.mjs` 成功，输出 219 个超过 warning threshold 的文件、16 个受零增长基线约束的超限文件。这里只执行了治理检查，没有执行 Tide 的产品测试，也没有验证 GitHub 服务端是否设置了 required checks 或分支保护。

它有三个特别值得借鉴的细节：基线与历史版本比较，不能同时修改源码和基线来伪造合格；扫描隐藏工具目录，防止另写一份私有规则；区分 project skill 与 reference skill，通用示例不自动成为项目实现方案。

约束能力也有明确边界：AGENTS.md 和 skills 是行为指导；检查器、编译器、测试和 CI 才能拒绝具体产物。拥有任意文件写权限的 Agent 仍可能修改检查器，因此治理文件自身也需要审阅与负向测试。代码托管平台的合并保护属于仓库设置，需要单独确认，不能从 workflow 文件推断已启用。

Tide 产品内置 Agent 的权限、ChangeSet、工具授权与沙箱属于另一类运行时机制。Folio 当前的 AI 问答无需为了限制开发 Agent 而引入这套产品架构。

| 注释类型 | 处理原则 | 例子 |
| --- | --- | --- |
| 直接复述代码 | 删除 | “读配置”“返回结果”“把值存进去”等可从下一行判断的说明 |
| 相同规则多处重复 | 在规则所属处保留一份，调用处只写必要例外 | 关停顺序、GPUI 唯一依赖方、re-export 路径兼容 |
| 开发过程、旧方案、失败流水 | 删除；确有长期价值的结论并入已有领域文档或 ADR | “原先在哪个 crate”“某次 CI 红了”“后来改成……” |
| 旧性能测量 | 代码只留当前选择理由；可复现数据进基准记录 | z/s 对比、包体大小、旧设备耗时，不当作当前保证 |
| API 契约 | 精简后保留 | 单位、范围、坐标系、空值/默认值、错误语义、稳定序列化 |
| 安全和正确性不变量 | 就地保留，不能只留下远端链接 | unsafe 的 SAFETY、锁顺序、取消/关停、授权、数据保全、溢出与边界 |
| 平台或依赖特殊约束 | 留触发条件、后果与移除条件 | cargo-ndk API 26、tts Bridge/R8、GPUI 同 rev、release panic=abort |
| 标准引用、许可证、工具指令、doc test | 保留或专项验证 | SPDX/版权、规范编号、lint/format 指令、Rust 文档代码块 |

写作默认：模块头说明职责与边界，通常 3–8 行足够；普通 API 文档通常 1–3 行，复杂状态机、算法或安全约束允许更长。数字是编辑参考，不是删除配额。注释说清“为什么必须这样”和“调用者容易犯什么错”，不解释 Rust 基础语法、不替变量名翻译中文、不写本轮任务流水。

执行顺序分三批：

1. **C01：构建清单与公共入口。** 精简根 Cargo.toml、app/core 的 Cargo.toml 和 core/lib.rs。三份清单现有 593 行独占行注释，初步目标减少约 50%–70%，以逐段审阅后的必要信息为准，不强行达标。配置值、依赖、features、rev、profile 和导出符号保持一致。
2. **C02：基础设施与配置。** 在 S01/D01 后整理 diagnostics、logging、services、config、store/books；避免与逻辑修复混成无法审查的大 diff。字段单位、serde 兼容、锁与文件生命周期约束优先保留。完成这一批后冻结首轮规模基线；其它未处理文件按现状登记。
3. **C03：阅读器与格式引擎。** 随 A01/A02、M01/M02、F01/F02 等领域工作分批整理 session、chapter_layout、collect/wrap、provider。先核对状态所有者、坐标和缓存规则，再精简；不全仓机械搜索替换。

纯注释变更与行为变更分别提交可审阅的 diff。Rust 需检查普通 token 一致，并额外识别 doc attribute、doc test、宏读取的文档和工具指令；TOML 比较解析后的配置值。不能用删除所有 `//`/`#` 的正则证明等价，因为字符串、嵌入样例和工具指令可能包含这些字符。必要时只运行受影响 doc test、契约检查或编译，不为可逆的纯注释清理新增实现镜像测试或启动全量测试。

每批交付报告：处理文件、注释减少行数、保留的关键约束、文档去重/迁移位置、语义一致性验证。迁出的内容要经过合并与删减，不将全部旧注释倒进另一份巨型文档；第三方技能、vendor/reference、生成代码和许可证内容不在此清理范围。

防回潮方案：`folio-change-workflow` 提醒审阅本次新增注释；`folio-architecture-review` 检查注释是否掩盖复杂职责。治理工具可对新增长段注释（例如连续超过 12 行）给出提示，但不按行数直接拒绝合法说明，也不把注释占比变成硬门槛。只有可确定的过时引用、重复事实和禁用模式才逐步加入自动检查。

**8. 数据可靠性需要明确操作边界和失败后的状态。**

D01 不将启动检查变成删除入口。`Path::exists()` 的 false 同时可能包含不存在和访问错误，后续用能够区分原因的 API；书文件缺失时保留 book_id、content_hash、批注、书签与进度，提供重新关联或重新导入后的恢复路径。清理可再生缓存与销毁用户数据分别处理。新增 unavailable 状态若进入数据库，使用追加迁移而非重写历史迁移。

D03 的恢复目标：先在临时位置校验 zip 路径、数量、总解压大小、数据库完整性和书文件引用；拒绝目录穿越、绝对路径、符号链接与不兼容版本。恢复进入明确维护窗口，停止会写入的服务；写出可恢复阶段记录，成功激活前保留原库与原文件。用户已经产生新写入后，不允许失败处理直接切回旧快照。SQLite 热备份沿用现有备份 API，不能直接拷贝正在写入的数据库主文件代替一致快照。

D03 的备份 secret 策略需单列 ADR：现有备份含配置密钥，不能在“脱敏”改动中默默破坏其恢复语义。默认导出、包含凭据的备份、未来凭据仓库迁移分别说明；若引入加密，使用成熟实现并明确密钥丢失后无法恢复的事实，不自创密码学方案。

D04 先确定同步语义再改字段：稳定排序必须绑定原始写入身份/逻辑版本，不能用接收方本机优先，也不能用转发快照的外层设备 ID 冒充原作者。对旧记录定义确定性兼容规则。云端快照的 exported_at 不是当前远端时钟，不能简单把陈旧快照平移到“现在”来修时差。优先建立不会倒退的逻辑版本与稳定 tie-break；需要扩展快照格式时保留旧快照读取能力，明确新旧客户端互通边界。

定向验收集合：同秒冲突、三端乱序、重复接收、时钟快慢/回拨、删除后恢复、部分上传失败、应用后上传失败、旧版快照、缺书后补书。先用纯合并函数与 Mock RemoteStore 证明，再决定是否需要额外真实协议集成。

**9. 性能改进从测量与执行闭环开始。**

P01 的第一份基准使用现有 bench-layout、bench-import、search-probe、pdf-probe 入口。记录 commit、toolchain、profile、机器、固定字体/度量、输入 hash、冷/热缓存、重复次数、p50/p95 与包体积。旧注释里的结果作为历史背景，不能替代现在的基线。先得到重复性，再设回归阈值；共享 CI 的噪声过大时只作趋势报告，不能直接设成必然波动的硬闸门。

M01/M02 分别处理局部缓存与全局预算：图片图集已有字节账，复用它；给章节源、DOM/布局、shaping/字体等补可解释的口径，标明 CPU/GPU、共享对象重复计数和估算误差。预算管理提供实际回收接口，并在压力上升时停止或缩小预取。当前可见内容允许占用保护，超预算时应报告，不能为满足数字制造每帧解码循环。

N01 将“用户请求取消”和“后台资源已回收”分开。下载/SSE 静默阻塞要能在明确的空闲读取期限内退出；不同调用有不同总预算，长书下载不能套短问答超时。request 小对象有明确最大响应，SSE 单事件、累计字节和事件数有上限。付费模型请求不得因断线盲目重发。网络错误日志保留分类、状态码与受控元数据，不回显密钥/正文。

F01 将 ParseBudget 的并发控制与恶意输入容量限制区分开。为 ZIP/RAR/7z/HTML/CSS/图片解码等入口分别确认真实上限，不因存在一个 Budget 类型就声称已防止资源耗尽。模糊测试作为隔离开发目标，普通应用构建不依赖 fuzz runtime；先选格式识别、href、CSS tokenizer、锚点映射等稳定输入口。

**10. UI 完善以 GPUI 的状态所有权和真实交互为主。**

A01/A02 不立即将每个页面拆成新 crate。先把 SizeClass、共享动效策略放在具备合适依赖方向的基础模块；ReadingPage 发出退出/导航等语义事件，shell 负责组装与导航；字体注册版本变化由独立服务或现有字体机制承载，services 不调用 reader feature 内部函数。

U01 优先覆盖阅读页、设置、书架、笔记四条主线：异步返回是否绑定 book_id/revision；关闭弹层是否恢复焦点；返回键是否只关闭最上层；删除按钮是否误触行跳转；换字号与窗口大小后位置是否稳定；长列表是否按可见范围工作。现有笔记页已经实现，不再把“新增笔记页”排为工作包。

UI 规范继续以 gpui-kit-design-guides 为准。应用按钮、表单、颜色、间距与焦点遵守 GPUI 组件规范；电子书作者 CSS、页内几何、图片像素与排版度量属于内容引擎，不纳入“禁止所有 px/颜色值”的粗暴规则。Web 动效技能只用于判断，不往原生 Rust 界面引入 GSAP、React 或 CSS transition。

桌面行为按 Windows/macOS/Linux 的适用范围分别验证。Android 只在用户明确要求查看时使用现有 scrcpy-android 虚拟显示；安装包交付不包含自动启动或操作手机。iOS/OHOS 在具备相应构建与行为证据前保持“入口存在/探索中”的状态，不与已发布平台混称成熟支持。

每条 skill 的建议结构：一个简短 SKILL.md、按需 references、agents/openai.yaml；只有重复且适合确定性执行的动作才加入 scripts。主文包含触发、任务边界、事实源、流程与退出条件；长期硬规则留在工程规范，skill 只引用 Rule ID，不复制整份规范。注释精简不额外新增第八条 skill，由 workflow 路由到当前领域技能，避免规则继续膨胀。通常加载工作流与当前领域一至两条，GPUI 改动另按仓库约定读两条基础规范。

安装流程遵守现有仓库约定：使用 skill-creator 编写并验证草稿，用 skills CLI 做项目级安装与 lock 同步；最终只有 `.agents/skills/` 一份权威内容，不建立第二份永久副本。首次处理本地自有 skill 时，在隔离临时目录验证当前 skills CLI 的 sourceType/local、重复目标与哈希行为，按实际 schema 登记；不得手工伪造 computedHash。若 CLI 自动生成 .claude/.qoder 的副本链接，只清理这次安装生成且已确认目标的链接，不递归删除用户其它工具文件。

自动发现保持默认启用；不擅自把 skills 改成只能显式调用，也不批量改第三方 frontmatter。任务不相关时由精确 description 避免误触发。

每条至少准备 3 类触发样例：应该触发、相邻但不应触发、缺少环境/事实时的正确处理。七条技能合计至少 21 个路由场景。具体验收包含：现有链接可读、命令确实存在、没有私自全量测试/手机操作/发布、能报告未测平台、不会因参考技能示例绕过 Folio 边界。人工路由评估与可自动化的 frontmatter/路径检查分别记录。
