# 性能基准记录（同步导出与书架投影）

日期：2026-11-23。状态：实验记录，不替代工程规范；先测量后阈值。

## 同步导出与库锁

目的是在改动 `collect_sync` 的锁范围之前，先量清两件事：导出本身随书数怎么长，以及导出期间另一条读路径要等多久。这样「第二只读连接」「导出批量化」才有判断依据，而不是凭感觉加并发。

条件：Windows x86_64、Intel64 Family 6 Model 183 Stepping 1（32 逻辑核）、Rust 1.99.0（b940084d7）、release 全局档位；单进程无并发负载，WAL、`synchronous=NORMAL`。代码基于 `3efea17` 加本轮未提交工作区（书架封面、笔记屏、封面补齐），不含已回退的书架 SQL 合并。机器、输入与提交都记下来，是因为这批数字只对本机这批输入成立。

入口为 `cargo +1.99.0 run --release -p folio-store --example sync-probe`，书数由 `FOLIO_PROBE_BOOKS` 覆盖（默认 200、1000、3000），每档都在临时目录新建库：

- 每本书一条 revision、一条高亮批注、一条书签、一个阅读位置，内容哈希互不相同（避免同内容多书目被并成一个同步桶）；
- 先空跑一次填充缓存，再跑 5 次 `collect_sync`，报 p50/p95；
- 锁等待：后台线程连续调用 `collect_sync` 三秒，主线程在这段时间里计时 30 次只为读一个偏好值的 `pref_number` 调用，报 p50/p95/max 与超过 1ms 的次数。

| 书数 | 导出 p50 | 导出 p95 | 等待 p50 | 等待 p95 | 等待 max | 超过 1ms |
| --- | --- | --- | --- | --- | --- | --- |
| 200 | 21.41 ms | 22.67 ms | 0.01 ms | 21.27 ms | 22.29 ms | 3/30 |
| 1000 | 112.42 ms | 112.91 ms | 0.00 ms | 0.01 ms | 60.01 ms | 1/30 |
| 3000 | 339.37 ms | 360.74 ms | 0.00 ms | 0.01 ms | 290.35 ms | 1/30 |

另跑过 100 本的冒烟档：导出 10.40 ms，等待 max 11.84 ms。

导出耗时随书数近似线性，约 0.11 ms/本。锁等待的中位数是 0，但 **max 与一整趟导出的耗时同量级**（3000 本约 290–360 ms）：`collect_sync` 进入即拿 `Mutex<Connection>` 并持有到函数结束，读者撞上就等整趟，而不是每本等一次。偶发的「超过 1ms」正是撞上导出窗口的那几次；中位数 0 说明大多数采样落在两次导出之间，不代表没有阻塞。

据此有两个判断：

- **第二只读连接不解决这条等待**。挡住读者的是进程内的 `Mutex<Connection>`，不是 SQLite 的连接数；换连接仍要经过同一把锁。
- **杠杆在让锁提前释放**。按页扫描、每页之间放锁，可把最坏等待从「一整趟导出」压到「一页的时间」；是否值得做，要等这条路径真的被周期调用（现在只有手动同步与局域网快照）再决定。

不据此设硬阈值：样本来自单机热缓存、WAL 且无真实磁盘抖动，Android 与真机未测；改动前后应当用同一入口、同一书数复跑对照。

## 书架投影的合并尝试

背景：`SHELF_COLUMNS` 每条书目带四个相关子查询（章节字数合计、无长度计数、按位置的已读字数与未知字数）。看起来可以合并成一次 `chapters` 分组，再用一次 join 取回，于是做了对照。

改法：把四格换成 `LEFT JOIN (SELECT book_id, SUM(char_len) … GROUP BY book_id)`，其余条件与排序不变。`cargo +1.99.0 test -p folio-store --lib shelf` 11 个用例全过，逐行数值与旧查询零差异，说明语义等价。

实测（合成库，本地 sqlite3/Python；不是真实书库）：

| 书数 / 章行数 | 旧：四个相关子查询 | 合并：一次分组 join |
| --- | --- | --- |
| 1000 / 200,000 | 17.7 ms（冷 25.4 ms） | 58–65 ms |
| 300 / 60,000 | 4 ms | 11.6 ms |

根因在查询计划：旧写法里「已读字数」与「未知字数」两格带 `c.idx < chapter`，能用上 `idx_chapters_book (book_id, idx)` 的第二列，计划是 `SEARCH c USING INDEX … (book_id=? AND idx<?)`；合并或改成 json 聚合后只剩 `book_id=?`，退化为整本扫，还要物化分组结果。数值虽等价，代价却约 3.3 倍。

结论：保留原来的四个相关子查询，不合并。这一项本来收益就小（1000 本约 18 ms），没有理由用三倍时间去换一次扫描的体面。真正贵的首帧成本在封面文件打开，不在这一格 SQL。
