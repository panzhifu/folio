# folio-render 编译档位基准

日期：2026-11-18。状态：实验记录，不替代工程规范。目标是核对排版从 core 拆出后继承 `z` 的实际影响。

条件：Windows x86_64、Intel Core i9-13900K、Rust 1.99.0（b940084d7）、根 Cargo.lock；release 全局 `z`、fat LTO、单 codegen unit、strip、panic=abort、core=`s`，仅通过 Cargo `--config` 改 folio-render 的 `z/s`。代码基于 `026c03c` 加本轮未提交工作区，包含 CSS 预算；两份二进制使用同一版格式/排版源码，不能当作干净提交基准。

入口为 `cargo +1.99.0 build --offline --locked --release -p folio-core --example bench-layout --config 'profile.release.package.folio-render.opt-level="z"'`，另一档将 `z` 改为 `s`。基准使用现有合成中/拉丁/混排语料、固定假度量（汉字1em、拉丁0.5em、空格0.25em）、600px内容宽；中文源1,452,490字节，内容键10226985284831276928。正文布局与级联在计时前准备，包含完整输出分配/销毁；每批20次，预热3批，再测30批。p50/p95是批平均的nearest-rank分位数，热缓存；块级缓存每次先填充旧版本再只计改一段，30个样本。

顺序为 z1→s1→z2→s2，四个进程串行，机器同时有定向测试/编译负载。耗时和峰值存在噪声，不据此设置硬性能闸门。

基准exe：z=983,040字节，s=1,003,520字节，增加20,480字节（约2.08%）；这不是最终应用包体积。SHA-256 分别为 `68eb4b1372f03c77f54596eb58fb91242d945728c44f40d126ebe734bfb95468`、`8a799c392e44a8ecc488f85f42e007abbbcb355bcd6a2b2021e28f539486abb5`。进程PeakWorkingSet每100ms采样：z两轮约63.1/62.6MiB，s约64.1/62.6MiB，未观察到可归因于档位的稳定差异，采样可能漏掉瞬间峰值。

完整排版两轮的p50均受益，块缓存路径亦改善；轻量路径变慢但绝对增量不足0.13ms，第二轮干扰明显。此次选择给 folio-render 单独设 `s`，保持其余包现有档位。结论只覆盖此机器、假度量及语料；真实字体/GPU、Android性能、最终包体积和导入/搜索热路径没有由此证明，后续在对应平台重测。
