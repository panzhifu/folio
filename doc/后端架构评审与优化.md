> 状态：**评审稿**（2026-11-09），只覆盖 `folio-core`（下文简称 core）。
> 行号会漂，认符号与职责，不认行号。

## 0. 结论（先看这一页）

**骨架是合理的，不需要重写。** core 与 app 的边界真实存在（`cargo tree -p folio-core`
里没有 gpui），模块按职责切得开，traits 选得对，Store 的并发纪律与测试密度都在。

**但有四条明确的债，按严重度排：**

1. **文档声称的「单向依赖」不成立**：`content → store / ingest`、`infra → 几乎所有模块`、
   `store ↔ net / sync` 都是真实存在的生产依赖边。环不影响编译，但让「改格式不牵动数据库」
   这条承诺失效。
2. **`Store` 是一个 121 个公开方法的门面**：文件拆得不错，接口没有收口，所有功能都从
   同一个类型进出。
3. **`content/format` 是 52k 行的单模块**：21 个 provider 加测试全在一个目录，review 与
   编译都集中在一个点。
4. **公开面没有收口、错误模型混层**：18 个 `pub mod`，`Error` 里同时有 `Sql` / `Json` /
   `Remote` / `Logging`，每个新格式都可能往同一个枚举里加变体。

**不建议现在拆成多个 crate。** 跨模块共享的 `Error`、`Config`、`Format` 太多，拆 crate
会先把依赖图弄碎，收益要等构建时间真的咬人才出现。**先做 §4 的 Stage 0–2，都是行为不变
的收口**；Stage 3 视 review 成本再定。

### 1.2 真实依赖图（生产代码，去掉 tests 与注释）

数字是 `crate::X::` 在源文件里出现的次数（粗略量级，不是精确引用数）：

```
backup  -> infra:7
content -> infra:42, layout:2, store:2, ingest:2
dict    -> infra:2
fonts   -> net:8, content:2, infra:1
group   -> store:2
infra   -> ingest:3, net:3, store:3, content:2, account:1
ingest  -> infra:29, content:18, store:8, net:6
layout  -> content:29, infra:15
net     -> infra:14, account:7, sync:4, ingest:3, position:1
reader  -> infra:4, layout:2, content:2
search  -> content:3, infra:1
store   -> content:45, infra:15, sync:5, position:3, group:2, net:1
sync    -> net:6, content:4, position:3, infra:2, store:2
text    -> content:5
```

`lib.rs:20-25` 写的方向是：

> `content` 可以依赖 `infra`，但不依赖 `store` / `ingest`；
> `ingest` 同时碰容器、文件系统与数据库；`infra` 谁都不依赖。

实际有三类偏离：

| 边 | 位置 | 为什么发生 | 后果 |
|---|---|---|---|
| `content → ingest` | `content/format/cover.rs` 的 `ContentHash` / `sha256_of_bytes` | 内容身份住在 `ingest::identity` | 一个格式模块为了算哈希依赖导入区 |
| `content → store` | `content/annotation.rs` 的 `Annotation` / `AnnotationStyle` | 领域类型定义在 `store::types` | 锚点解析、批注导出要认识数据库类型 |
| `infra → ingest / net / store / content` | `infra/services.rs` 注册 `WatchService` / `TransferServer` / `Store`；`infra/error.rs` 聚合 `net::remote::Error`；`infra/config.rs` 引用 `novel::rules::Edits` 与 `AnnotationStyle` | 组合根与错误聚合放在 infra，配置直接认识功能类型 | infra 不是叶子，改任何功能都可能牵动 infra |
| `store → net / sync` | `store/sync.rs` 用 `net::lansync::BookEntry`、`sync::DeleteRecord` | 同步协议 DTO 没有独立归属 | SQL 层认识网络协议形状 |
| `content ↔ layout` | `content/anchor.rs` / `hit.rs` 用 `layout::{Layout, LineFragment, Measure}`，`layout` 又用 `content` 的 DOM/CSS | 两个模块共同构成「排版」这一件事 | 环是真实的设计耦合，不是误写 |

**要区分「环」和「误放」**：`content ↔ layout` 更像一个被切成两半的子系统，硬拆环的
成本高于收益；`content → ingest/store` 与 `infra → 功能模块` 是明确的误放，可以低成本
消除。

### 1.3 六条主管线

#### A. 导入管线（`ingest/import`）

一条 `Source` trait 覆盖七种来源（选择文件 / 批量路径 / 整机扫描 / 文件夹监听 /
Wi-Fi 传书 / URL / 网盘），管线只有一份 `import_from`：

```text
1 来源分派      candidates()
2 写暂存        <书库>/.staging/.<名>.<序号>.part
3 算哈希 + 判定  sha256 → 三层格式判定（魔数 / 容器 / 裸文件）
4 判重          按完整哈希；命中先 stat 旧副本
──────────────── ingest 与 index 的分界 ────────────────
5 定名落地      暂存小屋 → 「建议名 + 判定出的扩展名」解析 → rename 成 <哈希前缀>.<格式>
6 解析          document::open → 章节表 / 资源表 / 目录 / 封面
7 落库          add_book + set_content_hash + save_document
```

关键设计：**判定排在落地之前**，副本名由内容决定；崩溃只留两类半成品（暂存区 `.part`、
改名成功但没落库的哈希名副本），各有清扫函数。锁纪律是「stage / hash / parse 不持锁，
只有 register 持锁」。

评价：这是 core 里最成熟的一条管线。抽象边界准确，失败语义分档清楚（拒收 / 坏容器 /
读不动 / DRM / 要口令），恢复路径有对应清扫。

#### B. 打开与解析（`content/document` + `content/format`）

```text
provider_for(path)
  → 先看容器骨架（ZIP 的 mimetype / container.xml+OPF / [Content_Types].xml / 图片全包 / HTML+图）
  → 退扩展名
→ DocumentProvider::index / read
→ Content::{Reflow(FlowDoc), Fixed(FixedDoc)}
→ BookDocument（唯一实现，格式差异已被 provider 抹平）
```

`BookDocument` 管三件与格式无关的事：懒开的容器句柄、`href → 实际条目` 的降级映射、
`Section` 族的整本正文 memo。取图片/字体字节时容器优先、provider 兜底。

评价：`Document` 接口与 provider 契约是这套架构里最值钱的部分之一。现在唯一的弱点是
provider 的**发现**仍以扩展名为主路径，内容嗅探只覆盖 ZIP；非 ZIP 的错名文件（例如
一个叫 `.bin` 的 PDF）打开时仍会走扩展名。

#### C. 排版与分页（`layout/`）

```text
Dom + StyledDom
  → collect（行内子树展平成文本 + piece 表，每个 piece 带自己的计算样式）
  → wrap_lines（UAX #14 断点；字体只提供单字前进量与整段度量）
  → children（块级顺序、外边距、text-indent、text-align）
  → 扁平 BlockBox / LineBox 表
  → fragments（按高度切页）
  → pages（页表、page_of_line）
```

坐标是布局空间绝对值，绘制层直接取。已知取舍写在模块头：不做父子外边距折叠、行内图片
不产出 run、分片丢上下 margin。这些是**明确记录**的取舍，不是遗漏。

评价：排版引擎与 `layout::Measure` 的倒置是正确形态：断行算法在 core，字体 shaping 在
app。不要为了「纯」把 `Measure` 搬进 core。

#### D. 阅读运行时（core 提供纯层，app 持有状态）

core 这边已经有：`reader::book`（拼接坐标、窗口范围、进度口径、链接解析）、
`reader::geometry` / `reader::turn`（页几何、翻页决策）、`cache::policy`（图集驱逐）。
app 侧持有 `Document`、`TextSystem`、`Entity`、`Window` 与渲染状态。

评价：边界切得对。剩下的 `toc_tree` / `chrome` / `turn_animation` 是纯逻辑但仍在 app
（见 §2.3 的「可继续下沉」），不是架构错误，是收益排序问题。

#### E. 存储与同步（`store/` + `sync` + `net/lansync`）

- `Store`：一个类型、一把 `Mutex<Connection>`、按主题拆 16 个文件；121 个公开方法；
  `schema` 是只增不改的迁移清单。
- `sync`：每台设备写自己的 `<device_id>.json`，按记录时间戳合并，删除走 tombstone。
- `net/lansync`：协议形状（发现、递清单、递快照），自己不起服务器，挂在 `transfer` 上。

评价：同步语义（每设备一份、最新写入胜、墓碑）是稳的。问题是 `store/sync.rs` 直接吃
`net::lansync::BookEntry` 与 `sync::DeleteRecord`，让 SQL 层认识协议 DTO。

#### F. 出网（`net/`）

```text
Request / Response（手写 Debug，URL 脱敏、头只留名字、体只报字节数）
  → Transport（request / download / upload）
    → UreqTransport（非 2xx 摊平成 Error）
    → Retrying<Transport>（429/408/5xx 全方法；连接错误只幂等方法）
  → RemoteStore / Drive / CloudProvider / Refresher / TokenStore
```

tokio 只在 `transfer` 里；core 其余公共签名不漏 `Future`。`AuthedStore` 做过期先续、
401 强刷重放一次；`share()` 默认套重试。

评价：网络层的接口分层（协议 / 传输 / 认证 / provider）是目前 core 里第二成熟的子系统。
`Drive` / `CloudProvider` 让「加一家网盘」从改 5 个文件降到 2 个。

#### G. 辅助域

| 域 | 入口 | 备注 |
|---|---|---|
| 字体 | `fonts` + `text` | 内置清单随二进制；下载走 `Transport`；加载管线在 `text::load`，gpui 接触点收在 `FontSink` |
| 词典 | `dict` | StarDict 整本读入内存，有硬上限 |
| 听书 | `speech` | 一根专职线程持 `tts::Tts`，命令/回调/事件两条管道 |
| 搜索 | `search` | 现读现扫，不建索引；有实测数据支撑 |
| 备份 | `backup` | `VACUUM INTO` + 配置原文 + 可选书文件；先写 `.part` 再改名 |
| 账号 | `account` | 128-bit 本机密钥 + HMAC 握手，无服务器权威 |
| 分组 | `group` | 纯函数；输入是 `store::ShelfItem`（一个可消除的边） |

### 1.5 已经做对、应当保留的事

1. **零 gpui 边界**：不是口头约定，`cargo tree` 可验证。
2. **tokio 只关在 `transfer`**：core 公共接口保持同步形状，app 自己决定放哪条线程。
3. **Store 锁纪律 + 编译期 `Send + Sync` 断言**：并发模型只有一处。
4. **端口 / 适配器用得对**：`Measure`、`FontSink`、`Transport`、`RemoteStore`、`Drive`、
   `CloudProvider`、`Refresher`、`TokenStore` 都是「接口在 core，实现在边界」。
5. **导入管线的失败分档**：拒收 / 坏容器 / 读不动 / DRM / 要口令，读者动作不同。
6. **格式契约门**：`content/format/contract.rs` 对 21 个 provider 统一验收。
7. **搜索不建索引有实测依据**：`search` 模块头有真书数据，不是拍脑袋。
8. **测试密度**：1,801 条；仅 `content::format` 就 695 条。

## 2. 问题清单

### 2.1 依赖方向没有被强制执行（P1）

症状与证据见 §1.2。具体四条：

- `content/format/cover.rs` → `ingest::identity`（只为哈希）。
- `content/annotation.rs` → `store::{Annotation, AnnotationStyle}`（领域类型放错层）。
- `infra/services.rs` → `ingest` / `net` / `store`；`infra/error.rs` → `net::remote::Error`；
  `infra/config.rs` → `novel::rules::Edits` / `AnnotationStyle`。
- `store/sync.rs` → `net::lansync::BookEntry` / `sync::DeleteRecord`。

影响：不是运行时 bug，是**认知成本**。下一个人照 `lib.rs` 的注释去改，会以为
`content` 不能碰 `store`，结果一编译发现能碰，然后不知道该信哪一条。

### 2.2 `Store` 的接口宽度（P1）

- 一个类型，121 个 `pub fn`：`books.rs` 36、`stats.rs` 18、`reading.rs` 10、
  `collections.rs` 9、`annotations.rs` 9……
- 文件拆分降低了「一个文件太大」，没有降低「一个类型知道太多」。
- 测试要为一个功能准备整个 `Store`，夹具会越来越像「模拟整个数据库」。

影响：新增一个领域的成本不是写逻辑，是往同一个类型上再挂几个方法；review 时也很难
看出哪些方法是同一子域。

### 2.3 还有纯逻辑留在 app（P2，不是错误）

按「0 gpui、有测试价值」两条，至少这些还可以搬，但这次**不建议一起做**：

| 模块 | 行数 | 依赖 | 判断 |
|---|---:|---|---|
| `toc_tree.rs` | 781 | 只依赖 `TocEntry` | 最干净，随时可搬 |
| `chrome.rs` | 796 | core 的 `PageMode` / `Appearance` | 可搬，与 toc_tree 相邻 |
| `turn_animation/*` | ~3,000 | 彼此 + `PageMode`，gpui 只在注释里 | 可搬，但改动面大 |

它们留在 app 不影响 core 的合理性；这是「还能再收一点」而不是「架构有问题」。

### 2.4 公开面与错误模型（P2）

- `lib.rs` 18 个 `pub mod`，app 可以碰到任何内部类型；core 没有「公共 API」这个概念。
- 一个 crate 级 `Error`（17 个顶层变体）同时装 `Sql` / `Json` / `Io` / `Remote` /
  `Logging` / 格式错误 / 导入拒绝。好处是调用方只认一个类型；坏处是每加一个外部依赖
  都可能往同一个枚举里加变体，且 `infra::error` 必须认识 `net`。

### 2.5 `infra/config.rs` 的体量与类型外溢（P2）

- 3,574 行，18 个配置节。节本身是强类型的，这点好。
- 但它直接引用 `novel::rules::Edits` 与 `store::AnnotationStyle`，把 infra 和两个功能
  模块绑在一起。
- 文件大本身不是罪，真正的成本是**任何配置改动都在同一个文件里 review**。

### 2.6 `content/format` 的集中度（P2）

- 52,124 行、21 个 provider，全部在一个模块目录。
- `contract.rs` 降低了「各自为政」的风险，但没有降低「一次改动要编译/审查整个格式层」。
- 拆 crate 的代价大于收益；拆子模块（`format::providers::epub` 等）是低风险选项。

**2026-11-09 更新：这一条已落地，结论反过来了。** 格式解析独立成 `crates/folio-format`
（54,333 行 / 68 个 `.rs`）：21 个 provider、容器/判定、DOM、CSS、scan、TextMap、
CharClass 与量具；`content/document` 门面与 `validate` 留在 core。当时说的「Error /
Config / Format 共享太多」是按源码里的 `crate::X::` 文字次数数的，把 doc comment 也
算进去了；按生产代码重数，format 向外只要 dom / css / scan / TextMap / CharClass /
metrics / paths / ImageScale / Rgba8 / cover 的 `ContentHash`，共 11 项，真正要设计的
只有 Error 与两三个小类型。拆完 core 126,291 → 72,289 行，707 + 1071 条测试全绿；
**编译时间不降**（满编 core 17.9 s，拆完两段串行），**评审面也没变小**（52k 只是换了
个 crate 名）—— 买到的是「格式层不拉 sqlite / 网络 / 语音」与编译器强制的方向。

### 2.7 文档漂移（P2）

`lib.rs` 的依赖说明与 §4.8 那一类「注释写着旧实现」的问题同源。现在 `lib.rs` 的三句话
里有两句已经不成立（`content` 不依赖 `store/ingest`、`infra` 谁都不依赖）。这比代码
问题更容易误导人。

### 2.8 没有架构门（P2）

没有 CI 检查「模块 A 不许依赖模块 B」。Rust 生态里可以用 `cargo-modules` 生成依赖图，
或者写一个小的仓库测试（解析 `use crate::...`）把几条禁令钉住。现在依赖方向靠人记，
必然漂移。

## 3. 优化原则

1. **先行为不变的地基，再结构**：能靠移动文件/类型解决的，不改逻辑。
2. **一次一刀、独立可发布**：每一刀都能单独跑测试、单独回滚。
3. **每刀带门**：新增的边界要有测试或 CI 检查，否则下一轮又会漂回去。
4. **不为架构而架构**：拆 crate、拆 trait 只有在「构建时间 / 多人协作 / 多端复用」
   真的痛时才做；当前只有一个 app 消费 core，很多抽象可以先不做。

## 4. 优化方案

### Stage 0：把话说对，把门立起来（小刀，零行为风险）

**做什么**

1. 修 `lib.rs` 的依赖说明：写成「实际依赖图 + 已知例外」，或者按 Stage 1 改完再写成
   真正的单向。
2. 新增一个仓库测试 `crates/folio-core/src/architecture.rs`（或 `tests/architecture.rs`）：
   - 解析 `src/**/*.rs` 的 `use crate::X` 与 `crate::X::`；
   - 钉住三条禁令：`content` 不许 `use crate::store` / `crate::ingest`；`infra` 不许
     `use crate::{store, ingest, net, content, layout}`；`store` 不许 `use crate::net`。
   - 允许白名单（例如 `infra/services.rs` 是组合根，Stage 1 会挪走）。
3. 在 CI 里跑这条测试（它和普通 `cargo test -p folio-core` 同一条命令，不需要新工具）。

**验收**

- `cargo test -p folio-core --lib architecture` 绿；
- 故意在 `content` 里加一句 `use crate::store::Store;` 能当场翻红。

**为什么先做这个**

没有门，Stage 1 改完三个月后又会长回去。这条成本最低，收益最长。

### Stage 1：拆掉三条误放的边（中小刀，行为不变）

#### 1.1 内容哈希下沉：`ingest::identity` → `infra::identity`（或 `infra::hash`）

- 移动 `ContentHash`、`sha256_of_bytes`、`HASH_ALGO` 与相关测试。
- 保留 `ingest::identity` 作为 `pub use`，避免一次改太多调用点；下一轮再删别名。
- 调用点：`content/format/cover.rs`、`net/{translate,ai}`、`store`、`backup`、`ingest` 内部。

**收益**：`content → ingest`、`net → ingest`（哈希那部分）消失。

**验收**：`content::format::cover` 的封面测试、`net::translate` / `net::ai` 的假传输测试、
`store` 的内容哈希测试全绿；`architecture` 门里 `content` 的 ingest 白名单删掉。

#### 1.2 批注领域类型归位：`store::types::Annotation` → `content::annotation`

- `Annotation` / `AnnotationStyle` 是「批注是什么」，不是「批注怎么存」。
- 移动后 `store` 反向依赖 `content`（已经成立 45 处），`content → store` 消失。
- 需要同步改 `store::types` 的 re-export 与 UI 的导入路径（可用 `pub use` 过渡）。

**验收**：批注 CRUD、锚点 relocate、批注导出三组测试；`content` 不许 `use crate::store`。

#### 1.3 组合根出 infra：`infra/services.rs` → crate 根 `services.rs`

- `services` 持有 `WatchService` / `TransferServer` / `Store` 的注册与生命周期，是
  **组合根**；组合根依赖所有模块是正常的，infra 依赖所有模块不是。
- 同时把 `infra/error.rs` 的 `Remote(#[from] net::remote::Error)` 改成：
  - 方案 A（推荐，改动小）：保留变体，但用 `#[from]` 的手写 `From` 放在 `services` /
    边界模块里，`infra::error` 不再 `use crate::net`；
  - 方案 B：拆 `CoreError` 与 `NetError`，在边界处包一层。工作量大，先不做。

**收益**：`infra` 变成真正的叶子（除 `config` 对功能类型的引用，见 1.4）；后续加功能
不会牵动 infra。

#### 1.4 配置只认识配置类型（可与 1.3 合并）

- 把 `novel::rules::Edits` 的引用从 `infra::config` 挪成 `novel` 模块自己的
  `NovelConfig::edits() -> Edits` 适配；`AnnotationStyle` 已经随 1.2 归位。
- 这一步不拆 `config.rs` 文件，只切断它对功能模块的类型依赖。

**Stage 1 完成后的目标图**

```
infra ← 所有模块
content ← layout / store / reader / search / text
store ← sync / ingest / group / services
net ← ingest / sync / services
services ← 所有（组合根）
```

`content ↔ layout` 仍然存在，这是有意的：它们是同一个排版子系统的两半。

### Stage 2：收 Store 与同步 DTO（中刀，行为不变）

#### 2.1 `Store` 分子域门面

不拆类型、不拆锁，先拆**接口**：

```rust
impl Store {
    pub fn books(&self) -> Books<'_>;
    pub fn annotations(&self) -> Annotations<'_>;
    pub fn stats(&self) -> Stats<'_>;
    ...
}
```

- 每个子门面只暴露本域方法；现有 `pub fn` 先保留，内部转发到子门面，分两轮迁移调用点。
- `notes` / `stats` 已经是独立文件，优先做这两个，收益最明显。
- 目标：`Store` 本体的 `pub fn` 从 121 降到 ~30（打开/备份/迁移/事务），其余按域下沉。

**验收**：现有 store 测试不改断言；UI 调用点逐步改成 `store.books().shelf(...)` 一类；
`grep -c "pub fn" store/mod.rs` 作为度量。

#### 2.2 同步 DTO 归位

- `net::lansync::BookEntry` 移到 `sync`（它是同步协议的数据形状，不是网络实现的私有物）。
- `store/sync.rs` 改吃 `sync::{BookEntry, DeleteRecord}`，不再 `use crate::net`。
- `net::lansync` 反向依赖 `sync`（已经成立），方向变成 `net → sync ← store`。

**验收**：局域网同步的假传输测试、`store::sync` 的合并测试全绿；architecture 门里
`store` 不许 `use crate::net` 生效。

### Stage 3：format 与公开面（按需，不建议现在动）

#### 3.1 `content/format` 拆子模块（不是拆 crate）

- 目标形态：`format::providers::{epub, pdf, mobi, ...}`，共享件留在 `format::{sniff, css,
  zip, charset, thumb, contract}`。
- 先只做目录移动与 `pub use` 过渡，不改任何 provider 逻辑。
- 触发条件：单次改格式层的 review 超过 ~1,500 行，或增量编译明显变慢。没有这两个信号
  就不做。

#### 3.2 公开面收口

- 把 `pub mod` 降成 `pub(crate)`，只保留 `lib.rs` 顶部的 `pub use` 作为 API。
- 触发条件：出现第二个消费 core 的 crate（例如未来的 CLI / 服务端），或 app 开始
  依赖 core 的内部实现导致重构困难。当前只有一个 app，收益有限。

#### 3.3 错误模型（可选）

- 如果 Stage 1 让 `infra::error` 不再依赖 `net`，可以先维持单枚举；只有当错误变体超过
  ~25 个或需要跨 crate 复用时，再拆 `StoreError` / `NetError` / `FormatError`。
- 现在拆的收益不抵改动面。

### Stage 4：什么情况下才拆 crate

满足任意两条再考虑：

1. core 的增量编译成为日常瓶颈（例如改 app 一行要等 core 几分钟）；
2. 出现第二个消费 core 的二进制/服务，且它只需要其中一两个模块；
3. 格式 provider 需要独立发版或独立测试矩阵；
4. 团队规模让「所有人改同一个 crate」产生协作冲突。

拆分顺序建议：`folio-format`（provider + sniff + css/zip）→ `folio-store` →
`folio-net`；`infra` 最后拆或不拆。**不要先拆 `infra`**，它现在承载了太多跨模块类型。

## 5. 决策点（请确认）

下面每条都给了推荐项；你只需要改不同意的。

- [ ] **D1. 先做 Stage 0（文档对齐 + 架构门）？**
  推荐：是。半天内完成，防止后续改动漂回去。
- [ ] **D2. Stage 1 的哈希下沉目标放 `infra::identity` 还是 `infra::hash`？**
  推荐：`infra::identity`（保留 `ContentHash` 这个名字，语义更明确）。
- [ ] **D3. `infra/services.rs` 是否挪到 crate 根 `services.rs`？**
  推荐：是。组合根不应该住在 infra。
- [ ] **D4. `Store` 是否分子域门面？**
  推荐：是，但只先做 `notes` / `stats` / `annotations` 三个域，验证调用点迁移成本。
- [ ] **D5. `Error` 是否拆？**
  推荐：现在不拆。先做 Stage 1.3 的 `Remote` 解耦，观察变体增长再说。
- [ ] **D6. `content/format` 是否现在拆子模块？**
  推荐：不拆。等 review 行数或编译时间出现信号。
- [ ] **D7. 是否现在就继续下沉 app 的 `toc_tree` / `chrome` / `turn_animation`？**
  推荐：不与本次架构优化混在一起；它们是 P8 之后的独立小刀，先不动。
- [ ] **D8. 是否接受「`content ↔ layout` 环保留」？**
  推荐：接受，并在文档里明确写成「一个排版子系统的两半」，不再宣称严格单向。

## 8. 这份文档没做的事

- 没有给每个函数级的迁移顺序（Stage 1 的 1.1–1.4 已经是文件级，函数级在动手时按编译错误推）。

  实施时按调用点决定。
