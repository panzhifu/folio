# 平板档设计稿（Medium 竖屏 + Expanded 横屏）

> 屏清单与数字表在 [`generate.py`](generate.py) 的文件头注释里；这份 README 说**为什么是
> 这两块画布**，以及平板上哪些屏真的与手机不同。

## 两块画布，不是一块

应用自己就把平板定义成两档，不是一块「平板屏」：

- `shell/navigation/mod.rs:98-104` 按**窗口宽度**分档 —— `<600` Compact、`600..840` Medium、
  `≥840` Expanded；
- `platform/android.rs:151` 那句注释是原话：「平板与折叠屏（最小边 ≥ 600dp）放开方向：
  跟随读者的旋转设定……**平板横过来的宽度本来就该走进 `SizeClass` 的 Medium / Expanded
  两档**」。手机在 Java 那一头保持竖屏锁。

所以平板档必须出两个朝向：竖屏落在 Medium、横屏落在 Expanded，而这两档的**导航形状本身就
不同**（rail 与 sidebar 两宽）。只出一张等于把平板读成「变宽的手机」。

## 设备

**小米平板 5：2560×1600 物理、系统报 320dpi（density 2.0）⇒ 逻辑 800 × 1280 dp。**

（点名到具体一台而不是写「那一族」：小米平板 6 是 2880×1800，同样 2.0 倍下竖屏宽 900dp
—— 那已经越过 840 落进 **Expanded** 了。要一台「竖屏 Medium、横屏 Expanded」的设备，
2560×1600 这一档才对得上。）

选它有三条理由：

1. 最小边 800dp ≥ 600dp —— 按应用自己那条判据，这是一台平板，不是放大版手机；
2. 竖屏宽 800 落进 Medium、横屏宽 1280 落进 Expanded，**一台设备正好覆盖两档**，
   两块画布之间没有第二个变量（DPI、字体基准、安全区都不动）；
3. density 2.0 是整数倍，逻辑像素与物理像素对得整齐，量出来的数好核。

| 朝向 | 逻辑画布 | 真机 PNG | `SizeClass` | 导航 |
| --- | --- | --- | --- | --- |
| 竖屏 | 800 × 1280 | 1600 × 2560 | Medium | 侧栏 rail |
| 横屏 | 1280 × 800 | 2560 × 1600 | Expanded | 侧栏 sidebar |

手机那一档（384 × 853，魅族 20）在 [`../`](../README.md)，两档共用
[`../_kit.py`](../_kit.py) 那一份尺：换画布走 `set_canvas(w, h, px_w, px_h)`，
它改的是 `_kit` 的模块全局，所以 `push_row` 那一类在调用时才解析 `W` / `RIGHT`，
一把尺跟着画布走。**平板脚本一律 `import _kit as k` 而不是 `from _kit import *`** ——
后者在导入那一刻就把值复制走了，`set_canvas` 对它无效。

## 平板上真的与手机不同的几处

- **导航从底栏换成侧栏**，且两档宽度不同（rail 48 / sidebar 260）。手机那条 56 高的底栏
  在平板上整条不存在。**选中那一格只换底色与前景色加 `font_medium`** —— 没有左标记条，
  文字也不另变色（`sidebar/menu.rs:316-320`），与手机底栏同一条「换页提示只有一处」。
- **设置换成一整个另一形的渲染器**：手机是钻入式分组列表（`settings/view/compact.rs`），
  两栏那边是侧栏 + 正文（`settings/view/desktop.rs`）。这一屏手机稿从没画过。
- **书架一行几本按宽度算**：Medium 四列、Expanded 五列（`grid.rs:79` 那条
  `floor((avail+8)/176)`），不是手机恒定的三列。
- **阅读页默认长出双页**：`spread_fits` 的门槛是栏宽 ≥ 200（`chrome.rs:56,157-159`），
  800 与 1280 两档分别得到 364 与 604 —— **都过槛，所以两档默认都是双页**。手机那一档
  栏宽只有 156，永远单页。
- **目录从底部弹层变成左抽屉**（320 宽、`left 12 / top 56 / bottom 12`），顶栏右侧也多出
  一颗目录开关 —— 那颗是 `wide` 才长出来的（`reading_page.rs:677-678`）。
- **扫描 / 建组 / 链接导入那三块是居中浮层**，不是手机那三个底部弹层
  （`shelf/view/mod.rs:1374-1398` 按 `size.is_compact()` 分两条路）。
- **钻入「组」那一页时侧栏整条不画、不留空位**（`shell/mod.rs:1037-1039` 的 `nav_gone`），
  而阅读层是 `absolute inset_0` 盖住侧栏且 `reserve.width = 0` —— 所以**正文按整窗宽算版心**，
  不是按内容列宽。

## 量到的几条，值得单独说

1. **两栏设置在 Android 平板上根本不成立。** 那道门是
   `host::supports_overlay_controls(cx)`（`shell/mod.rs:478-488`），桌面宿主 `true`
   （`host/desktop.rs:22-24`）、Android 宿主 `false`（`host/mobile.rs:27-31`，理由是那端
   浮层点不住，而「设置项点不动等于设置没有」）。所以**真机平板上「我的」画的仍是手机那份
   `CompactSettings`**，只是被撑到 752 / 1020 宽 —— 一张 44 高、整行宽的手机列表躺在平板上。
   `03-` 画的就是这个现状，`04-` `05-` 那两张两栏形态是「桌面宿主把窗口拉到平板宽度」那一台。
   **这不是画图的取舍，是应用现在真实的行为**，要不要让平板也吃两栏是一个待决的问题。
2. **统计在平板上反而不滚了**：手机那一档 53 列 × pitch 11 = 580 塞不进 332，只能横向滚；
   Medium 的可用宽 700 让 cell 长到 10、Expanded 让列夹在 720 居中，两档网格都小于可用宽
   ⇒ **都不横向滚**。一档之隔，行为反过来。
3. **横屏关掉双页会铺到 72 字一行**：`max_measure` 默认 0 是「不夹」的哨兵值
   （`config.rs:623`），1280 宽下版心 1232，单栏一行 72 个中日文字 —— 远超可读的行长。
   双页默认开着所以平时看不见，但读者手动切回单页就会撞上。设置里「版面 → 最大行长」
   那一格是唯一的上报入口。
4. **「浅深」那一组念两遍**：`appearance.rs` 里 `mode_group` 的组标题就是
   `field.appearance_mode`（现译「浅深」），而那一组唯一的项标题也是它。两栏形态下它同时
   是卡上方的组标题与卡里那一项的标题。旁支 `237621b8` 在关于页撞见过同一件事并撤掉了
   那边的节头 —— 但那条只在手机那一档生效，两栏这边组标题不能撤（它同时是侧栏子项）。

## 与手机稿共用的那一份尺

`_kit.py` 里所有几何都是**调用时**解析的模块全局，换画布走
`set_canvas(w, h, px_w, px_h)`；`scrim` 那一处的 `y1` 默认值原本在定义期就冻成了手机的
853，已改成函数体现问。手机那些脚本是 `from _kit import *`，值在导入时就被复制走了 ——
这正是想要的：平板脚本调 `set_canvas` 不会把手机稿带跑，重出后设置那 11 张仍逐字节一致。
**平板脚本一律 `import _kit as k` 并现问 `k.`**，不许 `import *`。
