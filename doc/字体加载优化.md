# 优化字体加载

> 一句话：把内嵌字体从 UI 线程上开书那一段搬走 —— **一趟容器走查同时取回样式与字体字节，
> 注册挪进单线程排版作业、在度量之前完成**。动手前先修「别名缓存拿容器路径当身份」这个
> 会让两本书互相认错字体的缺陷，并且先补计时再搬东西。

触发这份计划的一次核对（2026-10-27）：《哈利·波特全集》是手上唯一带内嵌字体的书，
它把「取字体」这一趟的重量暴露了出来。

## 一、目标与非目标

目标三条，按优先级：

1. 开书时 UI 线程不再为字体读字节 —— 那一趟的重量级实测接近「读完整本书正文」；
2. 同一进程里两本书的内嵌字体不许互相认错（这是正确性，不是性能）；
3. 这一段从此有计时器，收益与代价都有数。

非目标：不做字体磁盘常驻、不做全书预注册、不在作业里并行注册；不动
`folio-core` 不依赖 gpui 这条硬边界（取字节归 core，注册归 app）。理由见第五节。

## 二、现状（事实与实测）

开书这一段全在 UI 线程上串着做完整套字体：

1. `crates/folio-app/src/ui/features/reader/model/book.rs:148` 现取样式表 `doc.stylesheet()`；
2. `book.rs:159` `BookFonts::for_document(doc, &css, cx)`，里面依次做三件事：
   - 自己再解析一遍 CSS 拿 `@font-face`（`book_fonts.rs:118`），而 `book.rs:161` 的
     `author_rules(&css)` 又解析一遍 —— **同一份样式表在开书这一段解析了两遍**；
   - `doc.fonts(&wanted)` 取字节（`book_fonts.rs:134`）；
   - 逐份 `texts.add_fonts(...)`，每份前后各调一次 `all_font_names()` 求名字增量
     （`book_fonts.rs:144-155`）。

容器被重开、清单被重走：`crates/folio-core/src/content/format/epub.rs` 的 `font_bytes`
自己 `Zip::open` + 读 `META-INF/container.xml` + 读 OPF 并 `parse_opf`（HP 的 OPF 有 75 KB），
与 `stylesheet()` 那一趟各走各的。

实测（HP，python 的 zip 口径 —— 只用来定重量级，不代表 Rust 的实际毫秒）：

| 动作 | 字节 | 耗时 |
|---|---|---|
| 解开两份内嵌字体 | 7,993,764 B | ≈ 105 ms |
| 读完全部 301 章 XHTML | 8,581,162 B | ≈ 127 ms |
| 容器打开 + `container.xml` + OPF 一趟 | 75 KB | ≈ 5 ms |

**只为两章标题服务的一趟字体读取，重量级 ≈ 整本书正文一趟。**
两份字体是 `OEBPS/Fonts/dieyu.ttf` 3,485,272 B（内部名 汉仪蝶语体简）与
`qingkong.ttf` 4,508,492 B（汉仪晴空体简）；书里点名要它们的元素是 1,009 个 `<h2>`
章标题与 161 个 `<p class="script">`。

**没量到的**：`add_fonts` 本身多少毫秒、`all_font_names()` 一趟多少毫秒 —— 这段现在没有
计时器，而刀 3 的取舍要看这个数。所以第一刀是补计时，不是搬东西。

## 三、必须先修的正确性缺陷（比性能要紧）

进程级别名缓存是 `HashMap<String, Vec<String>>`，**键就是裸 href**
（`book_fonts.rs` 里的 `registered()` / `cached_names(href)`）。

同一条容器路径在两本不同的书里装着不同的字节，这在真实语料里是常态而非边角：HP 声明的
8 个「书里没有那个文件」的家族用的正是多看导出模板名 —— `Fonts/zw.ttf`、`fs.ttf`、
`kt.ttf`、`ht.ttf`、`h1/h2/h3.ttf`，整个多看语料都长这样。后果：同一进程里先开 A 再开 B，
B 的 `Fonts/kt.ttf` 命中 A 留下的键 → **跳过 `add_fonts`**，并把 A 的内部家族名登记到
B 的声明名下 → B 的正文静默用 A 的字体排，而 B 自己那份字节永远没进设备。

这与导入管线那次「暂存目录用给人看的名字，同名即撞、副本装着别人的字节」是同一类错，
那次的结论是**身份要用内容，不是路径**。现成的内容身份已经在中央目录里：
`content/format/zip.rs:171-186` 的 `range_of` 已经读回 `comp_len / raw_len / crc`，
**一次解压都不要**。

顺带第二条：字节是**先全部读完**才在循环里查缓存的，所以「同一本书重开」那 105 ms 每次付。
把「查身份」提到「取字节」之前，重开时这一趟根本不该发生。

## 四、计划：四刀

顺序是「先拿到数 → 再修身份 → 再合并走查 → 最后换线程」。每一刀都要中间可编译、
能独立验，所以各自成一笔提交。

### 刀 0：给开书这一段补计时（必须，先做）

沿用已有的 `crates/folio-app/src/ui/features/reader/model/perf.rs:306` 那个 `Timer`
（只在 `logging.level = "debug"` 出声，`info` 下每帧只多几次 `Instant::now`），
在 `Book::new` 那一段分四段记：

- `walk` —— 取样式表那一趟（含重开容器与解析 OPF）；
- `font_bytes` —— `doc.fonts(&wanted)`；
- `font_register` —— 逐份 `add_fonts` 加两次 `all_font_names`；
- `rules` —— CSS 解析，看那第二遍解析到底花多少。

**验收**：真机开 HP 那本，日志里四个数都在；`logging.level = info` 时一个都不出。
没有这一刀，后面每一刀的收益都是猜的。

### 刀 1：别名缓存的键换成内容身份（必须，独立成一笔）

- `content::format::FontBytes` 增加身份两格（`crc32` 与 `raw_len`），由 `epub.rs` 的
  `font_bytes` 从 `range_of` 那份现成元数据填 —— 现在它只取字节；
- `book_fonts.rs` 的缓存键从 `href` 改成身份（`(crc32, raw_len)` 够用；要更稳就用
  `sha2` 的前 8 字节，与封面/缩略图那套「文件名是内容哈希」同口径）；
- 查询顺序倒过来：先按身份查，命中就不再要字节。

**验收门（把修复关掉必须是红的）**：两份合成 EPUB，各自带**同路径不同字节**的字体、
注册出的内部家族名不同；先开 A 再开 B，断言 B 拿到的内部家族名来自 B 自己那份，
而不是 A 的。`book_fonts.rs` 的测试模块注释已写明「`for_document` 那一条要真容器与
真文本系统，归到集成那一档」—— 这条门就落在集成那一档，不在单元测试里假装测到。

### 刀 2：样式与字体合并成一趟容器走查

在 core 侧加一个入口，一次开容器把这本书开书要用的作者资料一起取回：

```
AuthorAssets { css: String, rules: Arc<RuleSet>, faces: Vec<FontFaceRule>, bytes: Vec<FontBytes> }
```

一趟之内做完：`Zip::open` → `container.xml` → 读 OPF 并**只解析一次** → 读那几份样式表
拼成 `css` → `RuleSet::parse` **一次** → 从 `font_faces` 折出 `wanted` 的容器绝对路径
（`base_dir` 就在这趟里）→ 按身份查缓存 → 只对没命中的那些读字节（含 WOFF 解回 sfnt）。

`Book::new` 那边变成：拿 `AuthorAssets`，`for_document` 只负责注册那一段（刀 3 之后再搬走），
`author_rules(&css)` 那次重复解析删掉。硬边界不动：**`folio-core` 不依赖 gpui**，
所以这一趟做到「取字节 + 解析」为止。

**验收**：`css-gap` 与 `font-probe` 两台量具的输出在改动前后**逐字节相同**（尤其 HP 那
10 个 `@font-face` 家族、取回的两份字节、以及样式表那 `21596 字节`），再加一条
「OPF 只被解析一次」的计数断言（`tracing` 或一个 `#[cfg(test)]` 计数器）。

### 刀 3：把注册搬进排版作业，在度量之前完成（看刀 0 的数再拍）

为什么这样成立、而且不产生可见重排：

- 排版队列是 `TaskManager::new(1)`（`chapter_layout.rs:438`）—— **单线程串行**，
  所以「这本书的第一趟作业负责注册、后面的趟次命中缓存」天然有次序，不需要再加锁；
- 作业本来就持有 App 级文本系统：`typeset_job` 里 `GpuiMeasure::new(input.texts, …)`
  （`chapter_layout.rs:491`）在 worker 上做度量；而 gpui 侧 `add_fonts` 是 `&self`
  （`gpui-pre-wgpu/src/cosmic_text_system.rs:143`，里面是 `self.0.write()` 一把写锁），
  从作业线程调合法；
- **绘制拿不到比排版结果更早的东西**：首屏那张纸是作业交回来的排版产物，同趟作业已经把
  别名表建好并随结果带回 UI → 屏上永远不会出现「先按读者字体排完、字体落地再重排」那一下。
  这是这条走法比「另起一趟后台任务」干净的地方；
- UI 线程上开书剩下的就只有 `document::open` 那一趟索引 + `BookImages::new` + 建锚章
  `Document`。字体读字节那 105 ms 整个离开 UI 线程。

要一起改的三处，全是次序问题：

1. `Book` 的 `faces` 字段先以 `BookFonts::empty()` 起（降级路现成：「空表 = 与没有这个
   功能时逐字节同一条路径」），作业回来时升级；
2. `TypesetInput` 多带一份字体身份清单与字节（从刀 2 的 `AuthorAssets` 来），
   `Typeset` 多带一份 `Arc<BookFonts>` 回 UI；
3. `session.rs:780` 那句 `self.font_cache.reset(cx.text_system().all_font_names())`
   现在紧跟在 `Book::new` 之后 —— 注册挪走之后必须挪到「作业落地那一刻」，否则缓存按旧表建，
   旧 `FontKey` 会命中上一本书解析出的 `Font`（那条评论自己写明了这条因果）。

**风险，动手前先认下来**：注册从「任何排版开始之前」变成「会话中途（第一趟作业里）」。
这条时间线现在也有 —— `session.rs:771` 的注释写着「`Book::new` 可能刚把书里的内嵌字体
注册进设备，字体表要重读一份」，沿用它不是新发明；但**字形/整形缓存在字体表变宽之后
是否留着旧条目**只有真机看得出来（`gpui-text-caches` 记过字形 tile 无人删）。
所以这一刀的验收必须包含真机开 HP、翻过一章，看章标题是不是汉仪蝶语体简 ——
按仓库技能走 scrcpy 虚拟显示截图，不占手机主屏。

`MAX_ONE = 8 MiB` 这道闸现在的行为是**整份丢掉**（`epub.rs`：单个超限只丢它自己）。
搬线程不改变它，但一旦字体成了 primary 正文用字，「10–20 MiB 的完整中文字体进不来」
就从无害变成有害 —— 见第六节第 2 条。

## 五、明确不做

- **不在导入那一趟把字体抽到磁盘常驻。** `FontBytes` 现在的定位是「容器不在时退回今天的
  样子」，抽出来就多一份要维护的落盘资产与一致性问题，而省下的只是重开时的读取 ——
  刀 1 的「先查身份再取字节」已经省掉大头。
- **不做「全书所有 `@font-face` 一次性预注册」。** 只注册作者候选链真点到的那些
  （`for_document` 按 `wanted` 取，口径是对的）。HP 那 8 个幽灵家族声明的是别的阅读器的
  机器路径，书里没带文件，取不到就是取不到，不必为它们加机制。
- **不在作业里并行注册。** 队列单线程已经把次序解决了，并行只是把同一把写锁的竞争搬上来。

## 六、要拍板的三件事

1. **正文那 40,951 个元素要的是宋体。** HP 全书最常出现的候选链是 `宋体, 明体, 明朝, serif`
   （51,590 个元素里的 79%），而 `measure.rs` 的同类映射找的是 Noto Serif CJK SC /
   Source Han Serif SC / Songti SC / SimSun 那五个名字 —— 两台机器都没装，APK 随包只有
   `NotoColorEmoji.ttf`。这不是加载问题，是设备上没字。要么随包带一本子集化的中文衬线
   （包体要重新量，release 包现在约 48 MB），要么接受「这本的正文用读者自己的字体排」。
   同族还有一条口径缺口：`gpui_font` 的同类映射只看候选链上**第一个**非泛族名，
   所以 `DK-FANGSONG, 仿宋, fangsong, sans-serif` 这条（3,075 个元素）因为首位是厂商前缀名
   而整条落空，能命中的「仿宋」排在第二位、根本没被看过。
2. **要不要上子集化。** 需求集已知：HP 要蝶语画 535 个不同字符、要晴空画 1,080 个
   （`font-probe` 的 `CHARSET` 行就是这份需求清单 —— 注意它**不是**字体自己的覆盖表，
   我一开始把它读反过一次）。实测两份 cmap 是 7,726 / 7,911 个码位、对需求覆盖 100%，
   也就是说**需要的只有约 7%**，切下来是几百 KB 量级，`MAX_ONE` 那道闸也不再是坎。
   代价要么引一个子集化依赖，要么自己在 `cmap + loca/glyf` 上动一刀。
   当前语料只有 1/3 本书带内嵌字体（另两本各 0 份），我倾向先不做，等刀 0 的数与
   「带大字体的书有多少本」的语料统计出来再说。
3. **四处过时的注释要一起改。** 「内嵌字体只用来**补缺字形**」已经不成立
   （`measure.rs:218-224` 现在让随书那份当 primary），但它还在四处充当决策依据：
   `content/format/epub.rs:100-105`（三道闸的理由，含那句「读者不会为了几百个生僻字预付 30 MB」）、
   `content/format/mod.rs:786-790`（「几个小文件、一次解压」—— HP 是 8 MB ≈ 整本正文一趟）、
   `examples/font-probe.rs:13-14`、`measure.rs` 里 `faces` 字段的注释。
   不改，下一次按它做判断还会往「无所谓，反正只补几个字」那一路偏。
   同一族里还有一条：`measure.rs:151` 引用的「同文件 424 行那段 HACK」不在那个文件里 ——
   `load_family` 是钉住的那份 fork 里 `src/ios/text_system.rs:227`，且那个「不带 `m` 就不加载」
   的门槛只在 iOS 那一路，folio 出货的安卓与桌面两侧都没有。

## 七、跑法备忘

```bash
# 这本书的作者样式与落地面（量具默认不带 HP，要把路径递进去）
cargo run -p folio-core --example css-gap -- tests/fixtures/local/hali-bote-quanji.epub
# 内嵌字体：声明 → 容器里真取回的字节 → 落在哪些元素（外加 CHARSET 需求清单）
cargo run -p folio-core --example font-probe -- tests/fixtures/local/hali-bote-quanji.epub
```

这台秤可信度的一次核对（同一轮做的）：`sup img` 241、`<table>` 5、`class="box"` 8、
`class="line"` 1 —— 从原始 HTML 独立数出来与 `css-gap` 报的元素数逐条相同。
HP 的样式落差里 91% 是 `duokan-text-indent` 噪声（写它的 17 条规则每条都带着逐值相同的
标准 `text-indent`），扣掉噪声这本真落差约 496 个元素、不到全书 0.96%。
