# 优化字体加载

> 一句话：把内嵌字体从 UI 线程上开书那一段搬走 —— **一趟容器走查同时取回样式与字体身份，
> 注册挪进单线程排版作业、在度量之前完成**。动手前先修「别名缓存拿容器路径当身份」这个
> 会让两本书互相认错字体的缺陷，并且先补计时再搬东西。
>
> **2026-10-27 复核**：旧稿有六处事实错误（`m` 门槛位置、cmap/覆盖率、计时、元素计数、
> 幽灵家族清单、`add_fonts` 行号），本版已按代码与复测数据更正；更正清单见 §〇。
> 行号是审计时的；本轮改了 `book_fonts.rs`/`book.rs` 之后会漂，认符号与现象，不认行号。
>
> **2026-10-31 更新**：EPUB 的 CSS 与字体身份现在共用**同一个已打开的容器** ——
> `stylesheet()` 在 UI 打开共享 `Container`，worker 的 `Document::font_refs_in` 复用它、
> 只补一遍 OPF（本机 debug 中位：`font_refs_in` 13.6 ms，旧 `font_refs` 自己开 ZIP
> 18.5 ms）；MOBI 也补了 `font_refs/read_font`（原始 FONT 记录的 CRC + 长度做身份，
> 不解压）。同一天还落了**内嵌字体子集化**（skera + 导入扫描收的整本字符集 +
> 每书唯一家族名），HP 两份字体注册字节 7.99 MB → 4.34 MB；子集化不减少读全量字体
> 的那一趟，省的是注册/字体表内存，代价是每次开书多几毫秒 CPU。见 §九。

## 一、目标与非目标

目标三条，按优先级：

1. 开书时 UI 线程不再为字体读字节 —— 那一趟的重量级与「读完这本书全部正文」同一档；
2. 同一进程里两本书的内嵌字体不许互相认错（这是正确性，不是性能）；
3. 这一段从此有计时器，收益与代价都有数。

非目标：

- 不做字体磁盘常驻；
- 不做全书预注册；
- 不在作业里并行注册；
- 不动 `folio-core` 不依赖 gpui 这条硬边界（取字节/身份归 core，注册归 app）。

## 二、现状（事实与实测）

### 2.1 开书这一段（2026-10-27 已改：字体进首趟作业）

现在分两段，UI 线程不再读字体字节：

**UI 线程（`Book::new`）**

1. `crates/folio-app/src/ui/features/reader/model/book.rs` 的 `doc.stylesheet()`。
   - 走 `BookDocument::stylesheet`：优先用 `flow.css`；否则用**共享的 `Container`** 读
     `flow.css_hrefs`。这一趟**不解析 OPF**，只读 CSS 并做 `url()` 绝对化。
2. `BookFonts::empty()` + `FontLoadJob::new(doc, css)`：只拿引用，不取字节、不注册。
3. `author_rules(&css)` 解析一次作者层规则（`chapter_layout` 的 `RuleSet::parse`）。
4. 建锚章 `Document`，`faces` 为空，挂上 `FontLoadJob`。

**排版 worker（首趟 `typeset_job`）**

1. `FontLoadJob::run(&TextSystem)` → `BookFonts::for_request`：
   - **先 `doc.font_refs_in(&wanted)`**：复用 UI 读 CSS 已打开的共享 `Container`，
     只补 `container.xml`/OPF 与中央目录区间（EPUB；本机 debug 中位 13.6 ms）。
     provider 没有这条路时退回 `doc.font_refs`（自己开 ZIP，18.5 ms），再没有
     元数据入口才退回 `doc.fonts` 一次读全；MOBI 的 `font_refs` 对原始 FONT 记录
     现算 CRC + 长度，**不解压**；
   - 逐份按身份查进程缓存：命中就**不读字节**；未命中才 `doc.read_font` 读这一份
     （EPUB 走 `epub.rs` 的 `read_font`，WOFF 在这里解回 sfnt）；
   - 逐份 `texts.add_fonts(...)`，每份前后各调一次 `all_font_names()` 求名字增量。
2. 作业把 `input.key.fonts_rev` 换成注册后的版本，`Typeset.fonts` 带回新表；
3. `Document::apply_typeset` 换 faces、清掉 `font_job`、重建 `measure`；
4. 下一帧 `Book::sync_fonts` 把新表灌给邻居章；`ReaderSession` 看到
   `fonts_revision` 变了就 reset `FontCache`。

旧同步入口 `BookFonts::for_document` / `for_texts` 现在只剩测试与 `font_load_bench` 用
（`#[cfg(test)]`），生产不再走它。`Book::new` 的 `author_rules` 与 worker 的
`FontRequest` 用的是**同一份** `RuleSet`，worker 不再解析第二遍 CSS。

容器账已经合并（2026-10-31）：`stylesheet()` 用共享 `Container` 读 CSS，worker 的
`font_refs_in` 复用**同一个** `Container` 补 OPF，不再另开一个 ZIP。第一次打开仍要
解析一遍 OPF（本机 debug 中位 13.6 ms），第二次打开（别名缓存命中、`bytes_read=0`）
剩下的也是它。`font_refs`（自己开容器）只剩 provider 单测、没有 `BookDocument` 的
调用方与「共享容器这条路给不出」的降级用。

### 2.2 字节数与计时（2026-10-27 复测）

HP 的字节数是硬的（Python `zipfile`，`tests/fixtures/local/hali-bote-quanji.epub`）：

| 动作 | 字节 | 本次复测（页缓存热，5–7 次中位数） |
|---|---:|---:|
| 解开两份内嵌字体（Python 解压） | 7,993,764 B | 47 ms |
| 读完全部 301 章 XHTML（Python 解压） | 8,581,162 B | 36 ms |
| `ZipFile` + `container.xml` + OPF | 75,241 B | 1.8–2.9 ms（三次新进程） |
| Rust `doc.fonts(&wanted)`（debug） | 7,993,764 B | **138–145 ms**（135–182） |
| Rust `doc.font_refs(&wanted)`（debug，只读中央目录，自己开 ZIP） | 2 份 | 17.6 ms（17.1–19.6） |
| Rust `doc.font_refs_in(&wanted)`（debug，复用已开容器） | 2 份 | **13.6 ms**（2026-10-31 复测；旧 `font_refs` 18.5 ms） |
| Rust `document::open`（debug，含索引） | — | 540 ms（这一趟不是字体） |
| Rust `doc.stylesheet()` / `RuleSet::parse`（debug） | 21,596 B | 1.44 / 3.49 ms |
| `Book::new`（UI，debug，不含字体字节） | — | **7.0–7.2 ms** |
| 首趟 `typeset_job`（worker，含字体 + 排版，debug） | — | 139–143 ms |

旧稿的 105 / 127 / 5 ms 在本机没有复现。**计时只作趋势**；后续验收用字节数、容器打开次数、
`doc.fonts` 调用次数、`add_fonts` 次数，不用墙钟。Rust 那一行是 `font-load-bench`（debug）
量的 `doc.fonts`，比 Python 纯解压多出 OPF 解析、中央目录与上限检查；它现在在排版 worker
上跑，不再压 UI 线程。`font_refs` / `font_refs_in` 那两行是同一个 `font-load-bench` 量的元数据入口（后者复用
`stylesheet()` 已打开的共享容器，少一次 `Zip::open`）；`BookFonts::for_request` 第二次
打开 HP 时 `bytes_read = 0`、`cache_hits = 2`（`the_second_open_reads_no_font_bytes`），
只付这 13.6 ms 的 OPF 扫描。

`BookFonts::for_document`（同步路径，`TestAppContext`）第一轮约 143 ms（parse 2.4 /
bytes 126 / register 1.6），第二轮起降到约 16.8 ms 且 `bytes=0` —— 身份缓存已命中。
但测试文本系统对 `add_fonts` 是空操作（`families=0`、首轮 `empty_diff=2`），
**1.6 ms 不能当真实注册耗时**；真实注册要在有窗口的桌面或真机上量。

结论：只为 1,009 / 161 个元素服务的一趟字体读取，**重量级与整本书正文同一档**（这次甚至
略高于全部 XHTML）。这不是「几个小文件」的量级。

### 2.3 字体与落点（font-probe 实测）

两份字体：

- `OEBPS/Fonts/dieyu.ttf` —— 3,485,272 B（内部名 汉仪蝶语体简）；
- `OEBPS/Fonts/qingkong.ttf` —— 4,508,492 B（汉仪晴空体简）。

font-probe 的落点口径是「候选链里点名这些家族的**元素**数」，不是标签计数：

- `hanyi`：1,009 个元素，样例标签 `<h2>`；
- `qingkong`：161 个元素，样例标签 `<p>`。

原始 HTML 独立数：`<h2>` 211 个，`class=script` 约 159 个（`p.class=script` 154 个）。
所以旧稿「1,009 个 `<h2>` / 161 个 `p.script`」是错的；它把「元素数」写成了「标签数」。

全书最常出现的 `font-family` 候选链（font-probe，共 51,590 个元素）：

- 40,951 个：`宋体, 明体, 明朝, serif`（79%）；
- 3,075 个：`DK-FANGSONG, 仿宋, fangsong, sans-serif`；
- 2,332 个：`DK-KAITI, 楷体, kt, sans-serif`；
- 2,000 个：未点名/继承；
- 1,009 个：`hanyi, 汉仪, sans-serif`；
- 563 个：`zw`。

CSS 里声明了、书里没有对应文件的 8 个家族：
`darkage`、`fs`、`h1`、`h2`、`h3`、`ht`、`kt`、`zw`。其中 7 个是多看模板名
（`zw/fs/kt/ht/h1/h2/h3`），`darkage` 是另一套；旧稿漏了 `darkage`。

### 2.4 cmap 与需求覆盖（fontTools 4.67.0 复测）

- 蝶语：best cmap **7,615** 个码位；union 7,726（多出来的是平台 1 的 226 项 symbol 表）。
  需求 535 个字符，覆盖 534，**缺 `¾` (U+00BE)**；比例 535 / 7,615 = **7.0%**。
- 晴空：best cmap **7,911**；需求 1,080，覆盖 1,080；比例 1,080 / 7,911 = **13.7%**。
- 合计需求 1,615 / 15,526 = **10.4%**，不是「约 7%」。旧稿的「100% 覆盖」只对晴空成立。

`font-probe` 的 `CHARSET` 行是**需求清单**，不是字体自己的覆盖表；这一点旧稿写对了。
子集化必须把 `¾` 补进去，或接受它回退到读者字体。

### 2.5 还没量到的

- `add_fonts` 本身多少毫秒、`all_font_names()` 一趟多少毫秒。`TestAppContext` 的
  `add_fonts` 是空操作（`families=0`、`empty_diff=2`），只能拿它打印占位；真实注册必须在
  有窗口的桌面或真机上量。
- `document::open` 的 540 ms（debug，含索引）不是字体那一笔，但仍占开书 UI 线程；
  它归索引那一轮，不在本文的四刀里。
- 真实设备上「字体表变宽后，已有 shaping/字形缓存是否继续命中」。

这三项要由刀 0 的计时与刀 3 的真机冒烟回答。

## 三、必须先修的正确性缺陷

进程级别名缓存是 `HashMap<String, Vec<String>>`，**键就是裸 href**
（`book_fonts.rs` 的 `registered()` / `cached_names(href)`，注释还写着「href 当键足够」）。

同一条容器路径在两本不同的书里装着不同的字节，在多本使用同一导出模板的真实书库里会
发生，而不是理论边角：HP 声明的 8 个「书里没有那个文件」的家族用的正是多看导出模板名
（`Fonts/zw.ttf`、`fs.ttf`、`kt.ttf`、`ht.ttf`、`h1/h2/h3.ttf`），多本多看导出的书会
重复这些路径。后果：同一进程里先开 A 再开 B，B 的 `Fonts/kt.ttf` 命中 A 留下的键 →
**跳过 `add_fonts`**，并把 A 的内部家族名登记到 B 的声明名下 → B 的正文静默用 A 的字体排，
而 B 自己那份字节永远没进设备。

本机三本语料里只有 HP 带内嵌字体（蛇结 0 条 `@font-face`；斗战狂潮 1 个幽灵 `easypub`、
0 份字节），所以「两本书同路径不同字节」目前是结构推演，不是本机实测；必须用两份合成
EPUB 做门。

这与导入管线那次「暂存目录用给人看的名字，同名即撞、副本装着别人的字节」是同一类错，
那次的结论是**身份要用内容，不是路径**。现成的内容身份已经在中央目录里：
`content/format/zip.rs:171-186` 的 `range_of` 已经读回 `comp_len / raw_len / crc`，
**一次解压都不要**。

顺带第二条：字节是**先全部读完**才在循环里查缓存的（`doc.fonts(&wanted)` 在
`cached_names` 之前），所以「同一本书重开」那 138 ms（debug；Python 纯解压 47 ms）每次付。
把「查身份」提到「取字节」之前，重开时这一趟根本不该发生 —— 但这需要**元数据入口**，
不是只加两个字段，见刀 2。

## 四、计划：四刀

顺序是「先拿到数 → 再修身份 → 再合并走查 → 最后换线程」。每一刀都要中间可编译、
能独立验，所以各自成一笔提交。

### 刀 0：给开书这一段补计时（必须，先做）

`perf.rs:306` 的 `Timer` 只是 `Instant` 包装，**不会自己出声**；帧级计时由 `perf::add`
加 `log_paint` 负责，`reset()` 在每帧 render 开头清账。`Book::new` 不在 render 帧里，
直接塞 `perf::add` 会被下一帧清掉。这里应另起一条明确的
`tracing::debug!(target: "folio_app::perf", ...)`（用
`tracing::enabled!(target: "folio_app::perf", tracing::Level::DEBUG)` 做闸门），
或加一个只给开书用的 `OpenBookTiming` 结构。

在代码里落成两条日志，因为字体那段已经不在 `Book::new` 里了：

- `book_open`（UI，`perf::log_book_open`）：`walk`、`rules`、`font_deferred=true`；
- `font_load`（worker，`FontLoadJob::run` 调 `perf::log_font_load`）：
  `font_parse`（生产为 0，CSS 已在 UI 的 `rules` 里解析）、`font_bytes`、`font_register`、
  `faces`、`font_cache_hits`、`font_bytes_read`、`font_failures`、`font_empty_diffs`。

**验收**：真机开 HP，两条日志都出现；`logging.level = info` 时一条都不出。
没有这一刀，后面每一刀的收益都是猜的。

### 刀 1：别名缓存的键换成内容身份（必须，独立成一笔）

- `content::format::FontBytes` 增加身份两格（`crc32` 与 `raw_len`）。
  EPUB 的 `font_bytes` 用 `zip.range_at(&name)`（内部就是 `range_of`）拿现成元数据，
  **先拿身份再读字节**；MOBI 没有 ZIP 区间，只能对已读出的字节算 CRC32/长度。
  两个构造点（`epub.rs:235`、`mobi.rs:226`）都要补。
- `book_fonts.rs` 的缓存键从 `href` 改成身份 `(crc32, raw_len)`。这是**快筛**，
  不是密码学身份：两个不同文件在 32 位 CRC 上碰撞的概率极低，但并非零。要「绝不认错」，
  命中后再读一次字节核对，或把缓存键换成完整内容哈希；**不要在 UI 线程对 8 MB 字体
  做 SHA-256**，那一步应放在刀 2/刀 3 的作业里。
- **真正「命中就不再要字节」不在这一刀**：`doc.fonts(&wanted)` 的签名就是「给 href
  列表、返回带字节的列表」，没有元数据入口。刀 1 只修正确性；刀 2 再拆 `FontRef`
  （href + media_type + 身份）与 `read_font(ref)`，让 app 先查缓存、再只读未命中的字节。
  否则会把 API 拆两次。

**验收门（把修复关掉必须是红的）**：两份合成 EPUB，各自带**同路径不同字节**的字体、
注册出的内部家族名不同；先开 A 再开 B，断言 B 拿到的内部家族名来自 B 自己那份，
而不是 A 的。`book_fonts.rs` 的测试模块注释已写明「`for_document` 那一条要真容器与
真文本系统，归到集成那一档」—— 这条门就落在集成那一档，不在单元测试里假装测到。

### 刀 2：元数据入口 + 命中不读字节 —— 落地（2026-10-27；容器合并 2026-10-31）

**已落地**

- core：`FontRef { href, media_type, raw_len, crc32 }`；`Document::font_refs` / `read_font`
  都是 `Option`，默认 `None`。EPUB 覆盖：`font_refs` 只读中央目录（不解压），
  `read_font` 只读一份（WOFF 解回 sfnt）。
- **共享容器入口**（2026-10-31）：`Container::entry_meta` 只读中央目录的两格；
  `DocumentProvider::font_refs_in` / `Document::font_refs_in` 用**已经打开的**
  `Container` 读身份（默认 `None`）。`BookDocument::font_refs_in` 把
  `stylesheet()` 打开的那个容器交给 provider，EPUB 只补 `container.xml`/OPF。
- app：`FontRequest` 在 UI 的 `author_rules` 之后折一次（wanted / declared_of / faces），
  `FontLoadJob` 直接带它进 worker；worker **不再解析第二遍 CSS**。
- `BookFonts::for_request`：先 `doc.font_refs_in`（共享容器）→ 退回 `doc.font_refs`
  （自己开容器）→ 再退回 `doc.fonts` 一次读全；逐份按身份查进程缓存 → 只对未命中的
  `doc.read_font` → 注册。命中时 `bytes_read = 0`。
- **MOBI**（2026-10-31）：`font_refs` 只读 FONT 记录的原始字节、对原始记录现算
  `crc32 + raw_len`，不解压；`read_font` 才去混淆 + zlib 解压。命中别名缓存时不再
  解一遍字体（仍要读原始记录算身份；MOBI 没有中央目录，这是最便宜的内容身份）。
- 门：`the_second_open_reads_no_font_bytes`（HP，ignored）实测第一次 `bytes_read=2`、
  第二次 `=0`、`cache_hits=2`；`one_open_container_serves_css_and_font_identity`
  钉住「CSS + 字体身份只开一次容器」（并对照旧路两次）。
- `the_worker_prefers_the_shared_container_over_opening_its_own` 钉住 worker 的顺序：
  `font_refs_in` 有值就绝不调 `font_refs`。

**合并后剩下的账**

`stylesheet()` 在 UI 打开共享 `Container`，worker 的 `font_refs_in` 复用它只补 OPF；
第一次打开仍要解析一遍 OPF（本机 debug 中位 13.6 ms），第二次打开（`bytes_read=0`）
剩下的也是它。**没有**把这一趟搬到 `Book::new`：实测 `font_refs_in` 本身就是 13.6 ms，
搬到 UI 会把「字体不压 UI 线程」这一条换回去；要再省只能把 OPF 的字体身份在导入时
存进库里（`FlowDoc` 加一列），或给 OPF/清单做进程级缓存 —— 都还没做。

**验收**：`css-gap` 与 `font-probe` 输出在改动前后逐字节相同；`the_second_open_reads_no_font_bytes`
的第二趟 `bytes_read=0`；`one_open_container_serves_css_and_font_identity` 的容器打开
次数为 1。

### 刀 3：把注册搬进排版作业 —— 已落地（2026-10-27）

实际落点：

- `BookFonts::for_request(&TextSystem, doc, request)` 是 worker 入口；`for_document` /
  `for_texts` 只剩 `#[cfg(test)]` 的同步路径（测试与 `font_load_bench`）。
- `FontLoadJob` 持有 `Arc<dyn Document>` + `FontRequest` + 一次结果缓存；随 `TypesetInput`
  进单线程排版队列。第一趟 `typeset_job` 在 `GpuiMeasure::new` 之前 `job.run(&input.texts)`，
  把 `input.key.fonts_rev` 换成注册后的版本，`Typeset.fonts = Some(fonts)` 回 UI。
- `Book::new` 不再取 `cx`/不读字体：先 `BookFonts::empty()` + `FontLoadJob`，锚章
  `Document` 挂 job；`Book::sync_fonts` 在 `ensure_window_spans` / `set_anchor` 前把锚章
  的新表接过来，邻居章继续共享同一个 `FontLoadJob`（它的结果缓存保证只读一次）。
- `Document::apply_typeset` 收到 `Typeset.fonts` 后换 faces、清 job、重建 `measure`；
  `poll_typeset` 返回“真正生效的键”（`fonts_rev` 可能变），`ensure_viewport` 用它继续
  比对/派活，避免拿旧键再排一趟。
- `ReaderSession` 新增 `book_fonts_rev`：render 开头发现锚章 `fonts_revision` 变了就
  `font_cache.reset(cx.text_system().all_font_names())`。这一步晚一帧落地；首帧的
  `FontKey` 已经是新表里的内部家族名，命中的是缓存里没有的键，不是旧 `Font`。

为什么成立（与旧稿一致）：

- 排版队列是 `TaskManager::new(1)`（`chapter_layout.rs` 的 `typeset_queue`）—— **单线程
  串行**，所以「第一趟作业负责注册、后面的趟次复用结果」天然有次序，不需要再加锁；
- 作业本来就持有 App 级文本系统：`GpuiMeasure::new(input.texts, …)` 在 worker 上做度量；
  gpui 侧 `add_fonts` 是 `&self`（`gpui-pre-wgpu/src/cosmic_text_system.rs:168`，内部
  `self.0.write().add_fonts(fonts)`），从作业线程调合法；
- **绘制拿不到比排版结果更早的东西**：首屏那张纸是作业交回来的排版产物，同趟作业已经把
  别名表建好并随结果带回 UI → 不会出现「先按读者字体排完、字体落地再重排」那一下；
- UI 线程上开书剩下的只有 `document::open` 那一趟索引 + `BookImages::new` + 建锚章
  `Document`；实测 `Book::new` **7.0–7.2 ms**（debug，HP），而首趟作业（字体 + 排版）
  **139–143 ms** 在 worker 上跑。

**风险与未结**：

- 注册时间线从「任何排版开始之前」变成「第一趟作业里」；真机要看章标题是不是汉仪蝶语体简
  （走 scrcpy 虚拟显示，不占手机主屏）。
- 字形/整形缓存在字体表变宽之后是否留旧条目，只有真机看得出来（`gpui-text-caches` 记过
  字形 tile 无人删）。
- **刀 2 的元数据/缓存已落，容器已合并（2026-10-31）**：首次打开仍付约 145 ms 读字节 +
  13.6 ms OPF（都在 worker，不压 UI）；第二次打开同一本只付 13.6 ms OPF，
  `bytes_read = 0`。`stylesheet()` 与 worker 的 `font_refs_in` 共用同一个容器，不再
  各开一次；OPF 仍解析一遍（要再省得把身份在导入时存进库里，或给清单做进程级缓存）。

`MAX_ONE = 8 MiB` 这道闸现在的行为是**整份丢掉**（`epub.rs:211`：单个超限只丢它自己）。
搬线程不改变它，但一旦字体成了 primary 正文用字，「10–20 MiB 的完整中文字体进不来」
就从无害变成有害 —— 见第六节第 2 条。

## 五、明确不做

- **不在导入那一趟把字体抽到磁盘常驻。** `FontBytes` 现在的定位是「容器不在时退回今天的
  样子」，抽出来就多一份要维护的落盘资产与一致性问题，而省下的只是重开时的读取 ——
  刀 2 的「先按身份查、命中不读字节」才会把这一笔省掉；刀 1 只修身份，不省读取。
- **不做「全书所有 `@font-face` 一次性预注册」。** 只注册作者候选链真点到的那些
  （`for_texts` 按 `wanted` 取，口径是对的）。HP 那 8 个幽灵家族声明的是别的阅读器的
  机器路径，书里没带文件，取不到就是取不到，不必为它们加机制。
- **不在作业里并行注册。** 队列单线程已经把次序解决了，并行只是把同一把写锁的竞争搬上来。
- **不把 `m` 门槛当成 iOS 问题。** 它是 `gpui-pre-wgpu`/Apple 两条文本系统共有的
  primary 过滤；纯中文、不带拉丁的随书字体会被它剔掉。要处理就改依赖或给字体补拉丁，
  不要按「只在 iOS」去绕。

## 六、要拍板的三件事

1. **正文那 40,951 个元素要的是宋体。** HP 全书最常出现的候选链是
   `宋体, 明体, 明朝, serif`（51,590 个元素里的 79%），而 `measure.rs` 的同类映射找的是
   `Noto Serif CJK SC` / `Source Han Serif SC` / `Noto Serif SC` / `Songti SC` / `SimSun`
   这五个名字；两台机器都没装，APK 随包只有 `NotoColorEmoji.ttf`。这不是加载问题，
   是设备上没字。要么随包带一本子集化的中文衬线（包体要重新量，release 包现在约 48 MB），
   要么接受「这本的正文用读者自己的字体排」。
   同族还有一条口径缺口：`gpui_font` 的「同类映射」只看候选链上**第一个**非泛族名，
   所以 `DK-FANGSONG, 仿宋, fangsong, sans-serif` 这条（3,075 个元素）在设备没装 `仿宋` 时
   整条落空；`仿宋` 排在第二位，`chosen` 那一步会检查它是否**已安装**，但没装时不会拿它
   去映射同类中文。旧稿写「根本没被看过」不准确：它被「已安装」那一遍看过，只是没进
   同类映射。
2. **要不要上子集化。** 需求集已知：HP 要蝶语画 535 个不同字符、要晴空画 1,080 个
   （`font-probe` 的 `CHARSET` 行就是这份需求清单 —— 注意它**不是**字体自己的覆盖表，
   我一开始把它读反过一次）。2026-10-27 用 fontTools 复测：蝶语 best cmap 7,615、
   覆盖 534/535（缺 `¾`）；晴空 7,911、覆盖 1,080/1,080；比例 7.0% / 13.7%，合计约
   10.4%，切下来是几百 KB 量级，`MAX_ONE` 那道闸也不再是坎。代价要么引一个子集化依赖，
   要么自己在 `cmap + loca/glyf` 上动一刀。当前语料只有 1/3 本书带内嵌字体（蛇结 0、
   斗战狂潮 0），我倾向先不做，等刀 0 的数与「带大字体的书有多少本」的语料统计出来再说。
3. **四处过时的注释要一起改。** 「内嵌字体只用来**补缺字形**」已经不成立
   （`measure.rs` 的 `gpui_font` 现在让随书那份当 primary），但它还在四处充当决策依据：
   - `epub.rs:100-107`（三道闸的理由，含那句「读者不会为了几百个生僻字预付 30 MB」）；
   - `content/format/mod.rs:788`（「几个小文件、一次解压」—— HP 是 8 MB ≈ 整本正文一趟）；
   - `examples/font-probe.rs:13-14`（「注册成功的名字只进 fallbacks，从不抢 primary」）；
   - `measure.rs` 里 `faces` 字段的注释（「只用来补缺字形」）。
   还有 `book_fonts.rs` 的「href 当键足够」——已随刀 1 改成内容身份。
   不改，下一次按它做判断还会往「无所谓，反正只补几个字」那一路偏。

## 九、内嵌字体子集化（2026-10-31）

**依赖选择**：引入 `skera 0.9.0`（Google fontations，MIT/Apache，纯 Rust，TTF/CFF/TTC，
保留 GSUB/GPOS 与竖排 metrics）。不自己写：`font-subset` 明确丢 GPOS/GSUB/kern；
`subsetter` 是 PDF 专用、会删 cmap；`allsorts` 的布局表不跟 GID 重映射走。自己剪
`glyf` 还要处理复合字形与 GSUB 闭包，等于重写 skera。

**字符集**：`content::scan::ChapterSummary.charset` 在导入扫描里顺手收（导入本来就把
每一章解出来数字数），EPUB 与 MOBI 都填；`FlowDoc.font_charset` → `books.font_charset`
（迁移 v28，`INDEX_VERSION` 13）。旧库 / 其它 provider 为空 → 整份字体。整本字符集是
**保守超集**：HP 实测 54.2–54.3%（7.99 MB → 4.34 MB）；按每个字体真正点到的字符切是
6.4% / 13.0%（3.49/4.51 MB → 224/587 KB），但那需要导入期全量层叠（font-probe 在
debug 下 13.4 s/HP），留作下一步。

**注册身份**：子集字体不是「同一份字体」—— 进程字体表是全局的，两个不同子集同名会
互相选错。因此子集切完先改名（家族 / 全名加 `#folio<tag>`，tag = 字体身份 + 字符集
hash），别名缓存键改成 `(FontId, subset_hash)`；整份字体仍用 `(FontId, 0)`。`#folio`
名字不进字体选择器 / host 兜底。子集/改名/字体解析失败、TTC，或子集不比原字体小，
一律退回整份。

**实测**（本机 debug，`TestAppContext`；skera 的 subset 本身 release 中位 6.3 ms/两份）：
`font_load` round 1 `subset_us≈225 ms`、`subset=7,993,764→4,335,588`；round 2 起
`subset_us=0`（别名缓存命中）。debug 下这一笔比原路径慢，release 的 skera 只要几毫秒；
真正的收益是注册进 `add_fonts` 的字节与字体表内存减半（4.34 MB vs 7.99 MB），**不是**
容器读取减半 —— 开书仍读全量字体。要省读取只有把子集字节存进库或导入期子集化，未做。

**门**：`the_index_collects_the_visible_book_charset`（导入收字符集）、
`hp_font_subset_is_renamed_and_smaller`（ignored，真书子集 + 改名）、
`subset_charset_keeps_ascii_and_hashes_stably`、store 往返（`font_charset` 列）。
fork 侧用 off-tree 探针验过：批量注册交回每个 source 的家族名、`font_has_glyph`
真查 cmap、无 `m` 脸能当 fallback 排出汉字。
