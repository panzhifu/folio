# 目录与组件：把「页面」和「组件」分开

**一句话**：现在的目录是**按文件的历史长度**长出来的，不是按**职责**切出来的 —— `widgets/` 里躺着
1467 行的模态弹层，`shared/` 里混着主题和服务，`shelf/view.rs` 一个文件同时是页面、工具栏、四张
浮层和卡片网格。这份计划先定四条依赖方向，再把每个纵切收成同一形状（`model` / `view` /
`components` / `overlay`），最后才把页面拆成组件。

> 可执行版（目标态完整目录树 + `mod.rs` 骨架 + 按批次的 `mv`/`sed` 脚本）在
> [`目录架构.md`](目录架构.md) —— 搬迁时照那份抄，不需要再判断一次。

> gpui-kit 的 Coding Guides 有一条正对着这件事：**按能力（capability）纵切，不要建全局的
> `views/` / `models/` / `modals/`**；它还定义了「app component = 重复出现的领域模式」这一层。
> 这份计划就是照那条走的 —— 只拆到「纵切内部四层 + 顶层一个 `components/`」，不建按渲染角色分的
> 全局目录。

## 一、判据：先定规则，再搬文件

搬文件之前先写死六条，之后每次「这个文件该放哪」都能直接查表：

| 区 | 只放什么 | 不许出现 |
|---|---|---|
| `ui/foundation/` | 主题、文案、错误约定、图片索引：**无业务、无 IO、无实体** | `Entity<T>`、`Service`、查库 |
| `ui/services/` | 应用级单例与后台管线句柄（配置、书库、导入队列、监听、传书） | 元素树、`AnyElement` |
| `ui/components/` | **跨 ≥2 个纵切**重复出现的领域模式（底部弹层、顶栏、搜索框、行/卡片/空状态） | 任何 `features::*` 的类型 |
| `ui/features/<cap>/` | 一个能力的 model + view + 自己的组件 + 浮层 | 兄弟纵切的内部类型 |
| `ui/shell/` | 外壳与导航：把页面摆进栈里 | feature 的业务判断 |
| `ui/host/`、`ui/platform/` | 平台适配。**全项目唯一允许 `cfg(mobile)` 的地方** | 界面逻辑 |

依赖方向（单向，不许成环）：

```
shell ──► features/<cap> ──► components ──► services ──► foundation
              │  (纵切内部)
              └──► model ◄── view ◄── components（纵切内）
host / platform：被上面所有人使用，自己不依赖任何人
```

纵切内部的四条子规则：

1. **`model/` 不建元素树**：可以有 `Context<Self>`（要 `notify`、要落库），但不返回 `AnyElement`、
   不写 `impl Render`、不摸 `Window` / `TextSystem`。
2. **`view/` 只组合**：读 `model` 的状态、拼 `components`；除了滚动条 / hover / 输入框内容这类
   **瞬时**状态，不持有业务状态。
3. **`components/` 不拿页面实体**：通过 builder + 回调（`on_*`）与页面说话。一个组件参数里出现
   `Entity<ReaderSession>`，它就还是页面的一部分。
4. **`overlay/` 只依赖同纵切的 `components` + `model`**：浮层是最容易长出跨纵切依赖的地方。

## 六、页面怎么写（「用组件构成页面」的落地）

一个页面文件里**只许**出现这三样东西：

```rust
impl Render for ReadingPage {
    fn render(&mut self, window: &mut Window, cx: &mut Context<Self>) -> impl IntoElement {
        div().size_full()
            .child(self.render_body(window, cx))                    // 区域
            .when(self.chrome.is_open(), |d| d.child(self.render_top_bar(cx)))
            .child(self.render_bottom_bar(cx))
    }
}
```

1. `render`：只做**排布**（哪个区域在哪、什么时候挂），不超过 30 行。
2. `render_<region>`：一个区域一个方法，**每个 ≤ 40 行**。
3. 超过 40 行、或者同一簇样式在本文件出现第二次 → 它就是一个组件，搬到 `components/`，
   参数用 builder（`.wide(bool)` `.title(impl Into<SharedString>)`），回调用 `on_*`。

三条自查（写进 PR 描述）：

- 页面文件里 `fn ... -> AnyElement` 的个数 ≤ 6。
- 页面文件里没有 `impl ReaderSession` / `impl ShelfView` 之外的 `impl`（页面不实现别的实体的方法）。
- `components/` 下的任何类型，`use` 里不出现 `features::<cap>::view`。

## 七、命名替换表（消 P8）

| 旧 | 新 | 理由 |
|---|---|---|
| `reader/document.rs` | `model/chapter_layout.rs` | 与 `core::content::document` 撞 |
| `reader/page.rs` | `view/reading_page.rs` | 「一屏」vs「一页」 |
| `reader/fixed.rs` | `model/fixed_book.rs` | 对齐类型名 |
| `widgets/` | `components/` | 「组件」是 gpui-kit 的词 |
| `shared/theme.rs` 等 | `foundation/` | 「地基」比「共用」有判据 |
| `shared/library.rs` 等 | `services/` | 「服务」有生命周期 |
| `modules/` | 摊进 `model/` | 那条分类线不成立 |

词汇按 gpui-kit 的约定表走：保留态模型 `…State`（`BottomSheetState` 已对）、语义通知 `…Event`
（`SearchBoxEvent` 已对）、构造 `new` / 语义构造器、fluent 属性用名词、`&mut self` 用 `set_`、
布尔读用 `is_`/`has_`、回调 `on_<intent>`、区域渲染 `render_<region>`。

## 九、测试放法统一（P7）

一条规矩：**测试跟被测代码同一个模块目录**。

- 常规：`mod.rs` 末尾内联 `#[cfg(test)] mod tests`（增量编译友好，现状里 `turn.rs` 那批就是）。
- 超长（> 800 行）：同级 `foo/tests/` 目录，一个主题一个文件（`scroll.rs` / `hit.rs` / `paint.rs`），
  由 `foo/tests/mod.rs` 用 `#[path]` 或 `mod x;` 收口。
- `folio-core/tests/`（crate 级集成测试）只放**跨模块公共缝**的用例，不放单文件细节。

## 十一、什么时候才拆 crate

Coding Guides 的建议是「大应用里一个能力一个 crate」。folio 现在只有
`folio-core` + `folio-app`，**这份计划不拆 crate**，理由是拆的前置条件还没到：

1. 缺一个 `folio-ui-foundation`（`foundation` + `services` + `components` 三层）—— 没有它，
   `folio-reader` 与 `folio-shelf` 会互相要 `shell` 里的 `NavPage`，成环。
2. `features/reader` 与 `ui/shared` 之间还没有稳定缝（`ConfigHolder` 是全局实体）。
3. 收益还没量：`cargo check` 现在改一个叶子文件只重编一个 crate。

触发条件（满足任一再谈）：纵切之间出现第二批跨缝 `use`；或者 `cargo check -p folio-app`
的时间成为日常等待的主项。

③ `settings/spec.rs` 是「两端共用的唯一数据源」—— 它其实同时被 `view` 与 `model` 读，
放进 `model/` 之后要不要把「页面顺序」那一格拆成 `view/order.rs`。

④ 提交 5 的力度：只替设置屏，还是连 `stats` 的外壳一起替（`stats` 有手绘图表，风险更高）。
