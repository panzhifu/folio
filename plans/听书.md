# 听书（合成朗读）后端

> 状态：**设计稿，未实现**。
>
> 主语是**合成朗读**，不是有声书：库里没有音频文件、没有音频时间点，只有「这一本这一章
> 的这一段字符，机器念出来了没有」。所以这条线的一切位置都是**内容坐标**（字符偏移），
> 与 `plans/Locator.md` 那一套同源，不需要也不该引入第二种坐标系。
>
> 后端选型钉在 [`tts`](https://crates.io/crates/tts) 0.26.3（`ndarilek/tts-rs`）。本文第二、
> 三节里的每条约束都是**读过源码或在机器上跑过命令**得出的，出处跟着写；没有实测过的
> 判断会明写「未实测」。

## 一、形状

一件事拆成四件，各自的归属不同：

| 事 | 住在哪儿 | 为什么在那儿 |
|---|---|---|
| 念什么（段的文本 + 段的字符区间） | `folio-core` | 段的定义是排版的事，与平台无关 |
| 怎么念（引擎、语速、音色） | `folio-core` 新模块 `speech` | 平台差异要有一处收口，界面不写 `cfg(mobile)` |
| 念到哪儿了（进度） | `positions` 表 | 与读的位置是**同一个东西**，见第六节 |
| 谁在念、什么时候停 | `folio-app` 的阅读会话 | 生命周期跟着那一屏走，不跟着进程走 |

## 二、`tts` 0.26.3 实测到的事实

**编译**：`cargo check` 过 x86_64-linux-gnu 与 aarch64-linux-android 两端（一个只依赖
`tts = "=0.26.3"` 的空白工程，2026-10-17）。Android 那一条要 `RUSTFLAGS=-C linker=$NDK/.../aarch64-linux-android26-clang`，
光给 `CC_*` 不够 —— 缺它时 `cc` 用宿主的 `/usr/bin/ld` 去链 aarch64 目标文件，报
`Relocations in generic ELF (EM: 183)`。

**API 面**（`src/lib.rs`）：只有 `speak(text, interrupt) -> Result<Option<UtteranceId>>` 与
`stop()`，加 `set_rate` / `set_pitch` / `set_volume` / `voices` / `is_speaking`，
和三条 `on_utterance_begin` / `_end` / `_stop`。**没有 `pause()` / `resume()`**，
也**没有词边界（word boundary）回调**。每个能力都先查 `Features` 那个结构体，
不支持就回 `Error::UnsupportedFeature`。

**两端的能力差**（`src/backends/*.rs` 里各自 `supported_features` 的返回值）：

| | Android | Linux（Speech Dispatcher） |
|---|---|---|
| `stop` / `rate` / `pitch` / `is_speaking` | ✓ | ✓ |
| `volume` | ✗ | ✓ |
| `voice`（列音色）/ `get_voice` | ✗ / ✗ | ✓ / ✗ |
| `utterance_callbacks` | ✓ | ✓ |
| 语速区间 | 0.1 – 10.0，常速 1.0 | （未读，取引擎报的数） |

两个坑：

1. **`Tts::min_volume()` / `max_volume()` 在 Android 上是 `todo!()`**。`set_volume` 有
   `Features` 拦在前面所以碰不到，但那四个 `min_*` / `max_*` 是**直接**转给后端的，
   没有闸门（`lib.rs:389-424`）。界面要给语速滑条标上下限，只能自己定数，不能问引擎。
2. **`voices()` 在 Android 上直接 `unimplemented!()`**，而 `Tts::voices()` 先查
   `Features.voice = false` 所以回 `Err` —— 走 `Result` 这条路是安全的。**不要**绕过
   `Tts` 去碰后端 trait。

## 三、Android 那三条硬约束

这三条决定了「接 `tts`」不是一行依赖的事，任何一条没做对都是**启动就没了**或者**按了没声音**。

**① `JNI_OnLoad` 会被塞进我们的 `.so`。** `tts` 的 Android 后端在 `android.rs:30` 定义了
`#[no_mangle] pub extern "system" fn JNI_OnLoad`，它 `find_class("rs/tts/Bridge").expect(...)`。
实测：一个只导出一个函数、依赖 `tts` 的 cdylib，`readelf --dyn-syms` 里
`JNI_OnLoad` 与五条 `Java_rs_tts_Bridge_*` 全在（`.so` 里 `android_main` 一个都没有）。
现在的 `libfolio_app.so` 里**没有** `JNI_OnLoad`（同一命令查过），所以加上 `tts` 之后它就是
唯一那一条 —— 而 `GpuiActivity` 明确调 `System.loadLibrary`（`GpuiActivity.java:55`，
注释写着「so that JNI can resolve our native methods」），于是**每次启动都会跑它**：
APK 里没有 `rs/tts/Bridge` 这个类，`expect` 就在加载期炸。

结论：接 `tts` 就必须同时随包一份 `rs/tts/Bridge.java`，并且它在 ProGuard/R8 下不能被剪掉
（上游那份带 `@androidx.annotation.Keep`）。

**② `onStop` 那条永远不会来。** `UtteranceProgressListener` 的抽象方法只有
`onStart(String)` / `onDone(String)` / `onError(String)`，`onStop(String, boolean)` 是
**非抽象的默认实现**（`javap` 打 android-34 的 `android.jar` 得到）。而上游那份
`Bridge.java` 声明的是 `public native void onStop(String, Boolean)` —— **装箱**的
`Boolean`，签名对不上，它是重载不是覆盖。所以框架调的是基类那个空实现，
`Java_rs_tts_Bridge_onStop` 一次也不会被叫到，`Tts::on_utterance_stop` 在 Android 上是死的。

这一条的后果写在第五节（`stop()` 之后没有任何回调，「停」只能自己记账）。

顺带：`onError(String)` 确实被覆盖、确实会来，而 `android.rs:141-164` 把它**映射成
`utterance_end`** —— 引擎报错与念完在回调层面长得一模一样。

**③ `Android::new()` 会阻塞最多 500 ms 并永久占住调用线程。** `android.rs:185`
`attach_current_thread_permanently()`，`:206-220` 一个 `thread::sleep(5ms)` 的轮询等
`onInit`。所以**句柄绝不能在界面线程上建**。

好消息：`ndk_context` 不用我们管。`android-activity` 0.6.1 在 `src/init.rs:285` 已经调了
`ndk_context::initialize_android_context(vm, app_global)`，而本仓库的入口正是它的
`android_main`（`platform/android.rs:17`）。上游 README 里那句「depend on `ndk-glue`」是过时的。

**还有一条不在 `tts` 里但在 Android 上**：`AndroidManifest.xml` 现在没有 `<queries>`
（查过：只有 VIBRATE / MANAGE_EXTERNAL_STORAGE 那几条与两个 intent-filter）。API 30+
要绑到系统 TTS 引擎，得声明

```xml
<queries>
  <intent><action android:name="android.intent.action.TTS_SERVICE"/></intent>
</queries>
```

否则 `TextToSpeech` 建得起来但 `onInit` 报服务不可用 —— 表现是「按了没声音」，最难查的那一类。

## 四、Linux 桌面的现实

`tts` 在 Linux 上不是直接对 espeak，而是对 **Speech Dispatcher**：
`Connection::open("tts","tts","tts", Mode::Threaded)`（`backends/speech_dispatcher.rs:24`）
—— 要一个**跑着的 `speechd`** 才连得上。本机实测：`libspeechd.so` 在（`/usr/lib`），
`speechd` 进程**没在跑**，`speech-dispatcher` / `spd-say` 两个可执行文件**都不在**。
也就是这台开发机上 `Tts::default()` 会回 `Err`。

所以桌面这一档必须按「拿不到引擎」设计，而不是按「一定有」设计：

- 建句柄失败 → 阅读页那一格**不摆**，而不是摆了按下去没反应、也不是弹一条错误。
  判据与「这台设备根本没有这一格」共用同一条（`host` 边界上那套
  「两端答案不同才上 trait」的规矩，见 `ui/host/mod.rs` 的模块文档）。
- 编译期还多一道：`speech-dispatcher-sys` 用 bindgen（`cargo check` 时它在建，
  拉进 `clang-sys` / `cexpr` / `regex`），所以 Linux 构建机要有 libclang 与 libspeechd 头。
  这条要进 `README.md` 那一段「Linux 需要 fontconfig、wayland、xkbcommon 的开发包」。

## 五、念什么、怎么停

**段，不是句。** 一段 = `Store` 交回的章节文本里一个**字符区间**，判据现成：
`content/hit.rs:148` 的 `paragraph_range(layout, dom, map, offset)` 给的就是
「拥有这一行的最深叶子块」那一段。取文本用 `TextMap::slice`（`content/anchor.rs:54` 起）。

为什么用段：句切分要么引一个分句器（中日文的句号规则又是一堆特例），要么用正则糊一个
（糊出来的东西在「1.5」和「他说。」上都会错）。而段的边界是排版已经算过一遍的事实。
代价是一长段可能被引擎自己截断 —— 引擎截断不影响我们的进度记账，因为**一段一条
utterance**，回调给的是「这一段完了」。

**一次一条，用 `QUEUE_FLUSH`。** `speak(text, interrupt=true)` 逐段推：念完一段的
`onDone` 里推下一段。不做预排（不把后三段 `QUEUE_ADD` 进去）—— 预排要处理「读者手动翻页
时那三段已经在引擎队列里」这件事，而 `stop()` 会把它们一起冲掉，正好把「往后退一段」也
变成一次 stop + speak。一次一条把这个分支消掉了。

**没有 `pause`，所以「停」和「暂停」是同一件事。** 都走 `stop()`。区别只在**要不要记住
当前段**：暂停 = `stop()` + 留在这一段；停止 = `stop()` + 位置落库。恢复 = 从头再念这一段
（不是从字中间）。这是 Android 那第②条的直接后果：`stop()` 之后**一个回调都不会来**
（`onStop` 是死的、`onDone` 只对念完的段落发），所以「停下来了」这件事只能由**我们自己
按下停止的那一刻**认定，不能等引擎确认。

`is_speaking()` 两端都有，可以拿来兜底刷新那一格图标，但别拿它当推进度的依据 ——
它在两段之间会短暂为假。

## 六、跟读与进度

**段边界精确，段内不精确。** Android 后端没有 `onRangeStart`（SDK 有这个方法，
`javap` 查得到，但 `Bridge.java` 没声明它，所以 `tts` 收不到）。要段内逐句高亮，
只有两条路：自己扩那份 Java Bridge（要动 `@no_mangle` 的符号名与 `CALLBACKS` 那张表 ——
即改 `tts` 或 fork 它），或者**按时钟估**。

估法：`on_utterance_begin` 到点记 `t0`，按「该段字符数 ÷ 当前语速下的字速」推当前位置，
用 `background_executor().timer` 逐帧刷。字速这个数**必须实测**，不许拍：中文与英文、
不同引擎、`set_rate` 的每一档都不一样。测不出来之前，段内不做高亮 —— 只做**整段**
点亮（念哪段亮哪段），那一条不需要任何估计。

**进度落在 `positions`，不新开一张表。** 听书的位置与读书的位置是同一个东西
（`Locator { chapter, offset }`，`position.rs:13`；写回 `Store::set_position`，
`store/books.rs:628`）。新开一张 `speech_positions` 会造出「读到哪儿」与「听到哪儿」
两个答案，而读者问的是同一个问题。停听即落库。

**会话时长复用 `reading_clock`**（`reader/modules/reading_time.rs`）：听就是读的一种。
它已经有 `begin_reading` / `note_reading_activity` / `end_reading` 与 300 s 的结算窗口，
听书在每段 `onDone` 时 `note_reading_activity` 一下就接上了，不必新写一套计时。

## 七、配置

`infra/config.rs` 里加一节 `Speech`（`serde(default)` + `Config` 字段 + `Default` +
`normalized()` 各补一处；配置文件是 **serde_json**，`~/.config/folio/config.json`）：

| 字段 | 默认 | 归一 |
|---|---|---|
| `rate: f32` | 1.0 | 夹在 0.5–2.0（**不是**引擎报的 0.1–10.0，见第二节那条坑 1） |
| `pitch: f32` | 1.0 | 夹在 0.5–2.0 |
| `auto_scroll: bool` | true | — |
| `voice: Option<String>` | None | 仅桌面（Android `voices()` 是 `Err`） |

UI 走 `ConfigHolder::edit_*` 那一套（`ui/shared/config_model.rs:138` 起），滑条的
形状照 `settings/typography.rs:52` 的 `SettingField`。

## 八、必须 / 可省

**必须**（少一条就是坏的功能）：

1. 随包 `rs/tts/Bridge.java` + 它在 R8 下不被剪 + manifest 补 `<queries>`。
2. 句柄在后台线程建，且建失败要有「这一格不摆」那条降级。
3. 停止不依赖回调（第②条约束）。
4. 进度写 `positions`，与读同一个坐标系。

**可省**（第一版不做，且不做的原因写在这儿，免得下次顺手加回来）：

- **不熄屏 / WakeLock**：念到一半屏幕睡了是引擎该管的事，`tts` 不管，我们也不管。
  真机反馈疼了再做。
- **不选音色**：Android 上 `voices()` 直接 `Err`，桌面那份清单在手机上无对应物。
- **不做锁屏控制**：`GpuiMediaSession.java` 与 `GpuiAudio.java` 在仓库里躺着但
  **没有任何 Rust 引用过**（grep `crates/**.rs` 零命中）。接它们是一件独立的事，
  不该挂在听书第一版上。
- **不写 trait 抽象**：`tts::Tts` 就是那个抽象（它内部已经按 `Backends` 分叉了）。
  再包一层 `trait SpeechEngine` 只有在「要换掉 tts」时才划算 —— 而换掉它的理由（第三节
  那三条）如果哪天真成立，换的是**整个 `speech` 模块**，不是给一个没人第二个实现的 trait。
- **不做音频导出 / 离线预合成**。

## 九、验收门

能在 headless 钉的：

- 段的切分：给一章 XHTML，`paragraph_range` 在段内任意偏移都回同一个区间，跨段回不同的。
  纯函数，不开窗。
- 「停不依赖回调」：喂一条 `onDone` 之后立刻 `stop()`，断言状态机不推进、不卡住。
- 进度：停听之后 `Store::position(book)` 读回来是**当前段起点**那个 `Locator`。
- 降级：`Tts::default()` 报错时，阅读页那一格 `try_find` 不到。
  （这条在 Linux 开发机上天然就是错误路径 —— `speechd` 没跑。）

只能真机测的（**别声称测过**）：

- `rs/tts.Bridge` 装进 APK 后 `JNI_OnLoad` 不炸、`onInit` 报成功。
- 有没有声音、`set_rate` 认不认、`onError` 什么时候来。
- `<queries>` 那条没补时是不是真的绑不上引擎。
