## 一、七级

形状由一件事决定：**位置在几何坐标系里怎么摆**。所以下表除了输入输出，还给出每一级
自己所处的参照系——参照系混用是这条线上最主要的 bug 来源。

| 级 | 输入 → 输出 | 纯？ | 缓存键 | 参照系 |
|---|---|---|---|---|
| 1 打开 | `book_id` → `Arc<Package>` + 章节表 + 资源表 + 位置 | 否（读库、开容器） | 一次会话 | 无（还没几何） |
| 2 取章 | `chapter_id` → 原始 XHTML 字节 | 否（容器 IO） | 章 LRU | 无 |
| 3 解析 | XHTML → `Dom` + `TextMap` | 纯 | 章内容哈希 | **内容坐标**（字符偏移） |
| 4 匹配 | `Dom` + 作者样式表 → 每节点命中的规则 | 纯 | 章哈希 ⊕ 样式哈希 | 内容坐标 |
| 5 层叠 + 排版 | 命中结果 + 读者偏好 + `LayoutKey` → 盒树 + 行盒 | 纯 + `Measure` 端口 | `LayoutKey` | **文档几何坐标** |
| 6 切片 | 几何 + 视口 → 页 / 栏 / 可见带 | 纯几何，便宜 | 不缓存，现算 | 文档几何 → 屏幕 |
| 7 呈现 | 可见带 → 已 shaping 的 run + 图 + 装饰 | 纯 + shaping | (文本, 字体, 字号) | 屏幕坐标 |

**级与级之间只靠数据结构对话，不许共享可变状态。**

## 二、三套坐标（定版式是第四套）与两处换算

| 坐标 | 单位与原点 | 谁产出 | 随版面变吗 |
|---|---|---|---|
| **内容坐标** `Locator`（章 ID + 字符偏移） | 字，原点是章首 | 不属于任何一级，是跨级的引用体系 | **不变**（这是它存在的全部理由） |
| **文档几何坐标** | 文档点 f32，原点是**章顶** | 第 5 级排版的输出属性 | 变：`LayoutKey` 一变就重算 |
| **屏幕坐标** | 像素，原点是视口左上 | 第 6 级切片时现算 | 每帧都可能变（滚动） |
| **页内坐标**（定版式） | 文档点，原点是该页左上 | 定版式提供方 | 不随读者偏好变（版面是死的） |

换算只允许发生在两座桥上：

```
内容坐标 ⇄ 文档几何      y_of(anchor, key) -> f32      hit(x, y, key) -> Hit
文档几何 → 屏幕坐标      screen = doc − 视口原点 (+ 栏偏移 + 边距 + 顶部预留)
```

三条规则：

**一、不许跳级换算。** 最容易被写出来的一行坏代码是"从锚点直接算屏幕坐标"——看着一步到位，
实际是把视口状态塞进了本该与呈现无关的内容坐标里，此后每一处视口变化都要回来改它。
恢复落点的正确走法要经过四个数：`Locator → 章 → 章内 y → 加章基线 → 全局 y → 减视口原点 → 屏幕 y`，
每一跳都对应上表里相邻的两行。

**二、叶子只存局部值，全局值靠前缀和现算。** 行盒的 y 相对**章顶**，块的 y 也相对章顶，章存自己的总高；
书级全局 y 是查询而不是字段。如果每行都存一个全书绝对 y，那么任何一章高度变化都要重写它之后的所有行，
而这正是"块级增量排版"要消灭的操作。唯一值得缓存的全局量是**全书总高**（进度条的分母），
它在章高变化时更新一次即可。

**三、单位与舍入要写死。** 几何全程 f32 文档点，中间不许 round——逐次舍入会在滚动时累计漂移，
表现为同一行在不同滚动位置抖动半像素。只在**切片边界**量化一次，`LayoutKey` 里的宽度用同一步长。
gpui 的 `Pixels` 只在第 7 级交给绘制时换算一次；几何层不许出现像素类型，否则文档坐标与屏幕坐标
会在类型上混成一套，而编译器帮不了你。

`LayoutMode::Fixed` 那一支的参照系与流式那套根本不同（页是既定的，没有推进轴），这就是 `LayoutMode`
这个字段存在的理由——不是为了分派代码。

## 三、中心结构：三级前缀和

这条线上绝大多数操作本质都是「在一根推进轴上定位一个点」。把它显式建成数据结构，而不是散落在各处
循环里的隐含假设：

```rust
/// 书 = 章序列，章 = 块序列，块 = 行序列；每一级持自己的高度前缀和
pub struct FlowGeometry {
    pub chapters: Vec<ChapterGeom>,   // 每章：总高、块表、与下一章的间隙
    pub chapter_prefix: Fenwick,      // 章基线（全局 y 由它现算）
    pub total_height: f32,            // 唯一缓存的全局量：进度条分母
}

pub struct ChapterGeom {
    pub id: ChapterId,
    pub blocks: Vec<BlockGeom>,       // 每块：相对章顶的 y、高、行区间 Range<usize>
    pub block_prefix: Fenwick,        // 块高的可增量前缀和
    pub lines: Vec<LineBox>,          // 按块先序连续入表
}
```

于是下面这些全都变成树上的查询，一次实现全部拿到：

- **块级增量排版**：改一个块只重排它自己，但它之后所有块的 y 起点都要变——`block_prefix` 就是为了
  这一笔。没有它，"增量"是假的，会退化成整章重排。
- **行 → 块**：块持有连续的 `Range<line>` 之后是一次二分。前提是「行按块先序连续入表」这条不变量
  写进排版层并被测试钉住。
- **可见带**：起止各一次二分，循环只跑真正可见的行。
- **`y → 锚` / `锚 → y`**（跳章、命中、进度、"本章还剩几页"）：同一棵树上的两种查询，互为逆。
- **跨章接缝**：邻章补齐与高度补偿都是"更新一个叶子 + 修一次前缀和"，不必重新累加整条链。

**推进轴的抽象层级**：`FlowGeometry` 里的"高度"应当写成"沿推进轴的推进量"+ 一个轴向量，而不是
字面的 `y`。竖排时这根轴变成 x，届时不必推翻这个中心结构。

## 四、样式分三段：解析、匹配、层叠

一个诱人但错误的合并是"XHTML 直接产出带样式的树"。不合并的理由有一硬三软。

**硬理由**：结构性伪类（`:last-child`、`:nth-last-child`、`:only-child`）在元素开标签那一刻**无法判定**，
因为它的后续兄弟还不存在。而选择器匹配用的 `selectors` crate 是在整棵树上做匹配的。合并之后要么放弃
这些伪类，要么仍然两遍走——那就没省下第二遍。

**三条软理由**：错误粒度会被糊在一起（解析失败等于那一章塌，样式缺失只是局部难看，读者要听的是两种
不同的话）；`TextMap` 必须与规范化文本同层（字符偏移坐标系只依赖空白折叠与行内图占位这类规则，
一旦和层叠纠缠，读者改字号就可能让批注漂移）；`<img src>` 归一化成资源表的键发生在解析期
（要用章节的 `base_href`），与样式无关。

真正的收益在别处——**三段的输入变化频率完全不同**：

```rust
pub struct LayoutKey {
    pub chapter_hash: u64,    // 第 3 级的输入；章里挂的 <style> 也长在它里面
    pub author_css_hash: u64, // 第 4 级的输入之一（样式表文件，与读者偏好无关）
    pub prefs_hash: u64,      // 整份读者偏好，见下面那条取舍
    pub width: u32,           // 栏宽，量化 1px（切片边界同一步长）
    pub columns: u8,          // 单栏 / 双栏：栏宽相同也要区分，切片要
    pub images_rev: u32,      // 本章图片索引的版本：<img> 固有尺寸是排版输入
    pub fonts_rev: u32,       // 内嵌字体集的版本（进程内「注册了几次」）
    pub metrics_rev: u32,     // 度量口径版本：换字体表实现、换断行/shaping 规则都要动
}
```

**落地时（`folio_core::layout::key`）对本文原稿改了三格，都是往「少一处人肉维护」的方向：**

| 原稿 | 落地 | 为什么 |
|---|---|---|
| `font_size: u32` + `line_spacing: u16` | `prefs_hash: u64`（整份 `Reader` 序列化后取哈希） | 逐格列等于一张需要有人记得维护的清单。实测这类漏法真的漏过一次：手挑的 `prefs_hash` 不含 `mono_font_family`，而等宽泛族名是折行的输入，于是「换等宽字体」不让任何缓存失效。改由 serde derive 覆盖全字段后，`Reader` 加字段自动进键，另有一条测试拿字段表反查这张清单（`layout::tests::every_reader_preference_changes_the_key`）。多算进来的目录那三格只值一次空转的重排，块级命中不受影响（块键含的是计算后样式哈希，目录档位进不了正文样式） |
| 无 `images_rev` | 加了 | `<img>` 的固有尺寸从 M3 起就是排版输入，而它既不在章文本里也不在样式里；不换这一格，换图片索引时旧块会被复用成上一批图片的行高 |
| `nonlinear: bool` | 去掉 | 排版目前把 float / absolute 一律当主流处理，这一格恒为 `false`。恒假的键格不是保险，是自欺：它让人以为已经守住了。接非主流几何那一级时**连同这一格一起**加回来，改动仍是一处。**2026-10-16 更新**：`float` / `clear` 已经接上，这一格不再是恒假 —— 但补的位置是**块级键**而不是章级键：一块让开多少宽由「旁边站着哪些浮动盒、以及它自己在哪儿」决定，那两个数按相对偏移折成一格进了 `layout::cache::BlockKey::floats`（没有浮动盒时恒为 `0`，正文的块一次都不多付），而 `LayoutKey` 那一层整个输入就已经包含章文本与样式，浮动盒是它们的产物，不必再单列一格 |

| 产物 | 键 | 含义 |
|---|---|---|
| `Dom` + `TextMap` | `chapter_hash` | 读者改任何偏好都不必重新解析 |
| 每节点的命中规则表 | `chapter_hash ⊕ author_css_hash` | **不含任何读者偏好** ← 整段设计的枢纽；这一行还没落地（命中表仍在每次排版时重算，见 §十三第 6 步） |
| `ComputedStyle` 与几何 | 上一行 ⊕ 其余字段 | 改字号只重跑层叠 + 增量排版 |
| `BlockCache` 的**复用范围** | `chapter_hash ⊕ images_rev ⊕ fonts_rev ⊕ metrics_rev`（`context_rev()`） | 任一格变了就整清：`NodeId` 只在同一份 DOM 里有意义，行宽只在同一张字体表里成立 |


命中结果与字号无关，而选择器匹配恰好是那条 O(节点数 × 规则数) 的贵路径
（`css/mod.rs:212` 的 `matched_in`）：把它单独缓存一级，读者拖字号滑条就只付层叠那遍算术的钱
（`css/computed.rs:469` 那句 `vec![root_base.clone(); dom.nodes.len()]` 也归入这一层，
拆出来之后它单独可优化，且不牵动 parser）。

**一个键、一处构造、各级缓存共用。** 谁都能问"现在第几代"，但只有会话能推进代次。
这条针对的是"同一个失效问题在 core 与 app 各答一遍"的写法——两处答必然漂。

## 五、缓存挂在哪一级：章的解析产物，不是文本

直觉是缓存取回来的章文本。但重复付的钱在后面：重新解析、重建 `TextMap`、重读样式表、重跑匹配。
所以缓存单位是**章的全部解析产物**：

```rust
pub struct ChapterArtifacts {
    pub dom: Arc<Dom>,
    pub text_map: Arc<TextMap>,
    pub matched: Arc<MatchedRules>,   // 与读者偏好无关，可跨代次复用
    pub char_len: usize,              // 与导入落库的那份字数比对
}
```

按 `chapter_id` 装进 LRU，**上限按章数**（DOM 是 arena，大小与文本长度近似线性，用章数封顶更好推）。
附带的好处：`char_len` 在导入落库处和解析产出处各出现一次，**两者不一致就是"这本书的索引过期了"的
免费检漏**，不需要额外的一致性扫描作业。

**落地到哪一步了（2026-10-12）**：`folio-app` 的 `reader/document.rs` 里有 `ChapterArtifacts`
（`dom` + `text_map` + 建它时那段文本的哈希），排版作业按 `chapter_hash` 决定「复用这份」还是
「重新解析一份」，验收是 §十二那条「改一次字号，重新解析的章数必须为 0」——已由
`document::tests::a_preference_change_reparses_nothing` 数出来（退回复用那一支它就会红）。
**还没落地的两件**：① `matched`（命中规则表）——`cascade` 仍是匹配与层叠一气跑完，拆开它是 §十三
第 6 步的活；② `char_len` 与导入字数比对的免费检漏。

**跨章那一件已经换了形状（2026-10-13 核对，原稿此处写的「只有一格」不成立）**：不是按章数封顶的
LRU，而是**锚章 ± 窗口**——`reader/book.rs` 的 `SPAN_WINDOW = 2` 让五个 `Document` 同时在场（锚章 +
上下各两章），每个各持一份自己的 `ChapterArtifacts`；换章走 `set_anchor`，新锚章若已在窗口里就
**把那份现成排版摘下来复用**（`take_span`），所以「上一章刚翻过来」今天**不重解析**。窗外整块裁掉，
驻留上界仍是常数量（5 份排版 + `TEXT_WINDOW = 3` 那份 ±3 章的正文文本）。待决第 4 条那个
「32–64 章封顶」因此不是还没定数，而是**被这个窗口取代了**——它要回答的问题变了：现在要定的是
窗宽，不是 LRU 容量。
`dom` 与 `text_map` 用 `Arc` 而不是各自 `Arc`：两者必须同源，一起换才不会出现
「坐标表指上一章的字」那种半新半旧。

## 六、后端形状

**边界：后端做到「几何」，不做「字形」。** 宽度可以离线算，glyph id 必须有字体。后端用 `FontKey`
描述"这一段想要什么字"，应用侧决定"这台机器上它是哪个字体"——这个交换词汇就是端口，也是后端能完全
脱离窗口跑的根本原因。

模块与职责：

| 模块 | 职责 | 含 IO |
|---|---|---|
| `store` | 查导入产物：章节表、资源表、目录、字体清单、位置、已读章 | SQLite |
| `format::container` | 容器家族的字节寻址：`Container` + `Package` | 容器读 |
| `document` / 会话 | 组装 `Book`、推进代次、持有各级缓存 | 无 |
| `dom` | XHTML → `Dom` + `TextMap` | 无 |
| `css`（match / resolve 两段） | 命中规则表；`ComputedStyle` | 无 |
| `layout` | 盒树、行盒、三级前缀和、块级缓存 | 用 `Measure` |
| `anchor` / `hit` | 锚↔几何互转、选区矩形、词边界 | 用 `Measure` |
| `position` / `annotation` | `Locator` 的序列化、比较、降级重定位；批注解析 | 无（读库在会话） |
| `task` | 上述"能后台做"部分的作业管线与事件流 | 无 |

端口只有两个，且这份设计刻意不加第三个：

```rust
pub trait Measure: Send + Sync {
    fn char_widths(&self, text: &str, font: &FontKey, size: f32) -> Vec<f32>;
    fn run_metrics(&self, text: &str, font: &FontKey, size: f32) -> LineMetrics;
    fn font_extents(&self, font: &FontKey, size: f32) -> (f32, f32);
    fn edges_in_run(&self, text: &str, font: &FontKey, size: f32) -> Vec<f32>;  // 命中与绘制同源
}

pub trait ImageProvider {
    fn render_source(&self, href: &str) -> Option<ImageSource>;
}
```

加端口的唯一合法理由是"后端要在没有窗口的环境里跑它"。字体解析（`FontKey → Font`）留在应用侧，
因为它只在绘制那一刻需要；进度反馈走 `task` 的事件流；容器 IO 不需要端口，后端本来就管文件系统。

对外的四个函数，就是后端在这条线上的全部暴露面：

```rust
fn slice(&self, viewport: Viewport, key: &LayoutKey) -> Scene;        // 可见带 → 可画的几何
fn hit(&self, x: f32, y: f32, key: &LayoutKey) -> Hit;               // 像素 → 锚
fn rects(&self, range: Range<Locator>, key: &LayoutKey) -> Vec<Rect>; // 锚 → 选区矩形
fn y_of(&self, anchor: Locator, key: &LayoutKey) -> f32;              // 锚 → 轴上位置
```

`key` 显式传参是为了让"用的是哪一代"在签名上可见；省略它就会有人拿旧 key 查新几何。
**应用侧只能通过这四个函数与排版对话；需要第五个就扩后端，不在界面里现算。**

后端在这条线上不许做的四件事：

1. 不许引用窗口、像素、字体对象那一类类型（core 与应用之间那条硬边界的含义）。
2. 不许出现按格式的分支：导入之后，`dom`、`css`、`layout`、`anchor`、`hit`、`store` 里不许有
   `match format`。今天排版层确实一处都没有，这条把范围扩到整条阅读路径。
   **唯一例外**：定版式需要格式知识参与"页"的语义，它出现在 `LayoutMode::Fixed` 那一支，不在主路径；
   这个例外要在注释里写明位置，免得将来被当成"漏了的分支"顺手补进主路径。
3. 不许在解析失败时把整本书拒掉——章是独立解析单元，坏一章只塌一章。
4. 不许把偏移坐标系与样式绑在一起：`TextMap` 只依赖规范化文本。若首字下沉之类需要改动文本序列，
   那必须仍然只在解析层发生。

另外，后端**不知道自己跑在哪个线程**（它没有线程概念），所以"不许在界面线程做 IO"这条只能由作业
划分来守；但后端要保证任何一次调用都不需要"当前线程"这个信息，这样调用方挪线程时后端不用改。

## 七、打开一本书：不走解析器

`book_id` → 可排版的状态，中间是三件事，**只有一件需要格式知识**：

| 段 | 谁做 |
|---|---|
| `book_id` → 路径与索引记录 | 库 / 会话（格式无关） |
| 打开容器、建 `Package` | **`Container`**（容器知识，不是格式知识） |
| 恢复位置、锚换算成几何 | 会话 + 排版（提供方不知道"位置"这个概念） |

于是 `DocumentProvider` **不需要 `open()` 方法**。分工成一句话：

```
导入：provider.index(container) —— 用一次格式知识，读清单，产出结构，落库
阅读：container.read(address)   —— 不需要知道这本书是 EPUB 还是 FB2
```

这条成立的**两个前提**，都必须落在导入产物里，否则运行时要回头找提供方：

1. **每章的 `base_href` 存进章节表。** 相对路径基准是格式知识（EPUB 相对 OPF 所在目录、CBZ 相对容器根、
   裸 HTML 相对自身、FB2 用 `#id` 不是路径）。存下基准之后，运行时的"src → 资源表键"退化成纯字符串运算。
2. **内嵌字体清单落库**（`@font-face` 声明的路径 → 已归一化的 `Address`）。否则取字体要重走一遍
   容器清单的定位链，那是"开书需要格式知识"的最后一个理由。

代价：提供方不参与打开，就没人替你验证索引还新不新。护栏是比对 `index_version`，加上
`ChapterArtifacts.char_len` 与库里字数的比对；检测到过期时**后台触发 `reindex`，不阻塞打开**——
旧索引通常只是目录粗一点，不是打不开。

## 八、容器共用层与 ZIP 直读

`Container` 的实现按容器家族分，数量比格式少得多：ZIP（EPUB / CBZ / DOCX / ODT / HTMLZ）、
ITSF（CHM）、已解到磁盘的漫画页（CB7 / CBR / CBT）；PalmDB（MOBI / AZW / AZW3 / AZW4 / PDB）另有一层
（`format::palmdb`，它的寻址是记录号而不是条目名，所以不进 `Family`）；OLE2（`.doc`，与 `.xls` /
`.ppt` / `.lit` 同一只壳）同样不进 `Family`，因为这一版只有判定层去开目录（认「有没有 `WordDocument`
那条流」，`format::doc::ole2_shape`），provider 那一路是把整份字节交给 `rwml`、容器在它内部解；
裸文件（TXT / Markdown / 单 XHTML /
PDF / DjVu）一次 `File::open` 就是全部寻址，也不需要句柄。**让每个提供方自己写一遍寻址，就会得到 N 份各自漂移的实现。**
「将来的 PDF」那一档也已经是过去式：PDF 不是第四种容器，它是「一页要算出来才有像素」那一种页。

ZIP 这一层有个具体的技术理由支持"存偏移直读"：`zip` crate 的 `ZipArchive::by_name()` 要 `&mut self`
（它得 seek 底层 reader），所以共享一个 archive 对象必然带锁；而每线程重建 archive 等于每次重解析中央目录。
出路是用资源表里已经存下的三个数（偏移、压缩后大小、方法）直接从偏移读：

```rust
pub struct ZipContainer {
    pub path: PathBuf,
    pub index: Arc<ZipIndex>,   // 中央目录解析一次的产物：归一化名 → (偏移, 大小, 方法)
}
```

四条必须避开的坑：

- **data descriptor**：流式写入的 zip 在本地文件头里 size 与 CRC 填 0，真值只在中央目录。
  所以以中央目录为准，本地头只用来取"名字长度 + extra 长度"这两个字段。
- **zip64**：条目太大时本地头的字段是 `0xFFFF` / `0xFFFFFFFF` 哨兵值，同样只能信中央目录。
- **裸 deflate**：zip 存的是没有 zlib 头的裸 deflate，要用 `flate2::Decompress::new(true)`（`raw = true`）
  自己喂缓冲，不能用 zlib 那套 reader。`flate2` 已是 core 的直接依赖，不新增树。
- **加密条目**：当"取不出"返回 `None`，明确失败，不许退化成乱码。

大小写与编码的降级（EPUB 引用与条目名不一致是现实）仍然要有，但它发生在**导入建表时**一次，
而不是每次取字节都扫一遍全书条目名。

**落地顺序**：第一步只把 `Zip::locate`（`format/zip.rs:40-46`，两遍全量扫描且每个条目名分配一个 String）
换成"解析一次建 `HashMap`、之后查表"，不动任何数据结构就能消掉滚动取图的主要浪费；第二步再上
`Address` 直读、把锁拿掉。顺序反过来做的话，会在改架构的同时改热路径，出了问题分不清是谁。

## 九、呈现层：场景跨帧稳定与字形级原子

**本节 2026-10-13 重写过。**原稿说「现状每条 run 每帧调一次 `shape_line`，修法是把 shaping 提到场景构造
并缓存」——那个诊断不成立，按它做会白改一遍。核对依赖源码（`gpui-pre-0.3.8`）后的事实是这三条：

| 原稿的说法 | 源码里是什么 |
|---|---|
| 每帧重新 shaping | `shape_line`（`text_system.rs:638`）每次调用都查 `LineLayoutCache`，键 `CacheKey{text, font_size, runs, wrap_width, force_width}`（`line_layout.rs:937`）。命中就**不重 shaping** |
| 缓存跨帧复用 | 缓存挂在 **`WindowTextSystem`（每窗口一份）**，只有 `previous_frame`/`current_frame` 两张表（`:459-460`），`finish_frame`（`:586`，由 `window.rs:3389` 每绘制帧调）互换、从上一帧搬正在用的那些（`:533-537`）。**保留期是两帧**，不是「跨帧」 |
| 真正的浪费是每次 `SharedString::new`，而参数是 `impl Into<Arc<str>>` | 参数就是 **`SharedString` 按值**，而它是 `SmolStr`——绘制里那句 `run.text.clone()` 是引用计数或 22 字节内联拷贝，**不是**堆分配。那次真分配在**场景构造** `scene.rs:117` |

所以钱付在别处。实测（2026-10-13，debug 构建，`flow()` 语料、窗宽 460、字号 16，一条 240 px 的滚动走完两帧）：

```
场景重建 5 次  ·  物化 62 个 run（62 次 SharedString 堆拷贝）  ·  shape_line 调用 62 次
```

- **5 次重建**：连续模式**每个进链的章各造一份场景**（锚章 ±2，见 `reader/book.rs` 的 `SPAN_WINDOW`）。
- **62 次物化**才是那笔真分配。它由视口决定，**不随书变长**——字越小、章越长都不会涨过一屏的行数。
- **62 次查表**：命中不重 shaping，但键含整段文本 → **命中也要把文本哈希一遍**。

还有一笔原稿与差额表都没记的：`collect_decorations`（`scene.rs:186`）**每帧走整章的 `layout.blocks`**，
逐块比对 cull。§十一 第 4 条那次「可见带二分」只给**行**做了，块装饰这条路是漏网的。同一份语料一章
**160 块**，长章（600 段那种）就是 600+，再乘进链的五个章——**这是本节唯一随书变长而变长的每帧开销**，
所以按代价排在 62 次拷贝前面。**这一笔已于 2026-10-15 接掉**（折成短表，见 §十一 第 12 条 —— 那一格原处方的二分对嵌套块不成立）。

**修法（2026-10-13 已决形状）**：把场景从「屏幕坐标的快照」改成「**行单元表（章内坐标）+ 每帧一个平移量**」。
根子在 `GlyphRun` 的 `x` / `baseline` 存的是相对**元素原点**的屏幕值（`paint.rs:26-38`）：滚动一动，每条
run 的 `baseline` 都变，于是整份只能重造。这正是 §二 规则 2「叶子只存局部值，全局值靠前缀和现算」
**在呈现层欠着的那一笔**——排版层已经照它做了（`BlockBox.y` 相对章顶、全局 y 由拼接链现算），绘制层还没。

| 存进表（章内局部量） | 每帧现算（三个平移数） |
|---|---|
| 文本句柄（物化**一次**）、`FontKey`、字号、粗细斜体、underline、`Option<Color>`、行内累加后的 `x`（相对**行首**）、基线（相对**章顶**） | 栏偏移 `column_x`、这一片的章内起点 `origin_y`、页眉带高 `top`；主题色在摆子那一跳由 `Option<Color>` 落成 `run_color` |

四条硬约束，漏一条就是把失效问题从一处拆成两处：

1. **键只用 `Document::applied` 那把 `LayoutKey`**（§四「一处构造」），行号直接当下标，不再拼第二把。
2. **主题色不许烘进表**：`LayoutKey` 里没有主题，烘进去就是「换了夜间模式但颜色还是旧的」那种看不出来的错。
3. **解析好的 `Font` 不许烘进表**：`FontCache` 已经有「换书 `reset`、改偏好 `clear`」那条纪律（`measure.rs:155`），
   表里再存一份就是第二个真相。它只是一次哈希查表 + 一次 `Arc` 克隆，不是这笔开销的主角。
4. **表的容量按整章一份**挂在 `Document` 上（随它进出 ±2 章窗口），懒物化：某一行的单元只在它第一次
   进带时才建。**这条决定了验收口径**——见下面那句。

**`ShapedLine` 那一格：已接（2026-10-15），但形状与这里的原案不同。**原案说「先不存，等行单元表
落地后重跑门」，实际是**单独先接了一张自己的表** —— 因为它不依赖行单元表，而且有一条源码事实把
形状改了：`ShapedLine.layout` 是 `pub(crate)`（`gpui-pre-0.3.8/text_system/line.rs:43-50`），
外部**拿不出**那份 `Arc<LineLayout>`；而 `ShapedLine.decoration_runs` 里**带主题色**，正是上面
第 2 条硬约束要拦的那种「换了夜间模式线还是旧色」。所以：

- 存的是 **`Arc<LineLayout>`**，键是 `(行号, 行内片段槽位)`，挂在 `Document::shaped`
  （`RefCell<HashMap<..>>`，容量 4096 条封顶、满了不再插、不做 LRU）。
- 绘制改走 `WindowTextSystem::layout_line`（`text_system.rs:886-892`，直接返回
  `Arc<LineLayout>`）而不是 `shape_line` —— 顺带不再每帧造一份**我们从没读过**的
  `decoration_runs`（差额表第 14 条记的就是这件事）。颜色不进键因此是**结构性**的，不靠纪律。
  `CacheKey.runs` 用的是 `FontRun{len, font_id}`（`line_layout.rs:937-943`）而不是 `TextRun`，
  本来就无颜色；而每条 run 单独 shape（一次一个 `TextRun`），`layout_line` 里按
  「装饰变没变」切 font run 那一支（`text_system.rs:896-922`）在只有一条时无从切起。
- 失效只挂 `Document::drop_fragments()` 一处（`set_chapter` / `set_prefs` / `set_images` /
  `apply_typeset` 四个都走它），不新造第二套失效判断。

验到的是**次数**：往返一趟从 62 次落到 0（`view::tests::scrolling_back_to_the_same_band_does_not_reshape`，变异验过 —— 关掉插入给 `left: 62`）；**每屏省下的毫秒 2026-10-15 已上真机复测**：冷一屏 `shape_only_us` 4792 µs → 暖 230 µs（下面那张表倒数第二行）。
变异验过 —— 关掉插入给 `left: 62`）；**每屏省多少毫秒还没上真机复测**，别把下面那条 4.6 ms 当成已证的收益。
`SceneRuns` 那 62 次文本拷贝照旧在付，那是行单元表的事，两条门分开钉。

翻页动画（gpui 没有通用变换，卷曲只能落在逐字形绘制上）要求「每个字形可重定位」。两条源码事实：
`Window::paint_glyph(origin, font_id, glyph_id, size, color)` 在 `window.rs:4687`，而 gpui 自己的
`paint_line`（`line.rs:521`，字形循环在 `:742`）**也是逐字形**——换成 `ShapedLine::paint` 并不会少干活，
只是把落点交出去。要自己算位移就得拿前进量，而 **`ShapedGlyph{id, position, index, is_emoji}`
（`line_layout.rs:45-56`）没有 advance**：只能从相邻 `position.x` 差分，或走 `TextSystem::advance`。
**这两件事在同一次改动里一起满足**：行单元表让字形位置跨帧稳定，卷曲就只需要重算位置、不需要重算几何。

四条纪律：

- 手势期间**不许推进代次**（拖动时读者改字号、字体注册完成、邻章补齐都不能挤进来），否则两页内容会
  在拖到一半时错位。**这条今天还没有门可挂**——树里一条补间动画都没有（翻页是页号 / `scroll_y` 一帧
  切换），所以它现在只是给接动画那一轮预备的约束，不是待修的 bug。
- 钉住代次靠**不可变值 + `Arc`**：界面持的那一代几何不可变，手势期间不取新一代即可。
  **不设计租约 / Guard API**——代价只是内存里可能同时存在两代几何，完全可接受，
  而省掉一整套需要小心维护的租约生命周期。（原稿写的 `Arc<ChapterGeom>` 是 §三 那个没建成的结构；
  今天实际被这样持有的是 `Document` 里的 `Layout`，锚章 ±2 各一份。）
- 命中与绘制必须同源（同一个 `Measure` 实例、同一代几何），否则"跳到那条高亮，高亮框画在下面两行"。
- **验收断的是往回滚，不是往前滚**：单元表懒物化，某一行的第一次进带**必须**物化它——所以
  「滚动一屏 `SceneRuns` 增量为 0」是个错的口径（原稿与 2026-10-13 立的那条门都写错过一次）。
  正确的两条是：① 滚下去再**滚回原处**，第二趟 `SceneRuns` 增量 = 0；② `SceneRebuilds` 仍然 > 0
  （摆子每帧都要走，那是可接受的代价，不该拿它当验收）。

   `view::tests::changing_the_font_size_reshapes_the_same_lines`（改字号必须 > 0），
   探测器是既有的 `a_scrolled_frame_currently_rematerializes_the_visible_runs`
   （往前滚三格计数都 > 0，把计数删掉它当场红）。
   **`Metric::ShapeLineCalls` 的口径随这次改动变了**：从「每条 run 一次」变成
   「表未命中一次」（`folio_core::infra/metrics.rs` 那条文档已同步）。
5. **行单元表：走过的行不再重物化**（2026-10-15，`reader/document.rs` 的 `Document::row_units`
   + `reader/scene.rs` 的 `Scene::build`）。§九 那个形状落地了：每行一条单元，值全是**章内
   局部量**，按行**懒物化**挂在 `Document` 上随它进出 ±窗口；每帧只往上加三个平移数。
   两样东西照 §九 那两条硬约束**没有烘进表**：解析好的 `gpui_kit::Font`（存 `FontKey`，
   每帧走 `FontCache` 现解析）与主题色（存 CSS 那一格 `Option<Color>`，每帧现落 `run_color`）。
   **与原案的一处不同**：单元里同时存**图片片段**的框（`RowFragment::Image`），因为 x 只能有
   一个来源 —— 要是文本的 x 从表里来、图片的 x 还在每帧的片段走里累加，那就是两个真相，
   漏改一侧就是断行与绘制错位。字节与固有尺寸仍然每帧现问 `ChapterImages`（那两样随
   图片索引变，不是这一格该留的）。失效仍然只有一处：`Document::drop_fragments`。
   `Metric::SceneRuns` 的口径同步从「每帧摆几条 run」改成「这一帧新建几条单元」，
   计数点跟着从 `Scene::build` 挪进 `row_units` —— **不改口径那条往返门永远绿不了**，
   因为缓存生效时搬运条数照样是满屏。
   门：`view::tests::scrolling_back_to_the_same_band_materializes_no_new_runs`
   （`#[ignore]` 已摘，往返增量 0；关掉命中支变异重跑给 `left: 62`）。
   **§九 那条「探测器接上之后要删掉」的预期没有兑现，也别去删它**：单元表是懒物化的，
   往前滚必然有新行第一次进带，那一趟该付，所以
   `a_scrolled_frame_currently_rematerializes_the_visible_runs` 改完口径之后**照样有效**，
   而且它现在是两张表共同的探测器（删掉计数它当场红）。
6. **排版键的两格输入哈希：算一次，不每帧重算**（2026-10-15）。
   `LayoutKey::compose` 从前收 `author_css: &str` 与 `prefs: &Reader`，于是
   `Document::layout_key()` —— **每帧、链上每个进链的章各一次** —— 都要付
   「整本书的 CSS 走一遍 SipHash」+「整份 `Reader` 用 `serde_json::to_vec` 序列化一遍
   再哈希（带一次堆分配）」（`layout/key.rs` 的 `prefs_hash`）。这与 §九 那条
   「`shape_line` 命中也要把整段文本哈希一遍」是同一个错误在上一层的复刻，
   而 CSS 是整本书共享的一份、通常比一章正文长。
   现在这两格活在 **`layout::LayoutInputs`** 里：建 `Document` 时算一次、
   `set_prefs` 时重算一次，`compose` 只搬那两个数。`Document::author_css` 那一格
   因此整个删掉（它存在的唯一理由就是被每帧哈希）。
   **纪律没有变成第二个来源**：样式与偏好的哈希仍然只由 `key.rs` 的
   `content_hash` / `prefs_hash` 产出，而产出点只有 `LayoutInputs::compute` 与
   `LayoutInputs::set_prefs` 两处；`LayoutKey::compose` 仍是唯一的构图点。
   门的分工是两层各一条 —— 键那一层
   `layout::tests::cache::the_layout_inputs_hash_once`（建一份输入、连问两百次键，
   `Metric::LayoutInputHashes` 增量 0），界面那一层
   `document::tests::asking_for_the_key_never_rehashes_the_inputs`
   （一个 `Document` 问 300 次键增量 0；变异验过：把 `layout_key()` 改回每帧
   `LayoutInputs::compute(...)` 就给 `left: 300`）。**省下的毫秒没在真机复测过**，
   **已量（本机 debug，`LayoutInputs::compute` 单次）**：2 KB CSS 23.8 µs、8 KB 49.7 µs、
   20 KB 96.3 µs、64 KB 256.6 µs —— 拟合出来是 **≈3.3 ns/字节的 CSS SipHash + ≈16 µs 的固定底**，
   而那个底就是 `prefs_hash` 里的 `serde_json::to_vec(Reader)`（它比整本 CSS 走一遍哈希还贵）。
   链上 5 个章各一次 ⇒ **样式表小的书 ≈80 µs/帧，22 KB 样式表的书 ≈480 µs/帧**。
   真机 release 会小一些，但量级在这里 —— 这一格比我当初估的大了一个数量级多。

7. **装饰短表：整章块表每次重排走一次，不每帧走**（2026-10-15，§十一 第 12 条）。
   `collect_decorations` 从前每帧、链上每个进链的章各把**整章的 `layout.blocks`** 走一遍，
   才筛出那几条带底色/边框的盒子（一份语料一章 160 块、长章 600+），而且每帧还为带内
   每个块 `style_of(node).cloned()` 克隆一份 `ComputedStyle`。
   现在 `Layout::decor_seeds(styles)` 在 `Document::apply_typeset` 里折一次成
   `Document::decorated`（与排版结果**同一批换**），每帧 `place_decorations` 只做三件
   确实有「此刻」的事：按可见带裁、加两个平移、落主题前景。
   **那张表不能按 y 二分**（与 `lines_in_band` 的区别，§十一 第 12 条原处方的错）：
   块是嵌套的，父盒 `y + height` 远大于其后的子盒，`Layout::stacked` 那一格只為行盒量过。
   `currentColor` 的折法挪到表里（边框没写色就取本块 `color`）—— 那是纯 CSS 解析，
   不含主题；剩下的「`None` 落主题前景」仍在每帧那一步，主题色一格都没烘进表
   （§九 第 2 条硬约束）。`Document::style_of` 随这次改动删掉（它唯一的读者就是这条路径）。
   门：`document::tests::scrolling_never_rebuilds_the_decor_table`（50 次问键增量 0；
   变异两头都验过 —— 不重折时红在「短表该有条目」，每帧重折时给 `left: 50`），
   加上 `layout::tests::index::the_decor_table_matches_the_per_frame_full_scan`
   拿**接线前那趟全表扫描**当参照实现逐条对拍（含顺序），以及那条单独钉四条筛子的
   `each_decor_filter_still_fires_on_its_own`。**省下的毫秒没在真机复测过**，
   它取决于每章有多少块，所以别的书仍可能更高。**2026-10-15 已上真机复测**：《未来简史》上 `decor_us` 读到 **0–3 µs/帧**，这一格已经不是帧预算里看得见的一项。
8. **作者样式表：一本书解析一次，不每进一章解析一次**（2026-10-15，真机拆开量出来的）。
   `Document::with_source` 从前每次构造都跑一遍 `RuleSet::parse(整本 CSS)` —— 一本书要建
   「锚章 + 邻章」好几个 `Document`，于是每进一章就在 UI 线程重解析同一份规则。真机探针
   拆开量到 **1.5–1.9 ms / 章**（《未来简史》23.6 KB / 323 条规则，`RuleSet::parse` 单独
   1.16 ms，release），跳一次章一次铺四章 = 7 ms 落在同一帧里。现在 `Book` 开书时
   `author_rules(&css)` 解析一次、各章 `Document` 分同一个 `Arc<RuleSet>`；**顺带把每次
   提交作业时的那份深拷贝也挪进了作业里**（`TypesetInput` 拿走的只是引用计数，
   `(*input.rules).clone()` 在排版线程跑）。修完在同一处复测：**6–73 µs / 章**（25–190×），
   而那一跑的日志里「规则表引用数」从 2 一路涨到 6 —— 那是「整本共用一份」的结构性证据，
   不依赖计数器。门：`document::tests::the_author_stylesheet_is_parsed_once_per_book`
   （`Metric::RuleSetParses`：开书 1 次，进 N 章与改偏好都 0 次；三条变异各红一次 ——
   `make_span` 换回自解析、`set_anchor` 换回自解析、计数器不接）。

**真书上的逐阶段帧分解**（2026-10-15，headless、debug、每次 reset 后渲一帧取回那一帧的分格，30 帧均值；
两本真书各 20 步 240 px 滚动）。**三条边界先说清**：① `cfg(test)` 下排版作业是**同步跑在帧里**的
（`reader/document.rs` 的 `if cfg!(test)`），所以「排版」那一列在真机上不在帧上；② debug 构建，绝对值
比真机大；③ `TestWindow` 有没有真走图集光栅化不确定，「逐字形」那一列只能当**下限**。相对结构与两个
零是可靠的。

| 一本书 | render 相 | 取章/窗口 | 排版(测试内同步) | 场景 | 其中装饰 | paint 相 | 其中逐字形 | **shaping** |
|---|---|---|---|---|---|---|---|---|
| 《蛇结》28 章 | 2246 µs | 80 | 2054 | 64 | 0.6 | 249 | 226 | **0.0** |
| 《斗战狂潮》1225 章 | 201 µs | 13 | 6.8 | 75 | 21.8 | 104 | 78 | **0.0** |

读出来的四件事：

1. **`shaping` 两本都是 0.0 µs/帧** —— ① 那张 shaping 表在真书上确认生效（进屏的行走的是表，
   gpui 那一层一次都没被叫到）。这一格从 §九 表里的「4.6 ms/屏」直接归零。
2. **`取章/窗口` 只剩 13–80 µs** —— ③ 之后 `spans_ns` 里已经没有容器读（真机应当更低）。
   《蛇结》那 80 µs 里每帧只有 0.10 个新章进窗口，所以它主要是 `window_range` 每帧量窗口，不是取正文。
3. **`render` 相里没分格的那一块 = 48 µs（蛇结）/ 106 µs（斗战）**，`paint` 相里没分格的是 23–26 µs。
   这就是 ⑥「旁支冻结」要省的东西：**合计 70–130 µs/帧，而你给它设的门槛是 ≥500 µs/帧。
   按这条实测，⑥ 不做。**
4. **`装饰` 在《斗战狂潮》上还有 21.8 µs/帧**（A 之后只剩裁短表），说明这一本每帧真有一批带装饰的块
   在屏上；相对它 201 µs 的 render 相是 11%，不值得再动。

**剩下唯一还值得动、且有数的一笔**：`逐字形`（② 的目标，但必须真机量 —— headless 只能给下限）。
§十一 第 9 条（**25 条批注 = 每帧 +1.7–2.2 ms**，比这张表里任何一格都大，因为它在**没有批注时是 0**，
所以这张表看不见它）**已接，2026-10-15**：同一把尺子上四臂实测 1.4–2.1 ms → **0.23–0.35 ms/帧**
（**6.1–6.2×**，一帧走的行数 1525 → 5–7）。数、门与「原处方对了一半」都在 §十一 第 9 条那一格。


**量过之后决定不做的三笔**（2026-10-15，本机 debug；一次性探针，测完即拆 —— 记在这里是别让下次
再量一遍）：

- **坐标链每帧重算** —— `Book::placements` 每次 `collect` 一个新 `Vec` + 一次 sort，被
  `window_range` / `spine_snapshot` / `compensate_spine` / `migrate_spine` / `content_height`
  / 渲染循环 / `resolve_position` 各调一遍。数出来**一次滚动步长 37 次调用**（`settle` = 两帧
  + 排版在飞时多跑的 parked 帧，所以 ≥18 次/帧），单次 **252–271 ns**，一帧合计 **≈5–10 µs**。
  相对稳态帧 1.1–2.5 ms 是 0.2–0.9%。**不改**：在链里缓一份 `Rc<[Placement]>` 要新造一套失效
  信号，几微秒换不来一个新失效点（这张链与 span 高度、窗口裁剪已经是三处各说一半的东西了）。
- **`sync_prefs` 每帧克隆整份 `Reader`**（`ConfigHolder::reader(cx)` 取一份 + `wanted.clone()`
  + 整份比较）—— 实测 **826 ns/帧**。**不改**，理由同上。
- **⑥ 旁支冻结**（每帧新建的 `div`/图片元素进 taffy，想用 `Entity::cached` 回放或改用 `paint_quad`
  绕开元素树）—— 上面那张表的「未记名」就是它的上界：**70–130 µs/帧**，而你给这条定的门槛是
  **≥0.5 ms/帧**。**不做**。附带一条：`Entity::cached` 的回放会连位置一起冻住，而装饰与图片的
  `top` 里含每帧的滚动偏移，所以真要走那条路得先解决「冻住的东西怎么跟着滚」，不是包一层就完事。

这两笔与 §九 那三笔的差别是**量级**：那三笔是每帧几十到几百微秒、且随屏幕与书长涨，这两笔是
常数微秒。**「看起来在重复干活」不等于「值得改」** —— 这条判据写在这儿，比这两个结论更值钱。

另外一条不是代码结构、但量出来最大的一笔：Android 上 gpui 的 wgpu 后端
`recommended_rendering_mode` **恒回 `Subpixel`**（`gpui-pre-wgpu/cosmic_text_system.rs:277`），
于是每个字形按 LCD 三通道光栅化 —— CJK 一屏新字形要 44–52 ms。`ui/platform/android.rs` 里
改成 `TextRenderingMode::Grayscale` 之后降到 6–10 ms。这是**观感换帧预算**的取舍，删一句就回退。

**上面那句「6–10 ms」2026-10-15 用同一个探针字段没复现出来**（灰度 AA 确实还开着，
`android.rs:95` 那一句在）：冷一屏读到 44.2 ms、暖 15.2 ms。要么当年那格量的不是同一个量
（只算光栅化、不含逐字建图元），要么这一年里别处把它抬回去了。**没复现出来的东西不删不改**，
但拿它当收益的那一步要按新数重算：首次光栅化 ≈29 ms/屏，另外 ≈15 ms/屏是每帧建图元，
后者不在 ② 的射程里。

**已落地的一笔与还欠着的一笔**（都不在上表里，按代价排）：

- **一章文本入库那一跳：已移出 UI 线程**（2026-10-15）。原来 `Book::ensure_window_spans`
  → `make_span` → `chapter_text_at` 在渲染帧里现读容器，实测 7–9.5 ms / 章
  （`reader/perf.rs` 的 `spans_ns` 那一格；`make_span` 里其余几件都是零头 ——
  `ChapterImages::new` 只是 `dir_of` 加两次 `Arc` clone，`Document::new` 拿的是空串所以不解析，
  `set_chapter` 只存串）。
  **做法是塞进排版作业，不是独立一趟预取**：`ChapterSource` 分成 `Text(String)` 与
  `Fetch { doc: Arc<dyn Document>, chapter: usize }`，`typeset_job` 的第一步把 `Fetch`
  解成文本，后面「解析按内容哈希复用」那一支照旧，取不到就降级成空章（与从前
  `chapter_text_at` 那句降级同口径 —— 让作业报错会让 `applied` 永远设不上，
  一本读不出来的书就变成每帧重投一趟作业）。
  独立预取会让一章的接缝付**两次**往返（文本回到界面才能投排版作业），而排版队列本来就是
  单线程 FIFO、每个 `Document` 至多一个在飞作业 —— 那是**串联**依赖，不是并联，
  原稿那句「修法与排版作业同款」不成立。
  随这次改动落掉的东西：`Book::texts` / `TEXT_WINDOW` / `prune_texts` 三格连同那条窗口裁剪
  测试。上游给了反向佐证 —— crengine **连解压后的条目都不缓存**，每次读重走一遍 inflate
  （`lvstream.cpp:2275-2293`），外面那层缓冲还是被注释掉的（`:2513`）。
  **键那一格的拆法**（唯一的拦路石）：`LayoutKey::chapter_hash` 从前从 `self.source` 算，
  界面不再持有正文就算不出来。现在 `LayoutKey::chapter` 存**身份**
  （`ChapterSource::identity`：按位置取的给章号，正文在手的给内容哈希，因为那种章没有章号可指），
  内容哈希搬到 `ChapterArtifacts.key` 上、由作业自己算 —— 两个哈希答两个问题：
  「这是哪一章」与「这份 DOM 是从哪段字节来的」。批注那级缓存本来读的就是产物
  （`Document::chapter_hash()` 返回 `artifacts.key`），所以那一格一个字没动。
  **代价，写在这里**：按位置取的那一路从此只认章号，所以**同一会话中途把书文件换掉**不会被
  发现，旧几何会静默留着。接受它的依据是：重扫的新索引本来就「下次开书才生效」，而文件真被
  换过的那一本内容指纹（`sha2`）也不同、在库里是另一条记录。要推翻这条判断，先看
  「同一会话里正文变过」到底能不能发生。
  门：`document::tests::the_key_and_the_fetched_chapter_are_the_same_chapter`
  —— 钉「身份与来路必须一起换」。删掉 `set_chapter` 里那句身份赋值，它当场红，
  既有的 `the_layout_key_is_composed_in_one_place` 同时红。
  **归因仍然没钉死，只是不再影响帧预算**：EPUB 那条早就走共享容器（`Container` 一本书只开
  一次），所以那 7–9.5 ms 里**没有**「重开容器 + 重扫中央目录」，剩下两种可能 —— 真是
  inflate + UTF-8，或者是在等 `Container` 那把 `Mutex`（图片字节走同一把锁，而取图在后台
  线程）。两种现在都在后台，但**后台吞吐够不够**要真机看：`spans_us` 应当归零，
  该盯的是排版队列的积压。
- **字形光栅化仍落在进屏那一帧**（冷 shaping 那一半已经接了，见上面「已落地」的第 4 项）。
  原稿写的机制**不成立，按它做会白改一遍**：`Window::with_content_mask`
  （`gpui-pre-0.3.8/window.rs:4029-4044`）是**与当前 mask 求交**（`:4036`），
  「视口下方一屏」与视口 mask 相交是空集，画不到视口外去。
  目的仍然能达到，但理由得换：`paint_glyph` 的光栅化发生在读 content mask **之前**
  （`:4725-4733` 在 `:4738` 之前），而且函数里**没有任何 bounds-vs-mask 的提前返回** ——
  mask 只是塞进图元交给 GPU 裁（`:4745` / `:4755`）。所以画在视口外确实会把字形烘进图集，
  代价是**每个字形照样 `insert_primitive` 一次**，正是上面第 1 项（`paint_layer`）刚消掉的那笔
  R 树开销；而 `sprite_atlas` 是 `Window` 私有的（`:1174`），**不存在「只光栅化、不进场景」的入口**。
  成立的那条依据仍在：图集键里的 `subpixel_variant.y` **恒为 0**（`SUBPIXEL_VARIANTS_Y = 1`，
  `:4704-4709`：量化后的 y 就是 `round(y)`，`fract()` 归零），x 那格是设备像素小数部分量化到
  1/4（`:4702` / `:4708`），而 `glyph_origin` 是绝对坐标（`:4699`）—— 竖向滚动不改它，

## 十、线程与后台作业

### 10.1 判据：一个步骤能进后台，要同时满足五条

1. **签名里不需要窗口**：`Window` 不进参数。gpui 的绘制、事件注册、纹理上传都持 `&mut Window`，凡是需要它的都留界面线程。
2. **输入不可变**：交进去的是 `Arc`，作业跑的过程中没人能改它。这条同时保证了"后台算的时候读者又动了偏好"不会产生半代结果。
3. **有取消检查点**：大文件与大册量随时能停，检查点放在**单元之间**（章与章、书与书），不放在一次函数调用的中间。
4. **结果整份搬回界面线程**：一次事件带回一个完整产物，而不是逐步回调界面。逐步回调会把"半代状态"重新引进来。
5. **失败只影响它自己那一步**：不破坏别处已经成立的状态。

配套一条必须写死的规则：**计算在后台，提交在界面。** 排版结果在后台算好，但"推进代次、决定采用哪一代"
只在界面线程做。否则读者会看到前一页是新字号、后一页是旧字号——那是比卡顿更糟的错。

### 10.2 逐级归属

| 环节 | 归属 | 可并行 | 取消粒度 | 说明 |
|---|---|---|---|---|
| 1 库查（章节表 / 资源表 / 位置 / 字体清单） | **界面线程** | 否 | 不需要 | 一次 SELECT。等它比等一次解压便宜 |
| 1 开容器、解析中央目录、建 `Package` | **后台** | 一本书一次 | 整次开书 | 产物 `Arc` 共享给后续所有作业 |
| 2 取章字节 | **后台** | **多章并行** | 单章 | 邻章预热就是这一格 |
| 3 解析 → `Dom` + `TextMap` | **后台** | 多章并行 | 单章 | 纯函数，输入是章字节 |
| 4 匹配 → 每节点命中规则表 | **后台** | 多章并行 | 单章 | **跨代次复用**，所以值得单独一个作业，一次算完整本书摆好 |
| 5 层叠 + 排版 | **后台** | 多章并行；同一 `(章, LayoutKey)` 去重 | 单章或单块 | 走 `Measure` 端口，见下面那条依据 |
| 6 切片（页 / 栏 / 可见带） | **界面，帧内** | — | — | 纯几何、便宜；放后台要为每个滚动事件回传一次视口参数 |
| 7 shaping | **后台预取**（见 10.3） | 多行并行 | 单行/单页 | 缓存键不含宽度，所以预取的成果不会被拖窗口作废 |
| 8 绘制 | **界面** | 否 | — | 需要 `&mut Window` |
| 位置落库 | **后台** | — | — | 界面只发信号，**跨行才写一次**，去重放在发送侧 |
| 批注回显的 relocate | **后台** | 是 | 整批 | 打开书时批量解析；不许在渲染路径里逐条做 |
| 封面字节抽取 / 缩略图解码 | **后台** | 多本并行 | 单本 | 解码在后台，**纹理上传回界面线程**（图像资源不能跨线程创建） |
| 全文搜索 | **后台** | 按章并行 | 单章 | 进度 + 可取消，形状与导入同构 |
| 导出批注 | **后台** | 否 | 整次 | 活小，但别在界面线程拼大字符串 |
| 目录定位 / `id → 偏移` 索引 | **后台** | 否 | 整次 | 属于导入产物；开书只是读表 |

**"排版能离屏"不是假设，是现状**：`Measure` 端口的实现持的是 `Arc<WindowTextSystem>`，而第 5 级在后台调
`run_metrics` 走的就是它。所以把 shaping（第 7 级）也放后台预取，用的是同一条已经验证过的通道；
不能离屏的只有 `paint_glyph` 那一层，因为它要 `&mut Window`。

### 10.3 作业的形状：合并、丢弃、优先级

**合并（coalescing）**：同一 `(章, LayoutKey)` 只允许一个作业在跑；后来的请求**覆盖待发的那个**，
而不是排队。反例很具体——读者拖一下字号滑条会产出几十次请求，排队的结果是界面停在半秒前的字号上。
注意"在跑"的那个不必取消，让它算完，只丢请求，因为结果本身无害。

**丢弃陈旧**：每个作业带回**它算的那一把 `LayoutKey`**，界面线程比对当代，不等就丢。这条让
"提交在界面"落地成一行比较，而不需要任何锁。后台作业不必知道结果会不会被用。

**优先级从高到低**：可见带的 shaping → 邻章排版预热 → 更远章节的冷预热 → 后台写库与缩略图。
理由是等待成本：第一档差一帧就看得见，最后一档晚两秒无人察觉。

**并发上限**：跨章并行没问题（各读各的条目、各自不可变产物）。同一本书的作业总数封顶
（比如同时不超过 4 个），否则一次"打开一本千章书"会把线程池占满，导入作业会饿死。

### 10.4 三件挪线程解决不了的事

它们不是"放错线程"，是形状本身要改，列在这里免得有人用挪线程去试：

1. **一把数据库连接锁被界面与所有后台作业共用**。界面读会排在一次写后面；更糟的是**锁内做了文件系统
   操作**（取文件元数据、提交后的空间回收），等于让界面线程等一次 IO。解法是读写分道 + 锁内不碰 FS，
   与线程分配无关。**2026-10-13 改了一半**：开书那条路上的 `Store::stale_reason` 现在锁内只问一句
   SELECT，`std::fs::metadata` 出锁再叫（那把守卫在作用域块结束时就放了）。
   **还剩两处**：① 提交后的空间回收仍在锁里——`save_flow` 持着 `conn` 调 `reclaim`
   （`store/content.rs:118` → `store/mod.rs:210` 的 `PRAGMA incremental_vacuum`，它会真动库文件）；
   ② **单一连接锁本身没动**，界面读仍排在一次后台写后面（读写分道是另一件事，见
   `plans/基础设施.md`）。这两条都没计数门——一次开书一次 stat、一次落库一次回收，
   插计数器就是量具自己变成被测量的开销（`infra::metrics` 模块头那条纪律），所以靠结构保证。
2. **任何配置变更都触发监听服务重启**，而"停旧服务"同步等待一轮 tick（一秒内）。解法是只在监听相关
   那几项真变了才动，且"停"这一步本身挪后台——不是把重启挪后台就完事。
3. **书架每次按键查一遍库并重建全部卡片**，网格没有虚拟化。解法是查询去抖 + 只重建可见卡片。

### 10.5 后端没有线程概念

后端不判断自己跑在哪个线程（它没有线程这个概念）。所以"不许在界面线程做 IO"这条只能由作业划分来守。
后端要保证的是一件不同的事：**任何一次调用都不需要"当前线程"这个信息**，这样调用方把作业挪到别的线程
时后端一行都不用改。跨线程只传 `Arc`，不传锁；后台结果通过事件流回会话，会话决定何时换代。

### 两阶段排版：量完之后不接（2026-10-12）

数字摆在一起就清楚了。整章 13200 行 / 379200px 高，视口 800px：

| 做法 | 开章 | 之后滚动一整章 |
|---|---|---|
| **现行**（全量排一次 + 二分窗口） | 127 ms | **0 ms** —— 行盒都在手上，滚动只是两次二分 |
| 两阶段（量高 + 按带渲染） | 6.95 + 0.43 ms | 0.43 ms × 约 474 条带 = **约 204 ms** |

**两阶段的 6.95+0.43 是「开章」的钱，不是「滚动」的钱**：文档里那个 19× 是拿它跟
「完整排版」比，而完整排版在现行路径上**一章只做一次**。两阶段快在「不为看不见的
部分建行盒」，代价却是**每滚一屏都要重排那一条带** —— 整章累计下来比一次性排完更贵。

而现行路径并没有在滚动上花钱：`layout_key` **不含滚动位置**，所以滚动不触发任何排版，
可见带之外的行不进绘制单元（差额表第 4 条那条二分已经接了）。

更要紧的一条：**排版跑在后台线程**（`typeset_queue()` 那只单线程池），所以那 127 ms
不阻塞界面；而读者真正高频触发的「改字号」走 `BlockCache` 只要 **5.6 ms**。
两阶段想省的那笔钱，块级缓存已经用另一种方式省掉了 —— 而两阶段**绕过 `BlockCache`**
（它缓存的是整章的块级产物，与「只排一条带」不是同一种形状），接上去反而会把
5.6 ms 那条路弄丢。

**结论：不接。** 保留 `measure_chapter` / `render_window` 作为 core 侧的一条可选路
（已测、已有门），等出现「必须只排一部分」的场景再接 —— 例如超大单章且
`BlockCache` 命中不了，或者竖排那类需要不同推进轴的场合。

判据留在基准里：`cargo run -p folio-core --example bench-layout` 现在多打一行
「两阶段 · 滚动一条带」。下一轮要重新决定时，跑它一次就能把三条数放在一起比。

这些是**计时**，所以只当参照，不当验收 —— 验收一律是计数（下面那张表的每一行）。
计时在这台机器上被调度噪声牵着走（`plans/layout-optimization.md` §5.3 实测 ±20%），
而「重排了几块」是个确定的整数。

  misses 增量 1、hits 增量 2」，并附带比对「增量结果与不缓存实排逐行相同」。所以第 3 步不是先补量具，
  是直接接线。
- 取字节那一侧已经立好：`folio_core::metrics` 的 `ContainerOpens` 与 `EntryNameTablePasses`
  （线程局部给测试、进程全局给诊断 dump），`format/zip.rs` 有「一次 open 只扫一遍条目表」的绿断言，
  `format/epub/tests.rs` 那条「一百次取图只该开一次容器」**已经转正成守门员**（2026-10-13 核对：
  不再挂 `#[ignore]`，全量跑绿；原稿写的「今天跑它是 `left: 100, right: 1`」是它被接上之前的状态）。
  同口径的还有 `format/container.rs` 与 `format/zip.rs` 各一条。**但第 5 步的 `Address` 直读并没有因此落地**
  ——门数的是「开几次容器」，`Container` 的开一次 + 带锁共享就把门满足了，锁那一半还欠着（见 §十一 第 8 条）。
- **呈现层这一侧（2026-10-13 新立）**：`Metric::SceneRebuilds` / `SceneRuns` / `ShapeLineCalls` 三格，
  记在 `scene.rs` 的构造收尾与 `paint_run` 的 `shape_line` 前。`SceneRuns` 用**新加的 `Metric::add(n)`**
  一次构造记一笔（逐 run 记违反模块头那条纪律：量具自己会变成被测量的开销）——`add` 有自己的单元测试
  `add_accumulates_into_the_same_slot_as_count`，钉它落进同一个槽位、且 `add(0)` 什么都不留。
  门两条配对：`view::tests::a_scrolled_frame_currently_rematerializes_the_visible_runs`（绿，实测基线
  **5 次重建 / 62 个 run / 62 次查表**，同时是「量具不是空转」的那面 detector）与
  `scrolling_back_to_the_same_band_materializes_no_new_runs`（`#[ignore]`，今天跑它 `left: 62`）。
  **这一条改过一次口径**：初版把它写成「往前滚一屏增量为 0」，那是钉一件本不该发生的事——单元表按行
  懒物化，新进入视野的行第一次被画就要建它。判据只能用**往返**：滚下去、再滚回走过的地方，第二趟
  才是那个确定的 0。往返只用一屏的量是为了待在同一个锚章的 ±2 窗口里（走远了整个 `Document` 被裁掉，
  那次重新物化是对的，不该记在「还没接」这笔账上）。`ShapeLineCalls` 不进这条门，理由见 §九 的「可省」。
- 应用侧那条**已经补上**（原先写「仍然缺」）：`Metric::DomParses` 在 `Dom::parse` 里记数，
  `document::tests::a_preference_change_reparses_nothing` 数的是「改一次字号 → 增量为 0，
  换一章 → 增量恰好 1」。**「重新层叠次数为 0」这条仍然没有**，它要等第 6 步把 `cascade`
  拆成匹配 / 层叠两段才写得出来——在那之前改字号**确实**要重跑一次层叠，那是设计允许的。
- 计数断言的读法统一是 `take_local`（读过即归零），所以断言的是**增量**而不是进程总量；
  线程局部这一点由 `metrics::tests::counts_are_per_thread_so_parallel_tests_do_not_pollute_each_other`
  钉住，因为 cargo 默认并行跑测试。
- **第 4 步的验收换了口径，得说明白**：原写「`block_of_line` 的线性扫次数为 0」，那是能数的，
  但数它要在**每行每次**的查询里插一个计数器 —— 与「每张图每帧一条 `info!`」是同一种错误，
  量具本身变成被测量的开销（`folio_core::metrics` 模块头那条纪律）。所以这一行改成的
  **结构 + 等价**两问：① 索引在每次组装时都折好（`Layout::assemble` 是构造 `Layout` 的唯一入口，
  私有字段让「拼字面量绕过折表」编译不过）；② 折表与二分对每一行、每一条 y、每一条带都与
  接线前那句线性扫同答案（`layout/tests/index.rs`，参照实现 `geometry::scan_reference` 是照抄的
  旧代码，只在 `cfg(test)` 里编译）。等价测试不会因「把索引拆掉退回线性扫」而变红 ——
  两条规则定义相同，这本来就不是快慢的证明，而是**口径没漂**的证明；快慢那部分留在 bench 里看。

第 1 步与第 6 步之间不要跳：跳过的后果不是变慢，是**改完无法证明改对了**，于是三个月后没人敢再动这块。
