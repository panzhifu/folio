状态：**计划，未动工**。前置三批凭证都在 GitHub 那头，不在代码里（见 §〇）：public

## 〇 双仓发布：软件公开，源码不公开

实测过的事实：**未登录的 GitHub API 读不到私有仓库的 release**。`api.github.com/repos/panzhifu/folio`
现在回 404（仓库私有），而 GitHub 没有「仓库私有但 release 公开」这一档 —— Releases 页和
资产继承仓库可见性。所以「代码不公开、软件公开」只有一个形状：

| 仓库 | 可见性 | 放什么 |
|---|---|---|
| `panzhifu/folio` | private（现状不动） | 源码、`ci.yml`、`release.yml`（构建在这跑，才读得到源码） |
| `panzhifu/folio-releases` | **public，待新建** | 只有 release：安装包、`sha256sums.txt`、CHANGELOG 正文 |

`release.yml` 推产物与 tag 到 public 那个仓，App 只读 public 那个仓。于是：

- **限流按用户自己的 IP 计**（匿名 60 次/小时），不是全队共享一份配额 —— 一次手动检查用掉一次，够用。
- 不需要 `update.json` 那类自建索引：`releases/latest` 一个请求已经把「最新版本号 +
  更新日志正文 + 资产清单」三件事都给全了。校验依据走随 release 发布的 `sha256sums.txt`，
  代价是检查到新版后多一次 GET，好处是不用手工维护第二份版本清单（第二份一定会漂）。

要在 GitHub 那头先做掉的四批事（我做不了，也需要你确认口径而不是我替你建）：

1. 建 `panzhifu/folio-releases`（public，空仓即可，release 由 CI 写进去）。
2. fine-grained PAT：只授权 `folio-releases` 一个仓的 `contents: write`，存成 private 仓的
   secret（默认 `GITHUB_TOKEN` **碰不到别的仓库**，这是跨仓发布的唯一路）。
3. Android keystore：本地 `keytool -genkeypair`（RSA 2048、有效期 25 年、alias 自定），
   keystore 文件 base64 后连同口令存 secret。**keystore 丢了 = 已装过的那批用户永久收不到
   任何更新**（签名对不上只能卸载重装），这条没有技术兜底，只有备份。
4. （可选）站点部署凭证 —— §三 Linux 那档要不要真发 `xdg-email` 的附件与此无关，先列着。

## 一 自动更新

### 数据源与比较

`crates/folio-core/src/net/update.rs`（新文件，**不含任何 gpui 类型**，与 `net/remote/`
同一条边界：core 只管「该发什么、回来的东西怎么读」）。

- GET `https://api.github.com/repos/panzhifu/folio-releases/releases/latest`，
  `Accept: application/vnd.github+json`，走已有的 `remote::Transport`
  （`net/remote/ureq.rs`：同步、15s 连接超时、UA 已经是 `folio/{CARGO_PKG_VERSION}`）。
- 读 `tag_name` / `body` / `assets[]{name, browser_download_url, size, digest}`，与
  `env!("CARGO_PKG_VERSION")` 比。比的是 **semver 三元组**，不是字符串：`v0.1.10` 比
  `v0.1.9` 新，字典序在这儿会判反。`v` 前缀、预发布后缀（`-rc1`）都要吃得下。
- 错误分三档，不糊成一团：连不上（DNS/TLS/超时）、被拒（403 限流，有明确的一句可说）、
  没发过 release（404，含义是「还没人发过版」，与「坏了」不同）。
- 资产按端挑：安卓只认 `folio-<ver>-arm64-v8a.apk`。挑不到就是「这一端没有可用包」，
  不许退化成随便挑一个下载。
  - `assets[].digest` 是 GitHub 现在直接给的 `sha256:…` 字段。有它就不必再取
    `sha256sums.txt`；**这一条要先实测**（本仓还没有过 release，字段在无认证请求里的可见性
    没量过）。取不到再退到那份 sums 文件。

### 两步，不是一步

**检查**与**开始下载**分两个动作。包体按实测的 debug 包 36 MB 量级估（release 更小），
移动网络下「点一下检查」不该直接开始吞流量，所以检查回来先报体积、由读者确认再下。
开机自动检查**默认关**：一份默认开的后台出网行为，读者第一次发现时往往是负面的。

### 安卓那一端：真把装上

链路八步，前三步纯 Rust，后五步要在 Java 侧落一个方法：

1. 检查 → 有新版 → 报体积 → 读者确认。
2. 下到 `cache/apk/`（`Transport::download` + `Sink`，跑在 `infra::task` 线程池上，
   回界面的那套照 `shelf/view/mod.rs:602-655`：`background_spawn` 泵 `mpsc` → `cx.spawn` 落
   `this.update`，**不要在下载线程碰界面**）。
3. 算 SHA-256 比对（`sha2` 已是 workspace 依赖，`ingest/identity.rs:19` 已在用，**不引新依赖**）。
   不符就删文件、报「包不完整」，不许「大概对得上也拉一下安装器」。
4. 查 `PackageManager.canRequestPackageInstalls()`。
5. 未授权 → 跳系统「允许安装未知应用」页（`ACTION_MANAGE_UNKNOWN_APP_SOURCES` 带本包 URI），
   回来**不自动续跑**，提示读者再点一次 —— 授权是系统页回来的异步事，自动续跑会撞上
   「还没生效」那一档，看起来像坏了。
6. FileProvider 出 `content://` URI。
7. `ACTION_VIEW` + `application/vnd.android.package-archive` +
   `FLAG_GRANT_READ_URI_PERMISSION`，交给系统安装器。
8. 读者点安装。装完进程被系统杀掉是**预期**，不做「装完自动重启」。

要动的三处非 Rust 文件：

- `AndroidManifest.xml`：加 `REQUEST_INSTALL_PACKAGES`（这一条 Play 会盯，但本仓不发 Play）。
- `res/xml/file_paths.xml`：现在**只**放行 `<cache-path name="share" path="share/"/>`，
  要补 `apk/` 那一档，否则 FileProvider 抛 `IllegalArgumentException`（是安全设计，别绕）。
- Java：`GpuiSystemUi.java:121-146` 那条 share 流程的姊妹方法。Rust 侧走 JNI（同
  `platform/android.rs:272` `share_image`），**只能界面线程调**。
  - `gpui_mobile::url_launcher` 做不到这件事：它带不了 MIME type、flags 与 FileProvider URI。

### 其他三端：只提示

弹一张卡片：「发现新版本 vX（当前 vY）」+ 更新日志 + 两颗按钮（打开下载页 / 复制下载地址）。
`platform::open_folder`（`platform/mod.rs:162-196`）旁边要新增一条同层的 `open_url`：
桌面 `xdg-open` / `open` / `explorer`，安卓递 `launch_url`，iOS 与 HarmonyOS 返回 `false`。

**桌面不做「下一份包再顺手装」**。理论上 Linux 装了 deb/rpm 可以让包管理器接手，macOS 的
裸 zip 就没这条路 —— 只给某一端开一键更新，比所有端都没有更容易让人困惑。这条写死。

### 一条无法回避的破坏性事实

现在装在各台设备上的包是 **debug 签名**。换成 release 签名后，系统判「签名不一致」而**拒绝覆盖
安装**，第一次必须手动卸载。这条绕不过（同一条签名规则正是自动更新能覆盖安装的前提），
只能写进 README 与 release 正文。

## 二 更新日志

- 正文就是 §一 那次请求返回的 release `body`，**不另设第二份文案源** —— 改 GitHub release
  就够，代码里不留副本。`CHANGELOG.md` 是唯一的手工来源，CI 把最新一段搬进 release 正文。
- 「更新日志」这一格**独立可点**：显示**当前装着的这一版**对应的那条 release，不必先走
  「检查更新」。读者要问的是「我手上这版改了啥」，这两件事在界面里不该绑死。
- 弹层复用仓库自己的 `ui/components/bottom_sheet.rs`（移动），桌面那侧用居中卡片。这一版
  **刻意不用 gpui-kit 的 `component::Sheet`**，理由已经写在那份文件头注释里（进入动画写死、
  没有退场），新弹层没有理由破这个例。
- Markdown 只按「标题 / 项目符号 / 普通段落」三档落版，其余原样当文本。
  `content::format::markdown` 已在依赖图里，够不够用要等真跑一段 release 正文再判，
  不为这块弹面单独引渲染器。
- 取不到（离线 / 限流 / 没发过版）：卡片里一句「暂时取不到」+ 打开 releases 页那颗按钮。
  不许显示空白卡片，也不许显示上一版的缓存正文 —— 让读者以为那是当前的。

## 三 日志反馈

日志文件**已经存在**，这一件事不是建设施，是给读者一个出口：
`infra/logging.rs:186` `log_file()` → `<data root>/logs/folio.log`（带轮转，
`paths.rs:135` `log_dir()`），`ui/services/storage.rs:296` 已经在解析这个路径 —— 复用。

- 先做一份快照（当前日志 + 必要时最近一份轮转），命名
  `folio-log-<版本>-<平台>-<时间戳>.txt`；正文头部带上**版本、平台、界面语言、配置根与数据根
  两条路径**，省得读者手抄这几样 —— 排障时缺这几样的一条反馈基本要来回问。
  **那两条路径都要给，不是只给数据根**：桌面上配置根（`~/.config/folio`，`config.json` 与
  `themes/` 在那儿）与数据根（`~/.local/share/folio`）是两个目录（`paths.rs:95-117`），
  而「存储」那一屏只报数据根 —— 这一条正是关于页撤掉「配置文件在哪儿」那一格之后，
  读者还能拿到配置根路径的地方（见 §界面落点）。
- **安卓**：走已有的系统分享面板。`platform/mod.rs:132` 那条 `share_image`（cache →
  FileProvider → `ACTION_SEND`）对文本文件完全适用 —— 一般化成 `share_file(bytes, mime, name)`，
  图片调用方行为不改。`HAS_SHARE_SHEET`（`platform/mod.rs:123`）那条判据同步复用。
- **桌面**：一次点击同时三件事 ——
  (1) 日志副本落到读者找得到的地方（复用 `host/desktop.rs:74` `write_to_downloads`）；
  (2) 拉 `mailto:` 草稿，主题带版本与平台，正文写清「请手工附上这个文件」与它的完整路径；
  (3) 界面给一句提示，并把**文件路径**（不是整篇日志）送进剪贴板
  （`selection.rs:640` 那条 `cx.write_to_clipboard(ClipboardItem::new_string(…))`）。
- **桌面做不到的一件事，写在这免得日后当 bug 修**：`mailto:` 按 RFC 6068 **不能带附件**；
  而「把文件当文件对象放进剪贴板、直接粘进邮件附件框」也做不到 —— `gpui` 的 `ClipboardItem`
  只有文本，那是 Windows `CF_HDROP` / Linux `x-special/gnome-fs-list` 那一档格式。
  Linux 上探到 `xdg-email` 时改走 `--attach`，那是唯一真能带附件的一档，其余两端只能手工附。
- 收件地址进配置（可覆盖），默认 `noke601508@outlook.com`。

- Windows 安装器要钉死 `UpgradeCode` / 产品 GUID，否则每次 CI 出一个新包，读者装的是并存
  两份而不是升级。

- ureq 2.12 的默认跳转上限是 10 次，GitHub 资产那个 302 → `objects.githubusercontent.com`

## 五 License：MIT 那串留着，源码继续私有（已决）

决定：**不改许可**。`Cargo.toml:10` 的 `license = "MIT"` 原样留着，不写专有 `LICENSE` 文本；
软件按 §〇 双仓公开**发布**，源码继续私有。

**先把上一版记错的事实订正掉**（它改变了这一节的形状）：本仓根目录**没有 `LICENSE` 文件**，
`SECURITY.md` 与 `CONTRIBUTING.md` 也不存在，README 里根本没有许可那一节。唯一的许可声明是
`Cargo.toml:10` 那串，两个 crate 靠 `license.workspace = true` 继承，`publish = false` 两处都在位
（`crates/folio-app/Cargo.toml:7`、`crates/folio-core/Cargo.toml:7`）。

- **所以代码层面这一节无事可做**：MIT 那串 + `publish = false` + 仓库私有，三者并存的结果是
  **外部读者看不到那串 MIT** —— 它今天不构成对任何人的承诺。要留一句防自己日后误读的话就够：
  README 加一小节「许可与发布」：MIT 声明在 `Cargo.toml`，**源码当前不公开**，二进制在
  `folio-releases` 发布。这一句同时把 §〇 的双仓形状对外说清，读者不至于在仓库找不到源码时
  以为链接坏了。（若哪天把 `Cargo.toml` 或源码包随 release 一起发出去，那串 MIT 就变成对外
  声明 —— 那天要重新看这一节。）
- **保留下来必须做的还是那件事，而且它与本软件走什么许可无关**：第三方依赖的 MIT /
  Apache-2.0 / BSD / MPL 许可证在**二进制分发**下要求在发行物里附带版权声明与许可文本。
  这一条不因为「你的代码私有」而消失，也不因为「你挂着 MIT」而自动满足。所以仍要做：
  - 生成 `THIRD-PARTY-NOTICES.txt`：本机**没装** `cargo-about` 也没装 `cargo-license`
    （本轮 `which` 量过），要 `cargo install cargo-about` 配一份 `about.toml`。
    不自己写那份解析器 —— 同名多版本、双 license 取哪一条这些判定面正是容易悄悄错的东西。
  - 随四端安装包进包：deb/rpm 的 `%doc`、tar 的 `share/doc/folio`、macOS `.app` 的 `Resources`、
    Windows 安装目录、APK 的 `assets/`；并在设置 → 关于给一格离线读它。
    **这一格正是 `about.rs:6-8` 那句注释里说的「许可证那一组」** —— 那句现在写的是
    「本应用还没有更新检查与授权子系统」，§界面落点 与这一节一起把它改掉。
  - 生成表出来后**人工过一遍 copyleft 那一档**（GPL / LGPL 的强 copyleft、MPL 的文件级
    copyleft）。撞上只能用源码形式满足的依赖，要么换掉它，要么单给它提供源码。
    **这是发布闸门，不是备注。**
    - **为什么是生成表而不是靠记忆，这里现留一个实例**：我上一版随手举「`resvg` 是 MPL-2.0，
      所以有文件级 copyleft」，实测 registry 里 `resvg-0.46.0.crate` 的 `license` 写的是
      `Apache-2.0 OR MIT` —— **举错了**。这类凭印象的许可判断正是这一档最容易悄悄错的地方，
      所以判定只认 `cargo-about` 从 `Cargo.lock` 现生成的那张表。
- **`reference/` 那条 ignore 要守住**：`.gitignore:28` 的 `/reference/` 里躺着 KOReader 与
