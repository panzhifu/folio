## 一、后台作业

### 1.1 一条队列，不要三条

现状是三套并存的管道：`folio_core::task::TaskManager`（std 线程 + mpsc）、应用侧的导入事件总线
（`ui/shared/import_queue`）、以及界面里各自 `spawn` 的作业。三套都能干活，于是每一处都要自己决定
用哪套，而取消、去重、进度这些能力在三套里的成熟度不一样。

统一形状只保留一个：**后端定义作业与事件，界面只在收事件的地方活着。**

```rust
// 后端侧（folio_core::task，已存在）
pub struct TaskManager<R> { .. }   // 线程池 + 队列；Drop 即关停（task.rs:264-266）
pub struct StageCtx { .. }         // 报数与看取消的把手，非泛型（dyn Source 里写不出泛型）
pub enum TaskEvent<R> {            // task.rs:53-64
    Started,                       // 被工作线程取到（排队阶段没有事件）
    Progress(ProgressEvent),       // 逐本 / 逐条读数
    Bytes(ByteProgress),           // 字节级读数，与 Progress 互不覆盖
    Finished(Result<R, TaskError>),
    Cancelled,
}
```

作业分四类，**优先级从高到低**，这是防饥饿的唯一手段：

| 类 | 例子 | 上限 |
|---|---|---|
| 交互 | 当前可见带的排版、shaping、命中 | 每本书同时在跑的作业数封顶（建议 4） |
| 预热 | 邻章与更远章节的取字节 + 解析 + 匹配 | 同上，可被交互作业抢占 |
| 落库 | 位置写入、批注写入、统计累计 | 串行一条即可 |
| 清理 | 缩略图重建、孤儿文件回收、重索引 | 低到"界面空闲才跑" |

反例很具体：打开一本千章的书会把线程池占满，导入作业饿死；批量导入 5000 本会让滚动掉帧。
两类共用一个池而不分队列，就一定互相拖累。

**但「一条队列」不等于「一只池」**，这是第五件要钉住的事。界面上只有**导入这一侧**用进程级那只池
（`folio_core::services`，监听 / 传书 / 手选 / 整机扫描都提交到这里）；**排版跑在自己那只单线程队列**上
（`ui/features/reader/document.rs` 的 `typeset_queue()`）。理由不是性能，是队列的形状不一样：
排版要的是「后一笔盖掉前一笔」（键相同就不重发，`pending` 只留一格，见 1.2 第 3、4 条），
批量作业要的是排队与封顶。代价必须说清楚：**上面那张四档优先级表管不到排版**，
所以「导入饿死滚动」这一对目前是靠两只池各跑各的挡住的，不是靠分档；而四档里真正有人用的
只有 `Persist`（导入）与 `Prewarm`（扫描），`Cleanup` 至今零调用点。哪天把排版并进
`Interactive` 档，要同步改这一条，否则文档与代码会说两套话。

### 1.2 五条作业纪律

1. **界面线程不许阻塞**，唯一例外是开书时那一次库查（等一次 SELECT 比等一次解压便宜）。
2. **计算在后台，提交在界面**：结果在后台算，采用哪一代由界面线程决定。半代状态比卡顿严重。
3. **作业带回自己那把键**（`LayoutKey` / 书的 `Address` / 章节 ID），界面比对当前代，不等就丢。
   这让"陈旧结果丢弃"落地成一行比较，不需要任何锁。
4. **同键的待发请求合并覆盖，不排队**（读者拖一下字号滑条就产出几十次请求）。在跑的让它算完，
   只丢请求，因为结果本身无害。
5. **取消检查点放在单元之间**（章与章、书与书），不放在一次函数调用中间。取消时**已经落库的那些是真的**。

### 1.3 生命周期

- 常驻服务（监听、传书）与作业池**不是一个东西**：服务是往队列塞活的驱动者，不是作业的一部分。
- **关停的语义是"跑完已排的"而不是"立刻停"**：`TaskManager::shutdown` 是幂等的，它不再等新活，
  但**把手上与队里已经排着的作业全部跑完**再回收线程（`task.rs:246-249`、`264-266`）。
  这带来一个必须写进关闭顺序的坑：**退出时若导入队列里还排着 5000 本，`Drop` 会等完它们。**
  所以关闭顺序必须是「先取消 / 停止投递 → 再关停作业池」，而不能只靠 `Drop`。
- 作业池必须**在数据库连接关闭之前**销毁，否则后台线程会拿着已失效的连接写。
- 退出时要 flush 的只有两样：**位置**与**配置**。两者都必须已经走"合并 + 节流"，所以退出路径上
  不该有等待数秒的事情。如果退出时能感到卡顿，八成就是上一条那个"关停会排干队列"。
- **不要在关闭时留下半成品**：临时文件与 `.part` 这类中间态在启动时扫一遍清掉（这条与导入管线里
  "库里只可能有 `.part`，不可能有半成品"是同一件事的另一半）。

## 二、配置

配置这件事只有三个需要规矩的地方：**谁读、谁写、写坏了怎么办**。其余都是细节。

### 2.1 三层来源，字段级合并

优先级从低到高：**内置默认 < 用户配置文件 < 环境变量覆盖**。三条必须钉住：

1. **合并粒度是字段级，不是整段替换。** 否则只想调级别的一条环境变量会把用户在配置文件里设的
   日志出口、大小上限、保留份数一起抹掉。
2. **每个键要知道自己来自哪一层（provenance）。** 这是"我明明改了配置怎么没生效"这类事故唯一的解药。
   诊断入口必须能打印：生效值 + 来源层 + 被谁覆盖。没有 provenance 的三层配置比一层更难查——
   你多了一个看不见的可能来源。
3. **写回只写用户层，绝不把生效值整体烤回文件。** 这是最容易做错、后果最实在的一条：很多实现保存时
   写"当前生效的完整配置"，那等于把环境变量的值和默认值**固化成用户的选择**——用户调过一次环境变量，
   之后所有默认值的升级都对他失效，而这个决定他从未做过。

内置默认必须在代码里存在（`Default` 实现），不能只存在于一份示例文件：否则升级时新增字段无处取值。

两条**不要加**的建议：

- **不加第四层「系统/设备默认」**（跟随系统深色、跟随系统语言）。把它做成用户层的一个取值
  （`"system"`）而不是独立一层：四层字段级合并的诊断成本上一个台阶，而收益只是少一个 `if`。
- **不加命令行层。** 桌面 `--data-dir` 看着方便，但 Android 与鸿蒙没有 argv，最终会写成
  "桌面有第三种来源、移动没有"——那正是配置代码开始分叉的地方。

环境变量的数量控制在 3–5 个：数据根、日志级别/过滤器、日志总开关、以及一个"忽略配置文件"的应急开关。
**每多一个环境变量，"用户配置没生效"就多一条隐蔽成因。**

实现上不引入通用多源配置框架：三层字段级合并 + provenance 手写就是一个函数，而框架会带来自己那套
合并语义（又一处要学的规则）和一条新的依赖树。

### 2.2 形状：后端管数据与 IO，界面只管通知与调度

```
后端（folio_core::config，已存在）
  Config 结构 + Default + normalize/clamp + load(paths) + save(原子写) + update(F)
界面
  一个实体持 Arc<Config>；唯一职责是"变了通知谁"；落盘调度（去抖）在这里
```

配置的全部价值在于**校验与字段定义放在一起**：夹取规则、默认值、版本兼容、原子保存都该在后端，
否则后端退化成一个谁都能写出非法值的裸结构体；而放进后端之后，那些脱离窗口的测试才真的覆盖到它们，
桌面与移动也共用同一份。

要切的一刀是：**后端没有"通知界面重画"这个概念**，所以订阅与调度留在界面。

两个细节：

- **写入口要在类型上强制，不靠约定。** 不要暴露 `&mut Config`。给
  `update(|c| c.font_size = 22)` 这样的口，内部**必然**跑 `normalize`、必然推版本号。漏掉夹取的后果是
  "文件里存着一个 900 的字号"，而界面下次读出来直接用。
- **去抖与何时落盘留在界面，后端只提供同步的原子写。** 去抖涉及时间与线程，后端不该 sleep
  也不该 spawn 线程（后端没有线程概念，见 `plans/阅读管线.md` 的 10.5）。

今天界面侧读配置走 `ConfigHolder`（`ui/shared/config_model.rs`），这个形状是对的；要补的是
"写只有一个入口"这条——散落的写入会让去抖与原子保存无处施力。

### 2.3 启动读一次磁盘；变更换 Arc，不改内容

**配置文件在启动时读一次、归一化、此后运行期永不重读文件。** 反对重读有三个具体理由：与自己的写入
竞态（刚 rename 完就有别处重读，会拿到旧 inode 或半新状态）；外部手工编辑会把半套值突然吞进来
（正在滚动时界面一半新字号一半旧字号，比"改动没生效"糟得多）；以及根本不需要——要查生效值走诊断入口。

但"读一次磁盘"不等于"取一次值就撒手"：字号一改阅读界面必须重排。正确的分发形状是
**持 `Arc<Config>`，变更时换整个 Arc**：

```rust
fn update(self: &Self, f: impl FnOnce(&mut Config)) {
    let mut next = (*self.current()).clone();
    f(&mut next);
    next.normalize();                 // 夹取，不可跳过
    self.publish(Arc::new(next));     // 换代；仍持旧 Arc 的一方继续用旧值
}
```

这个形状给三样别的方式拿不到的东西：

- **一帧之内一致。** 一帧里多处去读一个可变配置而中间有人改了它，会画出"标题旧字号、正文新字号"的
  撕裂帧。持有同一个 Arc 的 clone 就不可能撕裂。顺带解释了一件现状：每帧整份 clone 偏好
  （含字符串的那一大坨）正是在**用昂贵的手段要一致性**——Arc clone 是一次原子递增，同一个需求两种成本，
  换成 Arc-swap 之后深拷贝就没必要了。
- **后台作业的输入天然不可变。** 把 `Arc<Config>` move 进作业即可，这正是 1.2 第 3 条纪律
  （作业带回自己那把版本/键，界面比对不等就丢）的前提，两处是同一套机制。
- **换错了能退回去。** 旧 Arc 还在别人手里时不会出现半个新状态。

各处怎么拿：那个实体持 `Arc<Config>`，别的界面**订阅它的换代**，需要值时 clone Arc。
**不要做"全局可变配置槽"**——那等于把一致性和通知两件事都推给纪律去守。

### 2.4 热生效与重启生效，必须标在字段旁

| 生效时机 | 项 | 理由 |
|---|---|---|
| **热生效** | 字号、行距、字体、主题、边距、栏数、翻页动画、目录样式、语言 | 改完不动等于功能坏了，读者会立刻试 |
| **重启生效** | 数据根、库文件位置、日志级别与三个出口、监听服务的目录与节奏 | 要么在启动早期就被消费掉（日志），要么改一次等于换一个服务（监听） |

这个分类**写在字段旁边**，不能靠散落的 `if` 记着。两头都会错：热生效的项漏掉通知，症状是
"改了没反应"，会被报成 bug；重启生效的项被误做成热生效，症状是"当场没生效、重启才对"，也是 bug 报告。
只有字段上的标注能一眼看出哪个是设计、哪个是漏。

**实测的一处不符（2026-10-12 核对，接线排版失效键时撞见的）**：`Reader.paragraph_gap_em`
（设置面板「段间距」那格滑条）**当时没有任何消费者** —— 全仓库只有它自己的默认值、`validate` 里的
夹取，和面板那两条读写。段落间距实际来自 `css/ua.rs` 按 em 硬算的 `margin-bottom`。
按生效时机那张表它属于热生效，所以这不是"还没做"，是"界面说有、后端没有"——正是本节说的那类
会被报成 bug 的漏。（它同时**会**让排版失效键换格，因为整份 `Reader` 都进哈希，所以表现是
"白重排一次、版式纹丝不动"。）

**同日已接上**，走的不是改 `ua.rs` 的硬值，而是**读者层规则**：`Document::reader_rules` 拼一条
`p { margin-top: Xem; margin-bottom: Xem }`，以 `Origin::Reader` 进层叠。选这一层的三个理由：
`margin` 不是继承属性，挂在根样式上穿不到 `<p>`；`Origin::Reader` 在层叠里位于作者层之下
（`css/mod.rs` 的 `CascadeLevel`），所以书自己声明了段距时仍按书的，与浏览器一致；
`ua.rs` 那一对 1em 保留为「没有这条规则时」的兜底。
接线的几何代价要说死：默认值 0.75 生效之后，每段的上下外边距从 1em+1em 变成 0.75em+0.75em，
**每段少 0.5em 的空白**。界面侧两处按旧几何标定容差的用例同日跟着改了 —— 一处把段距显式钉回
1.0（`reader/view/tests.rs` 的 `prefs`，因为那些用例量的是坐标换算不是段距），一处补了一格滚动
（原来"刚跨进第二章"那一刻的章内偏移是 0，章高一变就证不了「重排过」）。**这类接线翻出来的旧
假设是接线的一部分，不是副作用**。

同一把尺子量出来还有两处（2026-10-12 补）：

- ~~**`Reader.justify`（面板「两端对齐」）动不了版式**~~ **已接**（2026-10-16）：`Justify`
  不再落 `_ => 0.0`，而是由 `layout::collect::justify_plan` 按行的剩余宽度把余量摊到行内的
  隙上（有空格拉空格、否则拉字间），末行与 `<br>` 行不对齐、RTL 一期不做。落点写进
  `LineBox.justify`，绘制（`paint::GlyphRun::glyph_shift`）与命中/选区
  （`hit::hit_test` / `rects_for_range_in`）按**同一句规则**逐字右推。分类表因此把
  `justify` 从 `NotWired` 提到 `Layout`，那条门也顺势收进了 `ink_width`（对齐不改
  `x`/`width`/行数，只看前三格会假绿）。
- **目录那三项**（`toc_density` / `toc_max_title_lines` / `toc_dim_read`）**会换排版失效键**。
  整份 `Reader` 进哈希，所以改一次目录样式就白重排整章，而正文版式纹丝不动。白重排本身是代价
  不是 bug，但"面板上能改、改了只换来一次无用的重排"仍是同一类信号缺失。

这三处现在都登记在一张分类表里（`reader/document/tests.rs` 的 `PrefClass` 与
`a_layout_preference_change_moves_the_geometry`）：归为**排版输入**的字段必须**真的**动到行盒，
归为**没接上**的字段必须**不动** —— 哪天接上了却忘了改分类，那条测试会先红一次。
`Reader` 新增字段而没归类是编译错误（那张表旁边有一份对 `Reader` 全部字段的解构）。
这是"标在字段旁"的当前形态：**落在测试与编译期，而不是注释里**，因为它能自己翻红。

另外澄清一句容易读混的话：文档里"日志级别改完重启就生效、**不用重新编译**"说的是不需要重编译，
**不是**不需要重启。

### 2.5 保存：去抖 + 原子 + 只写用户层

```
改一项 → 内存里立刻生效（换 Arc，界面照常重画）
       → 去抖 N 百毫秒后落盘一次
       → 落盘：写 <config.json.tmp> → fsync → rename 覆盖 config.json
       → 写的内容：只有用户显式改动过的项（见 2.1 第 3 条）
```

两个理由：**去抖**是因为拖滑条会产出几十次写，每次都是 fsync；**原子**是因为直接覆盖写会在断电时
留下一个截断的 JSON，而截断的 JSON 会让下次启动读不到配置。同文件系统内的 rename 是原子的，
所以最坏情况是"改动丢了"，不会是"起不来"。

连带一条：**任何配置变更不该触发无关服务重启。** 现状是配置观察者的回调里无条件重启监听服务
（`ui/shell/mod.rs:205` 那行），而停旧服务是同步等待（`ui/shared/watch.rs:28-31` 的模块注释自己写了
最多等一轮 tick，一秒内）。改法是：只有监听相关那几项（目录、开关、节奏）真的变了才动，
且"停旧"那一步挪到后台。

### 2.6 版本、夹取、未知字段：写坏了不能拒绝启动

配置文件要带**自身的版本号**，理由与数据库迁移一样：格式会演进，而读者会跨版本回退。
版本号只描述文件格式，环境变量的覆盖不参与版本判定。三条规矩：

1. **未知字段忽略，不报错。** 读者升级又降级是真实会发生的事；因为多认出一个字段就起不来，
   是最坏的一种失败。
2. **缺字段用默认值 + 一条 WARN**，而不是静默。静默会让"我的设置没保存住"变成无法诊断的问题。
3. **越界值夹取而不是拒绝。** 字号被手工改成 900 时，夹到上限并记一条日志，比拒绝整个配置好。
   后端已有的 `normalize`（读入后统一夹取）这个形状要保留并扩展到每一段。

合起来就是：**一份坏配置最坏只能让默认值生效，绝不能让应用起不来。** 起不来时读者连改回来的机会都没有。

### 2.7 路径：派生的进代码，用户挑的进配置

两类东西都叫路径，归属相反：

- **派生路径**——数据根、库文件、日志目录、主题目录、配置文件自身的位置。它们是"一个根 + 平台规则"
  算出来的，**不进配置文件**。三个理由：**引导循环**（要知道配置文件在哪才能读配置，而配置里写着
  配置文件在哪；移动端尤其无解，数据根要等宿主注入才知道，那一刻还没有配置）；**两处真相**（配置说库在
  `X`、推导规则说在 `Y`）；**跨机失效**（把 `config.json` 拷到另一台机器是很常见的自救动作，一拷就全错）。
  规矩是「别处不许拼路径」，靠一条纪律 + 一个来源模块（`folio_core::paths`）实现，而不是把路径搬进配置。
- **用户挑的路径**——书库目录、监听目录、导出目录。这些是用户的选择，**进配置文件**。

环境变量仍然可以覆盖**数据根**（一个根，其余全部跟着派生）——这条要保留，因为它是
"应用目录里取不到日志"时唯一的自救口。注意它的身份是**覆盖根**，不是配置里的一项。

### 2.8 秘密

**口令类字段集中成一个 struct**，即使暂时明文。理由不是安全，是**将来能整体平移**到系统钥匙串：
散在各处的明文口令无法一次替换。现状把 WebDAV 凭证放在同一个 struct 里正是为此；这条要当成
明确的技术债记着，不要当成已解决。

## 三、错误处理

### 3.1 两层库，三档可见性

库的分工已定：**后端一个能按分支处理的枚举（`thiserror`），界面一条能说清的因果链（`anyhow`）**，
后端不许反向依赖界面的错误类型。这里要补的是**读者能看见什么**这件事的分类，因为它决定错误
该往哪儿冒：

| 档 | 判据 | 例子 | 处置 |
|---|---|---|---|
| **致命** | 读者要的这件事没做成 | 这本书打不开、库打不开、写配置失败 | 界面必须说，带一条可操作的下一步 |
| **降级** | 做成了，但缺了一块 | 第 37 章坏了、这张图取不出、没有封面 | 界面就地标注，不弹窗（章内一行提示、图留位、版式兜底） |
| **自愈** | 读者不知道也好 | 缩略图重生成、孤儿文件回收、索引过期后重算 | 只进日志，级别 `debug`/`info` 各一次，**不许刷屏** |

三条硬规矩：

1. **底层错误留在 source 链上**，不许压成字符串。压平之后上层想按类型判断只能匹配文案——
   后端那个枚举的每个变体都因此要求带 `#[source]`，而 `error.rs` 里那个保留链的助手是现成的形状。
2. **`.ok()` 只允许出现在"自愈"那一档**，而且要配一句日志。其余一律显式处理。
   回调没有调用方可以 `?`，就在那一层 `report` 一次，把整条链写进日志。
3. **每条错误必须自带上下文**：哪个路径、哪本书、哪一章。没有上下文的错误等于没记录。

### 3.2 批量作业要出报表

一条与"三档"配套、但目前没有实现面的规则：**批量作业的错误要能聚合报表**（成功 4997 / 跳过 3 /
失败 1 + 原因分类），而不是只进日志。`ImportReject` 这类可数分支的存在就是为了这件事。

这是 `plans/import-trait.md` 的「还没做」里明确列着的一项——「导入失败的界面呈现（现在只有日志，
读者只知道少了几本）」。它属于基础设施，因为它是**错误类型的呈现约定**，不是某个功能的界面。

### 3.3 不许 panic 的边界

任何来自文件、网络、上传的输入都不许让程序 panic——畸形 zip、超深嵌套、假声明的 size、
截断的 XHTML 全都得走到某个 `Err` 分支里去。唯一允许 `expect` 的地方是**线程与运行时创建失败**
（起不来确实无法继续），这类调用点在导入、监听、传书三处，保持现状。

## 四、日志

### 4.1 形状已定，补纪律

三处出口共用一个过滤器：**文件**（`<数据根>/logs/folio.log`，开机轮转、写满即停手）、
**stderr**（桌面默认开）、**宿主**（Android 的 logcat）。级别在 `config.json` 的 `logging` 一节，
**改完重启生效、不用重新编译**——这一条是这套日志系统最大的价值，真机上出问题最怕的就是
"什么都不显示"，而重新编一遍 Android 是十几分钟加一次重装。

要补的是四条纪律：

1. **热路径不许 `info`**。现状有一条每张图片每一帧的 `info`（`ui/features/reader/scene.rs:133`），
   有插图的章节滚动时一秒能刷出几十条，既刷爆文件又让格式化开销进帧预算。降成 `trace`，
   或直接删（那三个字段的值在需要时从别处也能推出来）。
2. **默认级别不该包含依赖库**。`folio_core` / `folio_app` 自己可以开 `debug`，
   wgpu / cosmic-text 那一串固定在 `warn` 以上，否则"打开 debug"等于把整个 GPU 栈一起打开。
   要看它们，用环境变量按 `RUST_LOG` 的写法临时压过配置。
3. **字段化，别靠文案**。日志要带可 grep 的键：`book_id` / `chapter` / `job` / `stage` / `path`。
   一句"导入失败：xxx.epub"能查，一句"导入失败"不能查；而中文文案会随本地化改动，
   靠它做诊断等于给自己埋雷。
4. **耗时用 span，不要自己算时间差**。只有三处值得布 span：**一次排版作业、一次导入作业、
   一次打开容器**。它们恰好是性能问题最常出现的地方，所以 span 就布在这儿，而不是布在所有函数上。

### 4.2 开机那一条

启动时打一条 INFO，把**实际生效的结果**写出来：数据根、日志级别与目标、库的 schema 版本、
配置的版本、各常驻服务的起停状态。这一条的价值是：读者报障"什么都看不见"时，
那一条日志就能区分"配置没读到"、"日志没开"、"数据根不对"三种完全不同的事故。

## 五、还有什么：目前没人统管的横切事项

你问还有什么——这十一条是我认为现在散落在各处、缺一处收口的东西。每条给"规矩"而不是实现细节，
因为实现属于各模块。

1. **一切持久化格式带版本戳。** 这是整份文档最该立的一条。数据库有 schema 版本；配置该有自己的
   版本；阅读位置那串文本要有格式版本；分章与规范化口径已有 `index_version`（`store/schema.rs` 的 v9
   迁移里那一列）；内容哈希要配 `hash_algo` 列；缩略图要有"规格版本"（换尺寸/换编码就该重生成）；
   资源表里的容器内偏移只是提示、其新鲜度也要有个说法。**统一规矩：读到旧版本 = 迁移，不是崩溃，
   也不是静默当新版用。**
2. **存储与迁移。** 迁移必须在测试里被**真的跑过**（旧库 → 新库，然后断言旧数据还能读出来），
   而不是只测新库。库是唯一不可再生的数据（进度、批注、分组），所以还要回答一个目前没人问的问题：
   **要不要备份？** 至少要有"库文件打不开时不覆盖它"这条护栏——损坏的库被自动重建，等价于丢数据。
3. **内存预算。** 三条缓存各有封顶（章的解析产物、shaping、图片纹理），需要一个**总上限**和一个
   **降级顺序**（先丢纹理、再丢 shaping、再丢远的章节、最后才动当前页）。Android 上有内存压力回调，
   这是唯一一个移动端会强制你回答这件事的地方，桌面端则会一直不回答直到被系统杀。
4. **文案与语言。** 文案表在后端（编译期嵌入，`locales/` 下一门语言一份，回落到 `en`），
   与框架的组件层语言回落一致，这样缺一条日文文案时框架和我们一起回落。**规矩：代码里不许硬编码
   读者可见的文字**，包括日期与数字的呈现格式。
5. **时间与日界。** 阅读统计的"今天"依赖本地日与 UTC 秒的换算，跨时区与夏令时是已知坑，
   已经收敛在一个模块里；规矩是**其余地方不许自己除 86400**。
6. **启动与关闭的固定次序。** 配置 → 日志 → 库（含迁移）→ 界面 → 常驻服务。关闭时反序，
   且作业池必须先于库连接销毁（见 1.3）。这条现在没有任何地方写着，而每一次"启动顺序调一下"
   都可能撞上一条隐藏依赖。
7. **测试基建。** 三条既有规矩要成文：测试内联在被测代码所在文件底部；不用 glob 导入
   （框架那条依赖里带一个名为 `test` 的属性宏，glob 进来会让 `#[test]` 递归展开成它）；
   只测公开面。**再加一条新的：性能断言优先用计数而不是计时**（"取 100 张图，中央目录解析次数
   必须为 1"这类），因为计数在 CI 里稳定、不需要真机、不会被噪声骗。
8. **诊断入口。** 一个 dump（**每一项配置的生效值 + 它来自哪一层 + 被谁覆盖**、库版本、
   各缓存的命中率与占用、作业队列长度）。
   成本极低，而排障几乎全靠它。它同时是"缓存到底有没有命中"这个问题唯一的证据来源——
   这个问题在接线增量排版之后一定会被问到。
9. **平台能力的边界。** 平台分支只允许出现在两个模块（宿主服务、平台入口）；其余地方出现平台判断
   就是越界。这条与"后端零窗口依赖"并列，是这个项目两条真正的架构边界。
10. **安全边界成清单。** 路径穿越（上传的文件名在进收件箱前剥掉一切路径成分）、
    解包炸弹（取字节已有的三道闸：每本 face 数、单文件大小、总量上限）、配对码错误必须 403、
    随机配对码每次启动重生成。这些散在各模块里已经做对了，但没有一处把它们列成**必须守住的清单**，
    于是下一次重构很可能悄悄拆掉一条。
11. **界面线程与后端的唯一共享物是 `Arc`。** 不共享 `Mutex`；后端那个数据库内部的锁是实现细节，
    不许因为"界面想快一点"而在界面上再缓存一份可变状态——那是第二份真相。正确做法是走
    读写分道（读走快照，写走队列）。

### 7.2 实现与本文档口径不同的四处

「排版为什么走第二只池」这一处已经在 2026-10-12 写成 §1.1 的第五条规矩，所以这里不再列它。
剩下的四条是口径差异或仍未接的口子：

1. **封顶的口径不同。** §1.1 那张表的「上限」列写的是「每本书同时在跑的作业数」，实现是
   **每一档全局**封顶（4 / 4 / 1 / 1）。当前只有单本（`AppShell::reading` 是 `Option`），
   两种口径同解；多本同开那天必须挑一条。
2. **允许 `expect` 的三处换了名单。** 现在是 `task.rs`（起工作线程）、`watch.rs`（起监听线程）、
   `import::forward`（起事件转发线程）。传书那处已经改成返回 `Error::Io`，比 §3.3 要求的更严。
3. **三档可见性（致命 / 降级 / 自愈）没有落点。** 词汇散在注释里（`ui/shared/library.rs` 的
   「这是自愈动作」、`reader` 的降级路），但没有任何一处能让「这条错误该不该说给读者」被查出来；
   `or_log` 是这条纪律唯一成形的落点（它强制"自愈档可以吞，但必须留一句日志"）。
4. **缓存命中率仍然没有出口。** `BlockCache` 报得出 `hits` / `misses`，但那两份挂在阅读会话
   持有的实体上，而开机那一刻还没有任何缓存 —— 所以这一项要么在退出时补一条，要么给界面一个
   入口，挂在启动 dump 里会永远是空的。`metrics` 那三个计数器同日已经进 dump。

### 7.3 接下来能做的，按代价从小到大

2026-10-12 这两轮做掉的：段间距接上（§2.4 那段实测）、偏好消费者的那道门、诊断补计数器、
外壳那条平台判断挪进 `host`；导入那一轮又带走了「`Cleanup` 档零调用点」与「批量报表算不出数」
两条（见本节 §1.1 / §3.2 那两行）。剩下这些：

1. ~~**`justify` 接线或改名。**~~ **已接**（2026-10-16）：行内剩余宽度按「有空格拉空格、
   否则拉字间」摊开（`layout::collect::justify_plan`），绘制/命中/选区同源；分类表里
   `justify` 由 `NotWired` 提到 `Layout`。`Reader.justify` 默认 `true`，所以这一格接通后
   全书正文真的两端对齐了（此前一直按左对齐排）。
2. **目录那三项白重排。** `toc_density` / `toc_max_title_lines` / `toc_dim_read` 跟着整份
   `Reader` 进 `prefs_hash`，改一次目录样式就重排整章却不动正文。三条路：把目录字段从 `Reader`
   拆到另一节（`Reader` 就真的是"排版输入"那一节了）、`prefs_hash` 分部、或者认了这个代价并
   在字段旁写明。推荐拆节 —— 现在 `Reader` 这个名字与 §2.4 那张表已经在骗人了。
3. **热生效 / 重启生效标到字段旁（§2.4）。** 分类表管的是"有没有消费者"，管不了"改了要不要
   重启"。形式可以是每节一张 `生效时机` 常量表 + dump 里能打出来；重点是让「改了没反应」和
   「当场没生效、重启才对」两类 bug 一分开就能看出是谁漏的。
4. **落盘挪到后台线程，然后才谈 fsync**（§六 #2 剩下的半条）。现在 `ConfigHolder::save` 是
   界面线程里的同步写，加 `sync_all` 等于把这个代价直接放到帧预算上。
5. **批量作业的聚合报表**（§3.2 + §六 #7）。`ImportOutcome` 已经带逐本结果，缺的是按
   `ImportReject` 分类计数和一张可折叠卡片；`shelf/scan.rs` 那套「候选 / 跳过 / 截断」的
   呈现是现成的先例。
6. **三档可见性收口**（§7.2 第 3 条）。建议后端只报事实（可重试 / 可忽略 / 不可用），
   「读者看得见什么」这一档判据留在 `ui/shared/error`——它是界面属性，放进后端就会逼出
   一个「后端猜界面」的字段。这条要先定设计再动手。
7. **备份策略里最便宜的一档**（§六 #3）：`store.user_version` 一变就先拷一份库文件再跑迁移。
   比按时间定期备份小一个数量级的投入，而它防的正是「唯一不可再生的数据」最怕的那次改动。
8. **内存预算的执行端**（§5.3）。顺序按可逆性排：先给每类缓存加只读的 `bytes()`（随时能撤）→
   再接 `evict(fraction)`（会真丢东西，得先有 §5.3 那条降级顺序的测试压着）→ 最后才接
   移动端的压力回调。前一步没做完就不要动后一步，否则丢的是什么没人说得清。
9. **缓存命中率的出口**（§7.2 第 4 条）：`BlockCache` 的 `hits` / `misses` 已经在实体上，
    缺的只是「什么时候打」。
10. **安全边界成文**（§5.10）：四条列一张表，注上各自的测试在哪。实现已经做对了，缺的只是
    「下一次重构不许悄悄拆掉哪一条」这句话。
11. **iOS 与鸿蒙补上有序收尾**（§7.1 里 §1.3 那一行的缺口）。这两个入口没有 `run(...)` 返回
    之后那一步，所以监听线程、传书线程、作业池都靠宿主进程被杀来回收 —— 而 §1.3 说的「跑完
    已排的」与「作业池先于库连接销毁」在这两个平台上等于没生效。这一条不能顺手挂到
    `onDestroy` 上：那份 fork 的 Java `onDestroy` 是**等渲染线程停下来才返回**的
    （`gpui-mobile` 的 `src/android/host.rs` 模块注释写明了这条，为了 Activity 重建时不换新线程），
    所以在销毁回调里排干队列是反着来的方向。iOS 那边语法上有一个位置（`ios_main()` 里
    `run_app()` 返回之后，与桌面同形），但那个运行循环到底会不会返回要先实证。鸿蒙那一侧
    是 NAPI 模块、没有这个返回点，要么实证宿主给的销毁时机，要么就接受「进程被宿主杀掉时
    排不排干由不得我们」—— 后者的损失只有最后一小段进度，前提是位置与配置都已经在那个
    400ms 的去抖窗口里落过盘（§1.3 末条说的正是这件事）。
