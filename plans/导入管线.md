# 导入管线

> 状态：**施工中**。落地进度记在下面「施工标注」那一节，每完成一步就地标一次（标的是实际形状与偏离，不是复述本文）。
> 本文的原始设计内容保持不动——它是判定「代码对不对」的那一方，改它要另起一轮讨论。
>
> 这份文档定义「一本书从外部进到书库、变成一行可打开的记录」这条管线的形状。它替换的核心是

> `path TEXT NOT NULL UNIQUE`），本设计改为**内容哈希**。差额逐条列在第七节。
>

## 一、管线顺序

七步，分成两段，**分界在第 4 与第 5 步之间**：前四步是「把字节安全地搬进库」（与格式无关、可纯测、失败就删暂存），后三步是「把这堆字节变成一本书」（完全依赖格式）。这条分界不是为了好看，它决定了能不能有一个不重读字节的 `reindex`，见本节末尾。

```
来源分派 ──▶ 候选（一次性字节流 + 建议名 + 来源标识 + 大小提示）
      │  1
      ▼
完整写入暂存 ──▶ <书库>/.staging/<临时>.part   【唯一消费来源字节流的一步】
      │  2
      ▼
对本地 .part 算 SHA-256 + 三层格式判定   【本地可 seek：头部与 ZIP 中央目录都读得到】
      │  3
      ├─ 判不出 / 不支持 ─▶ 删 .part，报告「不支持的格式」
      ▼
判重（按内容哈希）
      │  4 ├─ 命中且旧文件仍在 ─▶ 删 .part，新来源挂到已有记录，报告「已存在」
      │    └─ 命中但旧文件已不在 ─▶ 继续落地（自愈：把丢了文件的记录重新接上）
      ▼  ──────────── ingest 与 index 的分界 ────────────
定名落地 ──▶ <书库>/books/<哈希前缀>.<ext>（同分区 rename，O(1) 且原子）
      │  5
      ▼
解析器分派 + index() ─▶ 元数据 / 资源表 / 章节表（含每章规范化字数）/ 目录 / 封面
      │  6   【允许读正文：字数就是这么来的】
      ├─ 解析失败（章节表出不来）─▶ 删副本，库里不留行
      ▼
落库 ─▶ 库里一行「可打开的记录」
         7 └─ 落库失败 ─▶ 删副本，库里不留行
```

| 步 | 做什么 | 产物 | 为什么必须在这个位置 |
|---|---|---|---|
| 1 | **来源分派**：按导入方式取候选 | `Candidate`（一次性字节流 + 建议显示名 + `size_hint` + `Origin`） | 「候选从哪来、一次来几个」是各来源自己的事，管线不想知道 |
| 2 | **完整写入暂存** | `.part` 文件 | 来源的字节流只在这里被消费一次；之后每一步都面对一个可 seek、可重读的本地文件（第四节解释为什么不在这里做边读边算） |
| 3 | **算哈希 + 判定格式** | 内容哈希、格式标签 | 哈希决定最终路径，必须先于落地；而 ZIP 的中央目录在**文件末尾**，只有落地成本地文件才读得到（第五节） |
| 4 | **判重** | 决定「继续落地」还是「挂到已有记录」 | 判重需要完整哈希，只能排在算完之后 |
| 5 | **定名落地**：`.part` 改名成哈希名 | 书库里的正式副本 | 改名与最终位置同文件系统，因此是原子的；崩溃时库里只可能有 `.part`，不可能有半成品 |
| 6 | **解析器分派 + `index()`** | 元数据、资源表、章节表与每章字数、目录、封面 | 解析要读容器与正文，只在书已在库里、路径已稳定之后做 |
| 7 | **落库** | 一行可打开的记录 | 第 6、7 步任何失败都会删掉刚落地的副本，因此「库里有这行」等价于「这本书能打开」 |

### 分界的用途：`ingest` 与 `index` 是两个函数

```rust
ingest(candidate) -> Ingested { path, content_hash, format }   // 第 1–5 步
index(&Ingested)  -> BookId                                    // 第 6–7 步
reindex(book_id)  -> index(...)                                // 只重跑第 6–7 步
```

`reindex` 必须存在，因为「分章规则或文本规范化口径变了」（见第六节版本戳那一段）要求全库重解析。如果把它实现成"删掉再导入"，就会重读一遍字节、要求来源还在原处（而来源常常已经不在了），并且会把读者手工改过文件名的那本当成新书。切开之后，重索引只是"对库里那个副本再解析一次"，与来源彻底无关。

## 二、三条不变量

这三条是整个设计的承重部分，破坏任何一条都会让某一类事故重新变得不可讨论。

**一、来源只交出「一批」，不交出「一条流」。**
`Source` 的一次调用返回一个候选列表；一次性来源（文件选择器、批量清单、单条 URL）返回 N 个，常驻来源（目录监听、Wi-Fi 传书）**每次事件返回一个**。于是"持续产出"这件事留在监听器和传书服务器内部，`Source` 里没有 async、没有 channel、没有回调，可以在工作线程上被同步调用，也可以在测试里用手搓的假来源直接喂。

代价归来源：常驻来源必须自己做**去重与稳定判定**——编辑器保存一个文件常常连发多个事件，网络上传也可能重复推送。判据举例：相邻两轮观察里文件大小一致才放行。这类规矩如果放到管线里，管线就会被来源类型污染。

**二、字节只读一趟，落地之后与来源再无关系。**
解析、判重、排版、缩略图生成，全都只碰库里那个本地文件。这条挡住三类事故：Android 通过 `content://` 拿到的 URI 常常只能读一次或不支持 seek；网络流读到一半断开；源文件在读取期间被别的程序改动。落地之后每一步都可以独立重试，因为输入不再会变。

代价：候选的字节流是**一次性的**，重试粒度是整本而不是"接着上次的字节"。电子书的体积（几 MB 到几十 MB）让这个代价可以接受。

**三、来源不算哈希、不判格式、不碰数据库。**
这三件事对所有来源都完全一样。写进任何一个来源的实现里就必然漂移，所以全部收在管线。来源的职责只有一句话：**把字节送到。**

## 三、`Source` trait

```rust
/// 一次调用交出一批候选；常驻性由调用方（监听器、传书服务器）负责。
pub trait Source: Send + Sync + 'static {
    /// 写进日志、以及界面「来源」那一栏用的名字："文件选择器" / "本地目录 ~/books" / "WebDAV 服务器"
    fn label(&self) -> String;

    /// 此刻可导入的候选。空列表是正常结果，不是错误。
    fn candidates(&mut self) -> Result<Vec<Candidate>>;
}

pub struct Candidate {
    /// 建议显示名，不含路径成分。路径成分在这一层就要剥掉（Wi-Fi 传书尤其重要）。
    pub display_name: String,
    /// 总字节数。拿不到就是 None，界面显示"大小未知"而不是编一个数。
    pub size_hint: Option<u64>,
    pub origin: Origin,
    /// 一次性字节流。管线只读它一趟（第二节不变量二）。
    pub stream: Box<dyn Read + Send>,
}

/// 一本书从哪儿来的。用途是「能不能再拿一次」和「读者问起时说得清」，
/// **不是去重键**——去重靠内容哈希。
pub enum Origin {
    Local {
        path: PathBuf,
        /// 以下两栏都只是**提示**，不是证据：同步盘和打包解压都会伪造或保留时间，
        /// 判等只能用哈希。它们的用途是「省一次重读」：路径 + 大小 + mtime 三项
        /// 与库里记录一致时，跳过重算哈希。
        size_bytes: Option<u64>,
        mtime_unix: Option<i64>,
    },
    Url { url: String },
    Watched { root: PathBuf, relative: PathBuf },
    Received { peer: String },
}
```

配套的管线入口和结果形状：

pub struct ImportOutcome {

pub enum Imported {

### 与现行实现的一处重要差别：`stage` 不再是来源的方法

现行 `Source` 要求每个来源实现 `stage()`（本地文件走 `fs::copy`，URL 走流式 GET）。本设计把它收进管线：来源只交出 `stream`，**「写暂存」由管线做一遍，之后的哈希与判定都只面对管线自己刚写下的那个文件**，四种来源共用同一份落地代码。

收益除了少写三份落地代码，更实质的是**身份与内容必然一致**：哈希算在我们自己刚写下的字节上，而不是"来源那份可能被改过的文件"上。现行写法里 `stage()` 与后续判定分两次读源文件，中间那段时间源文件一旦被改动（同步盘正在写、下载器重传），记录就会指向一份内容已经变了的副本。

代价：想保留「书已在设备上、就地登记不拷贝」这条入口（现行 `Policy.copy_in = false`）的话，它与内容寻址正面冲突——哈希必须读完整个文件才知道，就地引用又要求不读。两者只能选一个：要么这条路改成"后台一次性算完哈希再转成副本"，要么放弃内容寻址。**本设计放弃 `copy_in = false` 这条路**（理由见第十一节已决第 1 条）。

## 四、为什么不在一趟读里同时干三件事

直觉上「边读来源、边算哈希、边嗅探、边写盘」省掉一次本地读，值得做。**它不划算，所以本设计拆成两步：先把来源的流完整写进 `.part`，再对那个本地文件算哈希、做格式判定。**

不划算的关键是一个关于容器格式的事实：**ZIP 的中央目录在文件末尾**。条目清单就在那里，所以"只吃头部若干 KB"判不出 CBZ（要列全部条目的扩展名），也读不到 EPUB 的 `manifest`（除非它恰好在前面）。要守住"只读一趟"，就得再加两个机制——一个留住尾部字节的环形缓冲，和一个"缓冲不够就回读"的兜底——而这正是复杂度最容易长错形状的地方。

拆成两步换来三样东西：

- 环形缓冲与 tee 一起消失，判定层可以随意 seek、分多次读；
- 第 2、3、4 步各自是单一职责、能独立单测的函数，而不是三个消费者交织的一段循环；
- 哈希算在自己写下的字节上，身份与内容必然一致（第三节那段论证）。

放弃的只有一遍本地顺序读，它与一次闪存顺序读同量级，而导入本来就由 IO 主导。**如果将来实测证明这一遍读确实贵，再把它合回一趟**——届时环形缓冲的尺寸应由实测的中央目录分布定，而不是现在猜。

进度照样有：第 2 步按 `(已写字节, size_hint)` 报，第 3 步算完哈希再报一次。作业层的报数与取消沿用 `plans/background-pipeline.md` 已定的两条互不覆盖的读数（逐本计数与字节级读数），本文不重复定义。取消的检查点排在**书与书之间**：取消时已经落库的那些是真的，界面上因此可以放心放一颗取消按钮。

## 五、格式判定分三层

**只看魔数会漏，只看扩展名会错。** 大部分电子书格式没有可用的魔数：EPUB 和 CBZ 都是 ZIP，头四字节都是 `PK\x03\x04`，与 DOCX、JAR、普通压缩包无法区分；TXT 与 Markdown 根本没有魔数；只有 PDF 和 PalmDB 系（MOBI / AZW3）可靠。

| 层 | 依据 | 能判什么 | 判不了什么 |
|---|---|---|---|
| 粗筛 | 文件扩展名 | 批量导入时先排掉非书文件（5000 个文件里可能 4000 个是杂物），省掉无谓的哈希 | 用户改了扩展名；无扩展名的下载 |
| 魔数 | 头部字节 | `%PDF` → PDF；偏移 60 处 `BOOKMOBI` → PalmDB 容器；`PK\x03\x04` → 是个 ZIP（但不知道是哪种书）；BOM / 首字节 → 文本编码 | EPUB vs CBZ vs 普通 zip；TXT vs MD |
| 容器嗅探 | 打开 ZIP 读条目 | **EPUB 的正解**：第一个条目必须是 `mimetype`、内容为 `application/epub+zip`、且**存而不压缩**（规范定死在偏移 38，所以读 50 字节即可判）；**CBZ**：条目扩展名全部是图片；**FB2（`.fb2.zip`）**：条目里有 `.fb2` | 单个 XHTML 文件（要读进去看有没有 `xmlns="http://www.idpf.org/2007/ops"` 之类的包壳） |

一条硬规则：**判定或解析失败的候选，最终不能在库里留下记录。** 它在两个位置分别达成：第 3、4 步失败就删 `.part`（还没进库）；第 6、7 步失败要删掉已经改名的副本（回滚那一次落地）。库里出现一条指向打不开文件的记录，比拒绝导入糟糕得多——前者需要专门的清理功能，后者只需要读者换个文件再试一次。

文本类（TXT / Markdown）没有魔数，判定即"扩展名 + 能按某种编码读通"，而它们的**分章规则本身是一种解析决策**（Markdown 靠标题层级、TXT 靠空行块数），所以这类书的章节表依赖第六节那个版本戳。

## 六、身份：内容哈希

### 为什么从路径换成哈希

路径做身份有三个绕不过去的问题：**换设备/换目录全盘失效**（`books.path` 是 `UNIQUE` 的绝对或相对路径，书库搬家即整库认不出）；**同一本书从三个来源进来会存三份副本**（下载、WebDAV、U 盘各一条记录、三套进度）；**改名即丢记录**。哈希一次解决三件，还顺手给封面与缩略图提供了同一套命名机制。

### 存法

- 完整哈希（32 字节）留在数据库里。
- **文件名用截断后的哈希 + base32**，例如前 16 个字符。截断在内容寻址用途下安全，而完整哈希做文件名会让路径长度在 Android 和 Windows 上被咬。
- 库里额外存一列 **`hash_algo`**。哈希函数被写进了身份，将来换算法就是换身份；记下算法名，迁移才可能是"重算一列"而不是"数据作废"。
- **哈希算法已定：`sha2`（SHA-256）**。`blake3` 不在现有依赖图里（`Cargo.lock` 无此包），引入它是一条新树；`sha2` 已在图上，按 `flate2` / `base64` 那条「转成直接依赖、不新增依赖树」的先例用即可。选 `sha2` 而不是同样已在图上的 `ring`，理由是它纯 Rust：不牵进 C 与汇编的构建，交叉编译到 Android 与鸿蒙时少一个工具链变量。
  关于吞吐的一条核实过的信息：`sha2` 0.10.9 的依赖只有 `cfg-if`、`cpufeatures`、`digest`，**没有 `sha-asm` 也没有 `cc`**，所以它确实是纯 Rust 构建；而 `cpufeatures` 是运行时特性探测，x86 的 SHA-NI 与 aarch64 的 ARMv8 SHA 扩展都在它的覆盖范围内，因此不要预设"手机上只能软算"。**但"aarch64 上实际有没有走到硬件那条分支"仍属未实测**，本文不写吞吐数字。真正决定导入速度的是顺序读与图像解码，哈希大概率不占大头；若实测发现它占，换 `ring` 或 `blake3` 都只是一次带 `hash_algo` 的迁移，不是身份崩坏。
  另一个要留意的坑：`Cargo.lock` 里现在有**两个版本的 `sha2`**（0.10.9 与 0.11.0，`digest` 同样两版）。加直接依赖时必须对齐到其中的一个版本，否则会把两条 `sha2` 都编进来——这与 `folio-app/Cargo.toml` 里那条「`jni` 版本要和 `gpui-pre-mobile` 依赖的那份对齐，对不上就会链进第二个 jni」是同一个问题。

### 判重的语义

**同哈希 = 同一本书。**

**命中判重要 `stat` 一下那条已有记录的副本文件还在不在。** 不验证就命中，等于把一条指向不存在文件的记录又确认了一次——读者手工删过文件、或一次只同步了数据库没同步文件的迁移，都会造成这种状态。文件在 → 丢弃暂存、把新来源挂到已有记录；文件不在 → 继续走落地，并把路径写回那条记录。后者是**自愈**：把一个已经坏掉的库修回来，而不是又拒读者一次。

判重同时带来一个副作用：两条记录可以共用一个文件，于是删除变复杂——删掉一条不能连带删文件，否则另一条的正文和批注一起消失。两种处置：

- **引用计数**（推荐）：删除时数一下还有多少条记录指向这个哈希，为零才删文件。计数从库里查，不需要额外表，也不会有计数与记录不一致的问题。
- 只登记不删 + 定期 GC：用"库里记录指向的哈希集合"与"books 目录里的文件集合"做差集清理。更宽松，但要求读者接受"文件可能比记录多"。

**不要选"删除即删文件"。** 同一本书有多个副本的读者，会在那一次删除里同时丢掉另一本书的批注。

### 外部改动怎么算

文件字节变了哈希就对不上，严格讲那就是另一本书。三种处置：视为新书、**标记"文件已被外部修改，位置可能失准"但允许打开**（推荐）、报错拒绝打开。推荐中间那条的理由很具体：最常见的情形是读者用别的软件改过元数据后重存，内容其实还是那本书，报错对他是纯粹的侮辱；但也不能当作无事发生，因为他一改，字符偏移就可能集体平移。

`mtime` 与 `size` 在这里的角色被降级：它们**只用来省一次重读**（重扫 5000 本的目录时，路径 + 大小 + mtime 三项全同就跳过哈希），永远不参与判等。现行实现里 `mtime` 承担的是"发现正文文件被换了"这件事（`schema.rs` v9 那段说明 + `store/books.rs:479` 那条 `SELECT path, size, mtime, index_version`），本设计保留同样的用途，只是它不再是唯一防线。

### 版本戳

偏移口径一变，全库历史位置集体平移且**不报错**，所以每本书要带一个"这份索引是哪一版算法算的"。

这一条**不需要新建机制**：现行库里的 `books.index_version`（`schema.rs` v9 加的，注释原话是"分章规则或位置方案一改（比如 Markdown 的标题层级），老库里那些 `Section(n)` 就指到别的章去了"）就是这个东西。本设计沿用它，并把覆盖范围从"分章规则"扩到"文本规范化口径"——后者一旦改动（比如决定行内图片不再占一个字符位），后果与分章改动完全同类：所有历史偏移集体平移。

读到旧版本的记录时**做迁移而不是冻结旧算法**：用每条批注自带的原文快照搜索重定位，然后改写成新版本，只保留最新一条口径。

## 八、导入替阅读付的账

一条原则：**凡是需要读完整本书才能得到的数，全部在导入时算完并落库。** 导入是读者唯一愿意等待的时刻，阅读中的每一秒都不该为它付钱。这也回答了"为什么导入和阅读是两条管线"——不是模块划分的美学，是**代价的分配**。

按这条原则，导入的产物清单是：

1. **元数据**（都柏林核心骨架 + `role` 多值 + `identifier[]` 带 scheme + `extras` 逃生口）。
2. **资源表**：容器内每个条目登记一行 `href → (寻址方式, MIME, 长度)`，**条目本体不落库**，正文与图片按需从源文件读。这张表的设计规则集中写在第十节，此处钉住三条最要紧的：**归一化 href 才是身份**（容器内的绝对路径，已解码百分号、已折叠 `../`），偏移与长度只是**加速用的提示**——重新打包一次，条目名字不变而偏移全变，所以寻址必须是"按名字找、命中提示就免解析中央目录"；表要能**整表 `DELETE` 后重建**（`reindex` 就这么做），因为它不存任何读者数据，纯派生；查询带一次**大小写不敏感的降级重试**（EPUB 里的引用与条目名大小写不一致是现实中常见的坑），且这个降级只在寻址层实现一次，不在各 provider 里重复。
3. **章节表 + 每章规范化字数**。字数表是被位置设计逼出来的：全书进度百分比要**脱离排版**才算得出（书架不打开书也要显示"读了 37%"，且两台屏幕宽度不同的设备要显示同一个数），而它要求手里有每一章的规范化字数。
   现行 `char_len` 被删掉的两个理由在这里都要正面回应：
   - "只写不读" → 本设计给它一个明确的读者：进度、百分比、批注排序、剩余时间估算。
   - "出库之后写不出真值（要读正文才数得清）" → 就是**在导入读**，一次性、后台、可取消。这正好是第二节那条"代价进导入"的原则的落地。
   一条约束：算不出来的章记 `None`，**不用字节数估**。字节↔字符的比例在各章之间不均匀（中英混排、标签密度），估出来的百分比会**不单调**——读者往下读而进度条后退，是产品上不可接受的。

   **`index()` 允许读正文，字数就在它里面算**（这条已定，见第十节「`index()` 允许读正文」那一段）。代价写认下来：导入的 IO 从"读清单"变成"读全书"，`reindex` 必然全量重读。换来的是不存在"字数还没算完"的中间状态，进度百分比恒为精确值，UI 不需要"约 37%"那种降级显示。
4. **封面**：解析产物，从容器抽出后按**它自己的字节哈希**存盘；库里只存描述（封面哈希、宽、高、MIME）。落地时机与失败处置见本节末尾「封面：为什么它排在解析之后」。缩略图是**可丢弃的磁盘缓存**，不进库，见「缩略图：一次解码顺带产出两档」。
5. **目录归一**：目录项的目标解析成位置锚（`id → 偏移` 索引在这里建），无目录的书合成章表。

### 封面：为什么它排在解析之后

封面不是导入第一趟能算出来的东西。书自己的哈希在写暂存那一趟就拿到了，而"这张图才是封面"必须读过容器清单才知道：EPUB 判封面要依次试三条规则（manifest 里标了 `properties="cover"` 的条目 → 老写法 `<meta name="cover" content="图片id">` → 正文里第一个被引用、名字含 cover 的图）；FB2 的封面在 `binary` 块里，由 `coverpage/image` 的 `href` 指过去；TXT 与 Markdown 根本没有封面。所以封面落地只能排在第 5 步之后，写文件的顺序是：

```
解析（第 5 步）→ 定位封面条目 → 从容器读出封面字节 → 算它自己的哈希
              → 写 <书库>/covers/<封面哈希前缀>.<ext>
              → 库里记 (书 id, 封面哈希, 宽, 高, MIME)
```

四条规矩：

**封面用它自己的字节哈希命名，不用书的哈希。** 三个理由：两本书共用一张封面（同一套系列设计）时自然去重；重新解析或换 provider 不该让封面文件改名；封面目录可以独立做垃圾回收，不必和书的记录耦合。

**抽封面失败不阻断导入。** 封面是装饰，不是内容的入口。处置：书目记录照常落库并标 `has_cover = false`，把这本挂进"待补封面"的后台重试队列。不能因为封面抽不出来，就让读者看不见这本书。
同一批解析产物各部分的失败代价**并不相同**，要分开处置：元数据缺字段（没有出版社）不影响可读，资源表缺条目影响局部（某张图不显示），而**章节表失败是致命的**——等于这本书打不开，此时那一行落库记录不该出现。第六节那条"库里有这行就等于能打开"的等价关系，只由致命那一档来守。

**重导同一本书不重写封面。** 字节相同 → 哈希相同 → 文件已存在就不写。这让"重扫整库"成为安全操作。

**引用计数要同时覆盖 `books/` 和 `covers/` 两个目录。** 一本书的封面可能被另一本书引用（同哈希），删书时不能连带删封面文件；计数从库里查（还有多少条记录的封面哈希指向它），不另设计数表。

### 缩略图：一次解码顺带产出两档

封面原图（常见 800×1200）不能直接进网格，需要两档缩放图：卡片档约 400px 宽、列表档约 96px 高。**主要成本是解码那一次，不是缩放**，所以一次解码顺手产出两档几乎不额外花时间。两档都落在可丢弃的磁盘缓存目录（`<书库>/.thumbs/<尺寸>/<封面哈希>.*`），整目录删掉只需重跑生成；库里只记尺寸与格式，不记图像字节。

与"代价进导入"这条原则的关系要说清：缩略图**不属于**"必须读完整本书才知道的数"，它是"每本一次"的活，所以既可以进导入，也可以懒生成。取舍如下：

| 做法 | 好处 | 代价 |
|---|---|---|
| 导入时生成 | 首次进书架不卡；缓存可整目录重建 | 首次全量导入更慢 |
| 懒生成（首次显示时补） | 导入快；只为用户真正看到的书花钱 | 第一次滚动书架时几十张图同时开工，正是最要 CPU 的时刻 |

推荐导入时生成，理由是"第一次进一个全新的空书架"每个读者都会经历，而"一次导入 5000 本"不是。但**这条要等实测数字出来再钉**：5000 本导入到底多花多少秒，取决于目标机型的 JPEG 解码吞吐，本设计不写估计值。

## 九、测试门

新方案必须钉住的断言，每条都应当在功能未实现时失败：

- **同哈希的第二来源** → 不落地新文件、不产生新副本、来源挂到已有记录、报告为 `Duplicate` 而非成功。
- **嗅探不过的字节流** → 暂存文件被清掉、库里没有这一行。
- **落地后、落库前被取消** → 库里没有指向不存在文件的记录（这检验第 6 步"有这行就等于能打开"那条等价关系）。
- **`.part` 残留** → 重扫时被识别并清理，永不被当成一本书。
- **路径 + 大小 + mtime 三项全同** → 跳过重算哈希（这是省时的门，反向断言：mtime 变而哈希不变 → 不重导、不产生新记录）。
- **两条记录共用一个文件时删其一** → 文件仍在，另一本的正文与批注完好。
- **同名不同内容的两本书** → 两条记录、两个哈希、UI 上不加自动改名后缀。
- **抽封面失败** → 书目记录仍然落库、`has_cover = false`、进待补队列，读者在架上看得见这本书。
- **章节表解析失败** → 库里**没有**这一行（与上一条对照：装饰失败留记录，内容失败不留）。
- **重导同一本书** → 封面文件不被重写（同哈希已存在即跳过）。
- **两条记录引用同一张封面时删其一** → 封面文件仍在，另一本的显示不受影响。
- **无封面的书（TXT）** → `covers/` 下没有它的文件，而书架上不出现空白卡（兜底封面在绘制时生成）。
- **第 6 步解析失败** → 已改名的副本被删掉、库里没有那一行（检验"落库之前失败要回滚这一次落地"）。
- **判重命中但旧副本文件已不存在** → 不报"已存在"，而是重新落地并把路径写回那条记录（自愈）。
- **`reindex(book_id)`** → 不重读来源、不改文件名、不新增记录；章 ID 通过 `source_key` 全部找回，历史批注一条都不漂。
- **同一本书用同一 `source_key` 重解析两次** → 第二次拿到的章 ID 与第一次相同（映射表不许发新号）。

## 十、解析器与资源索引

### 四个类型的分工

```
DocumentProvider —— 按文件格式认领文件、把容器读成结构。无状态，注册表里一条静态项，可服务一万本书
Container        —— 一种容器家族的字节寻址：ZIP / PalmDB / 裸文件 /（将来）PDF
Package          —— 一本书的只读门面 = Container + 资源表 + href 归一化 + 大小写降级
Document         —— 一本书的阅读会话 = Package + BookIndex + 内容访问（流式与定版式两支）
```

`Container` 是这一层新增的类型，理由是一个数量事实：**容器家族比格式少**。EPUB、CBZ、`.fb2.zip` 都是 ZIP，它们的寻址代码应当是同一份；TXT、Markdown、裸 XHTML 都是"就一个文件"；MOBI 与 AZW3 都是 PalmDB。让每个 provider 自己写一遍寻址，就会得到 N 份各自漂移的实现。所以：**provider 只写格式知识，Container 只写容器知识，两者的实现数量分别是 N 与 4。**

### 资源寻址：身份是名字，偏移是提示

```rust
pub enum Address {
    /// ZIP 家族：条目名是身份。offset / size / compressed 是上次解析中央目录时缓存的加速提示
    ZipEntry { name: String, offset: Option<u64>, size: Option<u64>, compressed: bool },
    /// PalmDB（MOBI / AZW3）：没有条目名，用记录号 + 头部若干字节的指纹抗记录重排
    PalmRecord { index: u32, head_fingerprint: u64 },
    /// 裸文件：同一文件内的字节区间；区间边界由分章规则算出，所以它受版本戳管
    FileRange { start: u64, end: u64 },
    /// 解包成目录的书（手工 unzip 的 EPUB）；第一版不实现，留位
    Sidecar { relative: String },
}
```

三条规则：

**按身份取字节，提示只用于跳过解析。** 重新打包一次（换压缩级别、加工具元数据、条目排序变化），ZIP 的中央目录偏移整体改变，而条目名不变。所以偏移与长度当缓存用：命中就免读中央目录，不命中就回退到按名字查。这与 `mtime` / `size` 在第六节里的角色是**同一个模式的第二次出现**——易变的事实只能当提示，稳定的事实才配当身份。

**归一化 href 的活儿归 provider，产出物归资源表。** 相对路径的基准在各格式里不同：EPUB 相对 OPF 所在目录、CBZ 相对容器根、裸 HTML 相对自身、FB2 用 `#id` 而不是路径。所以归一化需要格式知识；但归一化的结果统一成一种形状——**容器内绝对路径，以 `/` 开头，百分号已解码，`../` 已折叠**。寻址层因此只认一种键，不需要知道这本书是什么格式。

**大小写与编码的降级只实现一次。** EPUB 里 `href="Images/Cover.png"` 指到条目 `images/cover.png` 这种不一致在真实书目里常见，而各家打包工具的宽容度不同。降级链条（精确匹配 → 大小写不敏感 → 只比对 basename）写在 `Package` 一处，各 provider 不许各写一份——否则每加一种格式都要重新决定一次"宽容到什么程度"。

### 章的身份：provider 交 `source_key`，永久 ID 由库分配

```rust
pub struct ChapterSource {
    /// 该格式内部天然稳定的名字：EPUB 用 spine item 的归一化 href，
    /// FB2 用 section 的 id，TXT / Markdown 用 "auto:<序号>"
    pub source_key: String,
    pub title: Option<String>,
    pub address: Address,
}
```

库里维护一张 `(book_id, source_key → chapter_id)` 的映射。重解析时按 `source_key` 找回旧 ID；找不到的（分章规则变了、`auto:` 那类合成章挪了位）走内容指纹匹配；再找不到才发新 ID。**分工的理由：格式知识留在 provider，身份稳定性留在库。** provider 因此不需要知道章 ID 这个概念存在，而 `reindex` 重跑时历史批注不会集体失联。

### `index()` 允许读正文：已定，连同代价

`index()` 可以读正文，每章规范化字数就在它里面算出来。写认下来的两条代价：导入的 IO 从"读清单"变成"读全书"，`reindex` 必然全量重读。一条好处：不存在"字数还没算完"的中间状态，进度百分比恒为精确值。

配套一条软契约：`index()` 里**只有字数那一循环允许读正文**，元数据、目录、封面定位、资源表仍然只碰清单。这不是强制的架构约束，目的是"将来若想把字数拆成独立作业，能一眼看出要动哪一处"。

### 流式与定版式只在内容访问处分岔

```rust
pub trait Document: Send + Sync {
    fn mode(&self) -> LayoutMode;                 // Flow | Fixed
    fn index(&self) -> &BookIndex;
    fn anchor_to_y(&self, anchor: &Locator, ...) -> f32;   // 跳(锚)
    fn y_to_anchor(&self, y: f32, ...) -> Locator;         // 命中
}

pub trait FlowContents: Document {
    fn chapter_text(&self, chapter: ChapterId) -> Result<String>;   // 排版引擎吃这个
}

pub trait FixedContents: Document {
    fn page_count(&self) -> usize;
    fn page_image(&self, page: usize) -> Result<ContentRef>;        // 现成的图，不排版
}
```

共用的部分（元数据、目录、资源、锚与几何的互转）占大头，只在内容访问这一步分两支。**要避免的偷懒是"把定版式伪装成一章一页的流式书"**：那样 PDF 的文字块坐标与 CBZ 的整页图语义都会被压扁，将来加 PDF 文字层批注要整个推翻。既然第一版不做定版式实现，`FixedContents` 这一支**只留类型定义、不留实现**——`LayoutMode` 与两个子 trait 是数据结构里的位，不是代码路径。

### 打开一本书：三段，只有一段在 provider 里

前端的问句只有 `book_id` 与视口参数，中间那段是：

```rust
pub struct Opened {
    pub document: Arc<dyn Document>,   // Send + Sync：排版要能在后台线程持有它
    pub index: BookIndex,
    pub chapter_ids: Vec<ChapterId>,
}
```

| 段 | 谁做 | 为什么 |
|---|---|---|
| `book_id` → 路径与索引 | 库 / 会话 | 与格式无关 |
| 打开容器、建 `Package` | **provider + Container** | 怎么打开是格式知识 |
| 恢复阅读位置、把锚换算成 y | 会话 + 排版引擎 | provider 不知道"位置"这个概念 |

三条硬要求：

1. `Document` 与 `Package` 必须 `Send + Sync`，**因为排版要能离开窗口在后台线程跑**。这是本项目早就实测确认过的一条性质（排版可在别的线程完成、缩放窗口时不卡主线程），也是 `plans/facts.md` 里那条结论的意义所在。
2. 打开时**不重新嗅探格式**：入库时记下的 `format` 那一列就是权威。重新嗅探等于把格式判定变成两处真相，还白读一次文件。
3. `Package` 内部对容器句柄的处理是：**中央目录解析一次、留成不可变索引（`Arc` 共享），取字节时按当次调用打开一个读位置，不为整本书设一把全局互斥锁**。否则并行的排版作业与图片解码会互相排队，而它们本就是各读各的条目。

## 十一、已决与待决

### 已决（本文各处已按此写死）

| # | 问题 | 结论 |
|---|---|---|
| 1 | 要不要保留「就地引用、不拷进库」的入口（现行 `copy_in = false`） | **放弃**。内容寻址要求书在库里；保留它等于同时维护两套落地形状，而它现在没有来源在用 |
| 2 | 内容哈希变了（书被外部改过）算新书还是更新 | **更新已有记录并标记失准**（第六节「外部改动怎么算」那一段） |
| 3 | 删除策略 | **引用计数**，从库里查不加表；`books/` 与 `covers/` 两个目录都按计数处置 |
| 4 | 书库目录要不要人类可读（Calibre 那种 `作者/书名/`） | **不要**：改名要重命名目录、路径里的非法字符清洗、中日韩长标题撞路径上限。可移植性做成一条**导出功能**，不是内部存储形状 |
| 5 | 哈希算法 | **`sha2`（SHA-256）**，另存 `hash_algo` 列留换算法的余地 |
| 6 | 要不要"一趟读同时干三件事" | **拆掉**：先完整写 `.part`，再对本地文件算哈希与判定（第四节） |
| 7 | 失败回滚的位置 | **落库之前**：第 6、7 步失败要删掉已经改名的副本（第五节那条硬规则） |
| 8 | 判重命中 | **先 `stat` 旧文件**，不在就自愈式重新落地（第六节「判重的语义」） |
| 9 | `ingest` 与 `index` 是否拆成两个函数 | **拆**，`reindex(book_id)` 只重跑 `index`（第一节末尾的分界） |
| 10 | 章身份 | **provider 交 `source_key`，永久章 ID 由库的映射表分配**（第十节） |
| 11 | 每章规范化字数由谁产出 | **`index()` 允许读正文，在导入时算准**（第十节末段） |
| 12 | 资源位置怎么索引 | **归一化条目名是身份，偏移与长度是加速提示**；大小写与编码降级只在 `Package` 实现一处（第十节） |
